# coreShare

<!-- report-chip: coreShare -->

| Поле | Значение |
|---|---|
| Ключ в `metrics.json` | `coreShare` (число от 0 до 1) |
| Чип на вкладке Metrics | **coreShare** (значение × 100 с суффиксом `%`, до двух знаков после точки: `0%`, `25%`, `33.33%`, `100%`) |
| Где считается | `CorePathAnalyzer.Compute`, вызывается из `StaticMetricsCalculator.Calculate` по [графу модулей](../glossary.md#module-graph) |
| Порог | собственного порога нет: метрика не входит в `baseline.ratchets` и ни одно правило её не читает; правило [B5](../findings/B5.md) использует абсолютный [coreSize](coreSize.md) |

## Что измеряет

Метрика отвечает на вопрос: **какая доля учитываемых модулей решения входит в ядро** — в наибольшую циклическую [компоненту сильной связности](../glossary.md#scc).

```text
coreSize    = размер наибольшей циклической SCC (см. coreSize)
moduleCount = graph.Modules.Count  — учитываемые модули, в которых есть хотя бы один тип
coreShare   = coreSize == 0 || moduleCount == 0 ? 0 : coreSize / moduleCount
```

Знаменатель — это число строк в таблице Modules на вкладке Metrics: все модули с ролью не `host` и не `test`, у которых есть хотя бы один тип, включая изолированные модули без единого ребра. Числитель — только **одно** ядро. Модули из других, меньших циклических компонент в числитель не входят.

Почему у двухмодульного цикла доля равна единице. Если решение состоит из модулей `A` и `B`, и они зависят друг от друга, то `coreSize = 2`, `moduleCount = 2` и `coreShare = 2 / 2 = 1`: чип показывает `100%`. Это не ошибка расчёта — в таком решении действительно все модули входят в ядро. Юнит-тест `Two_cycle_is_below_default_core_size_min` фиксирует именно этот случай: `coreShare = 1.0`, `coreSize = 2`, находки B5 при пороге по умолчанию нет. Поэтому долю нельзя читать без абсолютного размера ядра и без числа модулей.

Второй пример, `Equal_size_cyclic_sccs_pick_ordinal_min_member_join`: четыре модуля, две независимые пары `{M, N}` и `{A, B}`. Ядро — `["A", "B"]` (ничья по размеру разрешена по ordinal), `coreShare = 2 / 4 = 0.5`, хотя в циклах состоят все четыре модуля. Доля «модулей в каких-либо циклах» была бы равна `1`, но такую величину инструмент не считает.

## Как читать

- Чип и JSON показывают одно число в разных единицах: чип `25%` — это `0.25` в `metrics.json`. Ядро из трёх модулей в решении из двенадцати даёт `0.25`.
- `0%` означает `no module cycles` в разделе Cycles. Любое ненулевое значение не меньше `2 / moduleCount`.
- Доля меняется от обеих величин: она растёт, когда к ядру присоединяется модуль, и падает, когда в решение добавляют модули вне ядра. Падение доли при неизменном `coreSize` — не улучшение: ядро осталось прежним, просто решение выросло.
- Метрика считается только по статическим рёбрам. Рёбра `binding`, выведенные из регистраций DI, в граф модулей не входят: см. [runtime](runtime.md) и [R1](../findings/R1.md).
- На вкладке Matrix подсказка чипа `cycles` в шапке отчёта показывает, сколько **компонентов матрицы** сидит в циклах, — это другое разбиение и другая величина; см. [отличие DSM от графа модулей](../glossary.md#dsm-vs-modules).

## Что считать плохим

- **Ядро занимает заметную часть решения** — например, `40%` при десяти и более модулях. Это означает, что модульные границы номинальны: почти любое изменение проходит через «середину», которую нельзя собрать и протестировать по частям.
- **Рост доли при неизменном числе модулей** — к ядру присоединился ещё один модуль; вместе с этим обычно растут [coreSize](coreSize.md) и [tanglePct](tanglePct.md), а гейт выдаёт [B1](../findings/B1.md) по новой компоненте.
- **`100%` в маленьком решении** читается вместе с `coreSize`: у двух взаимно зависимых модулей это нормальный, но тревожный старт, а у восьми — уже сетка.
- **Снижение доли за счёт нарезки новых модулей вне ядра** — искажение показателя, а не разбор цикла: раздел Cycles и B5 по-прежнему видят ту же компоненту.
