# B8 — Зона боли по Мартину или недостаточно абстрактный модуль с контрактом

| Поле | Значение |
|---|---|
| Код | `B8` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet`; сама по себе находка не блокирует |
| Кто выдаёт | `MartinMetricsAnalyzer.Analyze`, вызывается из `StaticMetricsCalculator.Calculate` и получает от него `fanInOut` |
| Команды | `map` — находка снимка, попадает в `findings.json` и на вкладку Findings; `gate` — проходит в `gate-report.json`, если её отпечатка нет в `knownFindings` |
| Метрика | [`martin`](../metrics/martin.md) — таблица **Martin** на вкладке Metrics (`instable`, `abstractness`, `distance`, `afferent`, `efferent`) |
| Пороги | константы в коде: `PainInstableMax = 0.3`, `PainAbstractnessMax = 0.3`, `Ca >= 2` для тега `pain`; `ContractAbstractnessMin = 0.5` для тега `concrete`; в YAML не настраиваются |
| Отпечаток | `ForTypeEdge("B8", module, tag, [])`, где `tag` — `pain` или `concrete`; `FromModule` — модуль, `ToModule` пуст, `Evidence` пуст |
| Сообщения | `zone of pain: {module}` для тега `pain`; `contract not abstract: {module}` для тега `concrete` |

## Термины

Базовые понятия — [граф модулей](../glossary.md#module-graph), [fan-in и fan-out](../glossary.md#fan), [учитываемый модуль](../glossary.md#scored) и [роли сборок](../glossary.md#module) — определены в словаре. Метрики Роберта Мартина здесь считаются на уровне модулей, а не пакетов или сборок.

**`Ca` (afferent, входящие)** — fan-in модуля: число различных модулей, зависящих от него. **`Ce` (efferent, исходящие)** — fan-out: число различных модулей, от которых зависит он.

**Неустойчивость `I`** (`instable`) — доля исходящих связей: `Ce / (Ca + Ce)`, `0` для модуля без связей. `I = 0` означает, что модуль ни от кого не зависит, а от него зависят другие: его тяжело менять, потому что любое изменение задевает зависимых. `I = 1` — обратная картина: модуль зависит от других, но от него не зависит никто, менять его безопасно.

**Абстрактность `A`** (`abstractness`) — доля абстрактных типов: `Na / Nc`. `Nc` — число всех учитываемых типов модуля во **всех** его сборках (контракт, реализация, инфраструктура, UI), любой доступности и любого вида. `Na` — число типов, у которых `Kind == "interface"`, плюс типов с `Kind == "class"` и флагом `IsAbstract`.

**Почему абстрактные записи не считаются абстрактными.** Экстрактор присваивает каждому типу вид по Roslyn: для записей (`record`, `record struct`, в том числе `abstract record`) это `"record"`, а не `"class"`, и предикат `IsMartinAbstract` их не пропускает — так же, как `BindingSemantics.IsPort` не считает их портами для DI. Смысл в том, что запись — носитель данных: абстрактная запись задаёт общую форму DTO, но не является точкой подмены реализации, ради которой Мартин и вводит абстрактность. По той же причине не считаются абстрактными перечисления, структуры и делегаты.

**Расстояние `D`** (`distance`) — `|A + I − 1|`, удалённость от «главной последовательности», на которой устойчивые модули абстрактны, а неустойчивые конкретны. Правило не проверяет `D` напрямую, но таблица Martin его показывает.

**Зона боли** (по Мартину) — угол, где `I` низкая и `A` низкая одновременно: устойчивый конкретный модуль. От него зависят многие, его нельзя подменить, потому что он не даёт абстракций, и его больно менять, потому что каждое изменение расходится по зависимым. В коде зона боли задана порогами `I <= 0.3`, `A <= 0.3`, `Ca >= 2` и отсутствием контрактной сборки.

**Модуль с контрактом** — модуль, у которого в каталоге сборок есть хотя бы одна сборка с ролью `contract`.

## Когда срабатывает

```text
Ca = fanIn(m);  Ce = fanOut(m)
I  = Ca + Ce == 0 ? 0 : Ce / (Ca + Ce)
Nc = число учитываемых типов модуля во всех его сборках
Na = число типов с Kind == "interface" плюс типов с Kind == "class" и IsAbstract == true
A  = Nc == 0 ? 0 : Na / Nc
D  = |A + I − 1|

если у модуля есть сборка с ролью contract:
    B8 с тегом concrete ⇔ A < 0.5          (проверка зоны боли для такого модуля не выполняется)
иначе:
    B8 с тегом pain     ⇔ I <= 0.3 и A <= 0.3 и Ca >= 2
```

Теги взаимоисключающие: у модуля может быть только одна находка B8, и она либо `pain`, либо `concrete`. Поскольку тег входит в отпечаток, появление контрактной сборки у модуля с принятым тегом `pain` даст новый отпечаток `concrete`, и находка всплывёт снова.

Условие `Ca >= 2` означает, что модуль с единственным зависимым в зону боли не попадает. Условие `I <= 0.3` при `Ca = 2` выполняется только при `Ce = 0` (одна исходящая связь даёт `I = 0.333`); при `Ca = 3` допустима одна исходящая, при `Ca = 5` — две.

Важная особенность тега `concrete`: `A` считается по **всему модулю**, а не по контрактной сборке. У обычного модуля из `Account.Contracts` (несколько интерфейсов и записей) и `Account` (десятки классов реализации) абстрактность заведомо меньше `0.5`, и `contract not abstract: Account` появится независимо от качества самого контракта. На практике такие находки попадают в `knownFindings` при первом `arch-lens baseline`, а правило сигнализирует о новых модулях. Сборки с ролями `host` и `test` не входят ни в `Nc`, ни в `Na`, ни в `Ca`, ни в `Ce`.

## Пример

Юнит-тест `Stable_concrete_impl_with_dependents_is_zone_of_pain`: модуль реализации `S` с одним конкретным классом; модули `A` и `B` ссылаются на него.

```text
Ca = 2, Ce = 0  →  I = 0
Nc = 1, Na = 0  →  A = 0
D = |0 + 0 − 1| = 1
нет контракта, I <= 0.3, A <= 0.3, Ca >= 2  →  zone of pain: S
```

Отпечаток `ForTypeEdge("B8", "S", "pain", [])`, `FromModule = S`. Тест `Isolated_impl_with_one_dependent_is_not_pain`: тот же `S` с единственным зависимым (`Ca = 1`) находки не даёт. Тест `Abstract_class_counts_toward_Na`: если единственный тип `S` — абстрактный класс, `A = 1`, `D = 0`, находки нет. Тест `Abstract_record_does_not_count_toward_Na`: если этот тип — абстрактная запись, `A = 0`, и зона боли остаётся.

Тесты для модулей с контрактом: `Contract_of_only_interfaces_is_not_B8_concrete` — модуль `Account` из одной сборки `Account.Contracts` с двумя интерфейсами даёт `A = 1`, `I = 0`, `D = 0` и не даёт находки; `Contract_of_only_classes_is_B8_concrete` — та же сборка с одним конкретным классом даёт `A = 0` и находку `contract not abstract: Account` с отпечатком `ForTypeEdge("B8", "Account", "concrete", [])`.

Пример ближе к практике: модуль `Account` состоит из `Account.Contracts` (3 интерфейса и 2 записи-DTO) и `Account` (10 классов реализации). `Nc = 15`, `Na = 3`, `A = 0.2 < 0.5` — тег `concrete`, хотя контрактная сборка целиком состоит из интерфейсов и DTO.

## Где смотреть в отчёте

- **Вкладка Findings** — строка `B8 | trigger | S | | zone of pain: S | ` или `B8 | trigger | Account | | contract not abstract: Account | `; колонка From заполнена, To и Evidence пусты. Та же запись — в `findings.json`.
- **Вкладка Metrics, таблица Martin** — по строке на модуль с колонками `instable`, `abstractness`, `distance`, `afferent`, `efferent`; дробные значения выводятся не более чем с двумя знаками после точки (`0.33`, `0.5`), целые — без дробной части. Таблица не выводится, если модулей нет. В `metrics.json` те же числа лежат под ключом `martin`.
- **Вкладка Metrics, заголовки модулей** — перечень сборок модуля с ролями: по нему видно, есть ли у модуля сборка `contract`, то есть какая ветвь правила к нему применяется.
- **Вкладка Metrics, таблица Modules** — колонки Fan-in и Fan-out, совпадающие с `afferent` и `efferent`.
- **`gate-report.json`** — тот же объект с `"class": "trigger"`, если отпечатка нет в `knownFindings`.

## Как исправить

1. Откройте таблицу Martin и заголовок модуля, чтобы понять ветвь: без контракта и `Ca >= 2` — зона боли; с контрактом — недостаточная абстрактность.
2. Для зоны боли дайте зависимым абстракцию: создайте `X.Contracts` с портами (интерфейсами) и переведите внешние обращения на них. Модуль получит контракт, и проверка зоны боли для него выключится; следите, чтобы `A` модуля не осталась меньше `0.5`, иначе тег сменится на `concrete`.
3. Другой путь для зоны боли — инверсия: пусть портами владеют зависимые модули, а `X` их реализует. Тогда `Ca` падает, `Ce` растёт, `I` уходит из зоны, и модуль перестаёт быть тем, от чего все зависят.
4. Для тега `concrete` повышайте долю абстракций и снижайте долю конкретных типов там, где это отражает замысел: интерфейсы вместо конкретных классов в контракте (за конкретные классы в контракте отвечает и [A5](A5.md)), вынос вспомогательных классов реализации в модуль, которому они на самом деле принадлежат. Помните, что записи-DTO абстрактность не поднимают, где бы они ни лежали.
5. Проверьте результат командой `arch-lens map`: строка должна исчезнуть, а в таблице Martin `distance` — приблизиться к нулю.

**Когда допустимо принять.** Общее ядро (`shared`) по природе устойчиво и конкретно: примитивы, идентификаторы, часы — и роль `shared` от проверки зоны боли не освобождает, поэтому B8 с тегом `pain` для него нормален и принимается через `arch-lens baseline`. Так же принимаются теги `concrete` у модулей, чьи тела закономерно велики. Отпечаток по модулю и тегу устойчив, поэтому принятая находка не возвращается, пока не изменится ветвь; новые модули правило продолжит отмечать.

## Чего не делать

- Не добавляйте пустые маркерные интерфейсы, чтобы поднять `A`: церемониальные интерфейсы отмечает [E3](E3.md), а абстракции без потребителей ничего не защищают.
- Не делайте записи абстрактными в надежде поднять `Na`: анализатор их не считает намеренно.
- Не создавайте пустую сборку `X.Contracts`, чтобы выйти из зоны боли: при `A < 0.5` тег просто сменится на `concrete`.
- Не читайте сообщение `contract not abstract` как оценку одной лишь контрактной сборки: метрика считается по всем типам модуля.
- Не гонитесь за `distance = 0` у каждого модуля: таблица Martin описательная, а находки дают только две описанные зоны.
