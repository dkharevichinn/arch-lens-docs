# C2 — Анемичный контракт или непрозрачное тело модуля

| Поле | Значение |
|---|---|
| Код | `C2` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `SizeBalanceAnalyzer.TryC2`, вызывается из `StaticMetricsCalculator.Calculate`; сравнивает число типов в контрактных сборках модуля с числом типов в его теле |
| Команды | `arch-lens map` (находка снимка: `findings.json`, вкладка Findings) и `arch-lens gate` (проходит в `gate-report.json`, если отпечатка нет в `knownFindings`) |
| Порог | анемичный контракт: `contractTypes > bodyTypes` и `bodyTypes >= 1`; непрозрачное тело: `bodyTypes >= 4 × contractTypes` и `contractTypes >= 1` и `bodyTypes >= 20`; константы зашиты в коде |
| Отпечаток | `ForTypeEdge("C2", module, tag, [])`, где `tag` равен `anemic` или `opaque`; у одного модуля два разных возможных отпечатка |
| Сообщение | `anemic contract: {module}` или `opaque body: {module}` |

## Термины

Понятия [модуль, сборка и роль](../glossary.md#module) и [учитываемый модуль](../glossary.md#scored) определены в словаре. Для этого правила нужны ещё три.

**Контрактная сборка** модуля — сборка с ролью `contract` (по конвенции `X.Contracts`). **Тело модуля** — его сборки с ролями `implementation` и `infrastructure`, взятые вместе. Сборки с ролью `ui` и `shared` ни к контракту, ни к телу не относятся, и их типы в этом правиле не считаются вовсе.

**`contractTypes`** — число типов во всех контрактных сборках модуля; **`bodyTypes`** — число типов во всех сборках тела. Считаются все типы, как в [C1](C1.md): интерфейсы, классы, записи, перечисления, вложенные типы, независимо от доступности. Публичность типа значения не имеет: `internal`-класс в теле — это единица `bodyTypes`.

**Анемичный контракт** — контракт, в котором типов больше, чем в теле, которое его реализует: модуль обещает больше, чем делает. **Непрозрачное тело** — тело, которое в четыре и более раз крупнее контракта при внушительном абсолютном размере: снаружи видна узкая щель, за которой скрыт большой механизм.

## Когда срабатывает

Сначала проверяется предварительное условие: в каталоге модулей у модуля есть **и** сборка с ролью `contract`, **и** хотя бы одна сборка с ролью `implementation` или `infrastructure` (`HasContract && HasBody`). Наличие определяется по привязкам сборок, а не по числу типов. Модуль без контракта, как и модуль из одних контрактов, из проверки исключается.

Далее считаются две величины и проверяются два условия строго в этом порядке:

```text
contractTypes = число типов в сборках модуля с ролью contract
bodyTypes     = число типов в сборках модуля с ролями implementation и infrastructure

anemic: contractTypes > bodyTypes  и  bodyTypes >= 1
opaque: bodyTypes >= 4 * contractTypes  и  contractTypes >= 1  и  bodyTypes >= 20
```

Условие `anemic` проверяется первым, и при его выполнении проверка `opaque` не запускается. На практике порядок не важен: условия исключают друг друга (в первом контракт больше тела, во втором тело как минимум вчетверо больше контракта), поэтому у модуля не может быть двух находок C2 одновременно.

Границы стоит держать в голове. Контрактная сборка без типов не даёт ни одной из находок: для `anemic` нужно `contractTypes > bodyTypes >= 1`, для `opaque` — `contractTypes >= 1`. Тело без типов тоже молчит. Тело из `19` типов при одном интерфейсе в контракте не считается непрозрачным (`19 < 20`); тело из `20` типов при `5` типах контракта — считается (`20 >= 20`), при `6` — уже нет (`20 < 24`).

Отпечаток включает тег, поэтому переход модуля из одного состояния в другое даёт **новую** находку, даже если старая была принята через `knownFindings`.

## Пример

Юнит-тест `Anemic_contract_is_C2`: в `Account.Contracts` лежат три интерфейса `IOne`, `ITwo`, `IThree`, в `Account` — один класс `Service`. Получается `contractTypes = 3 > bodyTypes = 1`, находка `anemic contract: Account` с отпечатком `ForTypeEdge("C2", "Account", "anemic", [])`.

Юнит-тест `Opaque_body_is_C2`: в `Account.Contracts` один интерфейс `IAuth`, в `Account` — двадцать типов. Проверка: `20 >= 4 × 1`, `1 >= 1`, `20 >= 20` — находка `opaque body: Account` с отпечатком `ForTypeEdge("C2", "Account", "opaque", [])`.

Юнит-тест `Implementation_only_module_is_not_C2`: модуль из одной сборки `Account` с двадцатью типами и без контракта находки не даёт — не выполнено предварительное условие.

Как это выглядит в коде. Анемичный вариант:

```csharp
// Account.Contracts: IAuth, IProfile, ISessions, IAudit, IQuota — пять интерфейсов
// Account:           AccountService — один класс, реализующий IAuth
// contractTypes = 5 > bodyTypes = 1 → C2 anemic: четыре интерфейса никто не реализует
```

Непрозрачный вариант: `Billing.Contracts` с двумя типами (запись `InvoiceId` и интерфейс `IInvoices`) и тело `Billing` + `Billing.Infrastructure` из сорока классов дают `40 >= 8`, `2 >= 1`, `40 >= 20` — C2 `opaque`.

## Где смотреть в отчёте

- **Вкладка Findings** — строка `C2 | trigger | Account | | anemic contract: Account |` или `… | opaque body: Account |`; колонки To и Evidence пусты.
- **Вкладка Metrics, заголовки модулей** — под таблицей Contracts для каждого модуля перечислены его сборки с ролями, например `Account.Contracts (contract), Account (implementation), Account.Infrastructure (infrastructure)`. По этому списку видно, выполнено ли предварительное условие.
- **Вкладка Metrics, таблица Modules** — колонка Types показывает суммарное число типов модуля по всем ролям; отдельно `contractTypes` и `bodyTypes` отчёт не печатает. Точные числа можно получить из `graph.json`, сгруппировав типы по сборке, или из таблицы Layer LOC как грубого ориентира (там строки, а не типы).
- **Вкладка Metrics, таблица Contracts** — колонка Surface считает публичные типы и члены контрактной сборки; это метрика [contractSurface](../metrics/contractSurface.md), она с `contractTypes` не совпадает.
- **`gate-report.json`** — находка проходит через гейт, если её отпечатка нет в `knownFindings`.

## Как исправить

1. Для анемичного контракта выясните, кто использует каждый тип контрактной сборки. Интерфейсы без реализации в теле и DTO без внешних потребителей — кандидаты на удаление либо на перенос внутрь тела. Ориентир — таблица Contracts и находки [A5](A5.md) о церемониальных интерфейсах.
2. Если контракт честный, но тело маленькое, спросите, не живёт ли реализация в другом модуле или в `host`: возможно, перенос кода в тело модуля восстановит пропорцию и заодно уберёт [A1](A1.md).
3. Для непрозрачного тела проверьте, какие возможности модуля соседи получают в обход контракта (находки [A1](A1.md)/[A2](A2.md)) — это порты, которых в контракте не хватает. Опубликуйте их как интерфейсы и DTO.
4. Если тело действительно велико, разделите его по фичам на модули с собственными контрактами, используя [D2](D2.md) и [D3](D3.md) как карту, а не выносите «инфраструктуру» в отдельный технический модуль.
5. Повторите `arch-lens map` и убедитесь, что не появились новые [A4](A4.md)-ключи с непродуманной поверхностью.

**Когда допустимо принять.** Модуль, который по замыслу состоит из контрактов и тонкого адаптера (например, модуль интеграционных событий), анемичен по природе; модуль-«движок» с намеренно узким фасадом непрозрачен по природе. Такие находки фиксируются командой `arch-lens baseline`: отпечаток с тегом попадает в `knownFindings`, и гейт молчит, пока модуль не сменит состояние. Опишите причину в описании коммита с `baseline.json`.

## Чего не делать

- Не добавляйте в контракт пустые интерфейсы и маркерные типы, чтобы «уравновесить» непрозрачное тело: это увеличит [contractSurface](../metrics/contractSurface.md) и разбудит [A4](A4.md), а [A5](A5.md) отметит церемониальные интерфейсы.
- Не удаляйте контрактный проект, чтобы снять предварительное условие: без контракта соседи смогут зависеть от модуля только в обход, и каждое такое ребро станет [A1](A1.md).
- Не переносите классы тела в сборку с ролью `ui` и не переназначайте роли в `arch-lens.yaml`, чтобы уменьшить `bodyTypes`: числа поменяются, архитектура — нет.
- Не сливайте два маленьких контракта в один ради пропорции: контракт описывает границу одного модуля.
