# C3 — Код UI модуля объёмнее кода его реализации

| Поле | Значение |
|---|---|
| Код | `C3` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `SizeBalanceAnalyzer.Analyze`, вызывается из `StaticMetricsCalculator.Calculate`; сравнивает два поля `LayerLoc` модуля |
| Команды | `arch-lens map` (находка снимка: `findings.json`, вкладка Findings) и `arch-lens gate` (проходит в `gate-report.json`, если отпечатка нет в `knownFindings`) |
| Метрика | [layerLoc](../metrics/layerLoc.md), таблица Layer LOC на вкладке Metrics, колонки `implementation` и `ui` |
| Порог | `uiLoc > implementationLoc` и `implementationLoc > 0`; порог не настраивается |
| Отпечаток | `ForTypeEdge("C3", module, "", [])` — один на модуль |
| Сообщение | `ui outweighs implementation: {module}` |

## Термины

Роли сборок описаны в [словаре](../glossary.md#module); там же есть краткое определение [LOC](../glossary.md#loc). Для этого правила его нужно понимать точно.

**LOC типа** (`Loc`) — число строк исходного текста, которые занимает объявление типа: от строки, на которой начинается объявление, до строки его закрывающей скобки, включительно. Экстрактор (`RoslynGraphExtractor.CountLoc`) берёт диапазон строк каждой синтаксической части объявления и складывает их, поэтому `partial`-класс из трёх файлов даёт сумму трёх диапазонов. В счёт входят пустые строки, комментарии и XML-документация **внутри** объявления, но не `using`-директивы и не объявление пространства имён снаружи. Части, лежащие в сгенерированных файлах (с суффиксами `.g.cs`, `.g.i.cs`, `.generated.cs`), пропускаются. Это не «логические строки» и не число операторов: длинный метод с одной инструкцией на строке весит ровно столько строк, сколько занимает.

**Послойный LOC модуля** (`LayerLoc`) — четыре суммы `Loc` по типам модуля, сгруппированным по роли сборки: `contract`, `implementation`, `infrastructure`, `ui`. Типы сборок `host` и `test` не учитываются, типы сборок `shared` не входят ни в одну из четырёх колонок.

**`uiLoc`** и **`implementationLoc`** — две из этих четырёх сумм: строки типов в сборках с ролью `ui` и строки типов в сборках с ролью `implementation`. Колонка `infrastructure` в этом правиле не участвует.

## Когда срабатывает

Для каждого модуля графа модулей проверяется одно неравенство с защитой от деления смысла на ноль:

```text
uiLoc             = Σ Loc(type) по типам сборок модуля с ролью ui
implementationLoc = Σ Loc(type) по типам сборок модуля с ролью implementation

C3 срабатывает, если uiLoc > implementationLoc и implementationLoc > 0
```

Сравнение строгое: при равенстве строк находки нет. Условие `implementationLoc > 0` означает, что модуль, состоящий только из UI-сборки, или модуль, у которого вся не-UI логика лежит в сборке с ролью `infrastructure`, никогда не даёт C3 — сравнивать UI попросту не с чем. Инфраструктурные строки не прибавляются к реализации: модуль с `ui = 500`, `implementation = 100`, `infrastructure = 900` всё равно получает находку.

Считаются строки объявлений C#-типов, а не файлы: разметка Razor, XAML и прочие не-C#-файлы в LOC не входят; C#, сгенерированный из них в файлы с суффиксом `.g.cs`, тоже пропускается. В счёт идут написанные вручную типы — code-behind, view-model, обработчики.

## Пример

Юнит-тест `Ui_heavier_than_implementation_is_C3`: модуль `Home` из сборок `Home` (роль `implementation`) и `Home.Ui` (роль `ui`). Тип `H.Service` занимает `3` строки, тип `H.Page` — `10`. Послойный LOC модуля равен `LayerLoc(contract: 0, implementation: 3, infrastructure: 0, ui: 10)`, и так как `10 > 3` при `3 > 0`, выдаётся находка `ui outweighs implementation: Home`.

Юнит-тест `Ui_without_implementation_loc_is_not_C3`: модуль из одной сборки `Home.Ui` с тем же типом на `10` строк даёт `LayerLoc(0, 0, 0, 10)` и находки не даёт.

Тест `Layer_loc_sums_by_role_and_ignores_host_test` показывает, что попадает в таблицу: типы `App.Host::H.Program` и `M.Tests::T.Specs` по `99` строк каждый не добавляют ничего ни в одну колонку, а `M.Infra::M.Store` на `4` строки попадает в `infrastructure`, которую C3 не читает.

Как это выглядит в коде:

```csharp
// Home.UI — сборка с ролью ui
public sealed partial class OrdersPage           // Loc = 240: обработчики, маппинг, проверка правил
{
    private readonly IOrders _orders;             // Home.UI → Home.Contracts::IOrders, ребро fieldType
    // ... 200 строк ветвлений: скидки, валидация, форматирование
}

// Home — сборка с ролью implementation
internal sealed class OrdersService : IOrders     // Loc = 60
{
    // ... тонкая прослойка над репозиторием
}
// uiLoc = 240 > implementationLoc = 60 → C3 на Home
```

## Где смотреть в отчёте

- **Вкладка Findings** — строка `C3 | trigger | Home | | ui outweighs implementation: Home |`; колонки To и Evidence пусты.
- **Вкладка Metrics, таблица Layer LOC** — колонки `contract | implementation | infrastructure | ui` по каждому модулю; правило сравнивает вторую и четвёртую. Таблица не выводится, если ни у одного модуля нет типов с этими ролями.
- **Вкладка Metrics, таблица Modules** — колонка LOC показывает сумму по всем ролям модуля и для C3 напрямую не подходит.
- **`metrics.json`** — `layerLoc.{module}.ui` и `layerLoc.{module}.implementation`.
- **`gate-report.json`** — та же находка при `arch-lens gate`, если отпечатка нет в `knownFindings`.

## Как исправить

Смысл правила — представления должны оставаться адаптерами, а правила поведения жить в реализации, где их можно тестировать через контракт.

1. Найдите в UI-сборке типы с наибольшим `Loc` (в `graph.json` у каждого типа есть поле `loc`) и выделите в них то, что не относится к отображению: оркестрацию сценариев, маппинг DTO, проверку бизнес-правил, работу с хранилищем.
2. Перенесите эту логику в сборку с ролью `implementation` того же модуля — как сервисы сценариев за интерфейсами контракта. Тогда UI будет зависеть от `Home.Contracts`, а не от внутренностей.
3. Если UI-сборка обращается к реализациям чужих модулей, вы увидите рядом находки [A1](A1.md); их исправление обычно и есть перенос логики.
4. Повторите `arch-lens map` и сверьте колонки `implementation` и `ui` в таблице Layer LOC.

**Когда допустимо принять.** Модуль, который по замыслу почти целиком состоит из представлений (дизайн-система, тонкая витрина над контрактами других модулей), будет объёмнее в UI, чем в реализации, и это нормально. Зафиксируйте находку командой `arch-lens baseline`: её отпечаток попадёт в `knownFindings`, а таблица Layer LOC продолжит показывать пропорцию для ревью.

## Чего не делать

- Не переносите типы представлений и view-model в сборку реализации только ради колонки: они останутся UI по смыслу, а реализация начнёт зависеть от UI-каркаса.
- Не переназначайте в `arch-lens.yaml` роль настоящей UI-сборки на `implementation` и не переименовывайте `Home.UI` в `Home.Presentation`, чтобы конвенция перестала её узнавать: правило замолчит, а пропорция не изменится.
- Не удаляйте и не «обнуляйте» реализацию: условие `implementationLoc > 0` заглушит правило, но модуль станет только хуже.
- Не набивайте реализацию пустыми строками и комментариями, чтобы догнать UI: LOC считает их, ревьюер — тоже.
