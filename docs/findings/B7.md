# B7 — Fan-in / fan-out outlier

| Field | Value |
|---|---|
| Code | `B7` |
| Class | `trigger` |
| Analyzer | `SizeBalanceAnalyzer` |
| Commands | `map` and `gate` (unless `knownFindings`) |

## When it fires

`N = ModuleGraph.Modules.Count` must be **≥ 4**. Then either:

- **God row:** `fanOut >= N - 1` (depends on almost every module), or
- **Magnet:** `fanIn >= N - 1` **and** the module is **not** `shared` **and** it has **no contract assembly**.

Shared hubs and modules that expose a contract are allowed to have high fan-in.

Fingerprint: `ForTypeEdge("B7", moduleId, "", [])`. Message: `fan-in/out outlier: {module}`.

## Example

Five scored modules. `Orchestrator` implementation references the other four → fanOut 4 ≥ 4 → B7. A `SharedKernel` with fanIn 4 does **not** magnet-fire. An `Account` module with a Contracts assembly and fanIn 4 does **not** magnet-fire.

## How to fix

1. Stop depending on everyone's **implementation**; depend on contracts.
2. If everything depends on your implementation, **publish a contract** and make the body internal.
3. Split a true god orchestrator into use-case modules.

## What not to do

- Do **not** add a dummy `X.Contracts` project with no types to dodge the magnet clause if the public surface is still the implementation (you'll still have [A3](A3.md)/[C2](C2.md) problems).
- Do **not** declare the module `shared` in YAML to dodge magnet — shared gravity ([B9](B9.md)) will catch a junk kernel.

See also [fanInOut](../metrics/fanInOut.md), [B9](B9.md), [P1](P1.md).
