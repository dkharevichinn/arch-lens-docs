# B7 — Модуль-выброс по fan-in или fan-out: зависит от всех или нужен всем

| Поле | Значение |
|---|---|
| Код | `B7` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet`; сама по себе находка не блокирует |
| Кто выдаёт | `SizeBalanceAnalyzer.Analyze`, вызывается из `StaticMetricsCalculator.Calculate`; `GateEvaluator` эту находку не синтезирует |
| Команды | `map` — находка снимка, попадает в `findings.json` и на вкладку Findings; `gate` — проходит в `gate-report.json`, если её отпечатка нет в `knownFindings` |
| Метрика | [`fanInOut`](../metrics/fanInOut.md) — колонки **Fan-in** и **Fan-out** таблицы Modules на вкладке Metrics |
| Пороги | `N >= 4`; `fanOut >= N − 1`; либо `fanIn >= N − 1` у модуля без роли `shared` и без контрактной сборки; все три условия — константы в коде, в YAML не настраиваются |
| Отпечаток | `ForTypeEdge("B7", module, "", [])`; `FromModule` — модуль, `ToModule` пуст, `Evidence` пуст |
| Сообщение | `fan-in/out outlier: {module}` — одно и то же для обеих ветвей условия |

## Термины

Базовые понятия — [граф модулей](../glossary.md#module-graph), [fan-in и fan-out](../glossary.md#fan), [учитываемый модуль](../glossary.md#scored) и [роли сборок](../glossary.md#module) — определены в словаре.

**Fan-out** модуля — число **различных** модулей, в которые у него есть хотя бы одно ребро; **fan-in** — число различных модулей, у которых есть ребро в него. Это счётчики соседей, а не суммы весов: одно упоминание типа и тысяча упоминаний добавляют по единице. Считаются только учитываемые модули: ссылки из `host` и из тестов fan-in не увеличивают.

**`N`** — число модулей графа (`graph.Modules.Count`): учитываемые модули, у которых есть хотя бы один тип. Максимально возможное значение fan-in и fan-out равно `N − 1`, поэтому условия правила означают буквально «связан со **всеми** остальными модулями».

**Модуль-«бог»** (god row, «строка-бог» матрицы) — модуль с `fanOut >= N − 1`: он зависит от каждого другого модуля. Обычно это оркестратор или «модуль приложения», который знает обо всём.

**Магнит** — модуль с `fanIn >= N − 1`, от которого зависят все остальные, при двух дополнительных условиях: ни одна из его сборок не имеет роли `shared`, и в модуле нет сборки с ролью `contract`. Первое исключение очевидно: общее ядро и должно быть нужно всем. Второе означает, что у модуля есть официальная граница, через которую к нему приходят зависимые (а [A1](A1.md) и [A2](A2.md) следят, чтобы приходили именно через неё); магнитом правило называет модуль, к телу которого все обращаются напрямую. Признак «есть контрактная сборка» берётся из каталога сборок (`snapshot.Modules.Bindings`), а не из числа типов: контрактная сборка без единого типа формально тоже считается.

## Когда срабатывает

```text
N = число модулей графа
B7(m) ⇔ N >= 4 и ( fanOut(m) >= N − 1
                   или ( fanIn(m) >= N − 1 и у m нет сборки с ролью shared и нет сборки с ролью contract ) )
```

Правило проверяется для каждого модуля, поэтому в одном снимке может быть несколько находок B7 — по одной на модуль. Если у модуля выполнены обе ветви сразу, находка всё равно одна: отпечаток и сообщение от ветви не зависят. При `N < 4` правило не срабатывает никогда: в решении из трёх модулей любой из них может быть связан с двумя другими без подозрений.

Понять, какая ветвь сработала, по сообщению нельзя: нужно открыть таблицу Modules и сравнить Fan-in и Fan-out с `N − 1`.

Находка снимка проходит через фильтр `knownFindings` гейта; отпечаток зависит только от идентификатора модуля, поэтому принятая находка остаётся принятой, пока модуль существует, а появление нового модуля-выброса даёт новый отпечаток.

### Чем B7 отличается от соседей

| Правило | Что измеряет | Отличие от B7 |
|---|---|---|
| **B7** | число прямых соседей модуля против `N − 1` | — |
| [P1](P1.md) | доля **веса** исходящих рёбер, приходящаяся на один модуль (не меньше 70 % при весе не меньше 5) | P1 работает с весами, B7 — со счётчиками соседей |
| [P3](P3.md) | `fanIn = 0` и `fanOut = 0` при наличии типов | противоположный полюс той же таблицы |
| [B8](B8.md) с тегом `pain` | `Ca >= 2`, низкие `I` и `A`, нет контракта | B8 срабатывает уже от двух зависимых и учитывает абстрактность; магнит B7 требует всех `N − 1` |
| [B9](B9.md) | доля межмодульного веса, направленного в `shared` | B9 следит за тем самым `shared`, который B7 освобождает от проверки на магнит |

## Пример

Юнит-тест `Fan_out_to_all_other_modules_is_B7`: четыре модуля реализации, `God` ссылается на `A`, `B` и `C`. `N = 4`, `fanOut(God) = 3 >= 3` — находка класса `trigger` с `FromModule = God`, отпечатком `ForTypeEdge("B7", "God", "", [])` и сообщением `fan-in/out outlier: God`; для `A`, `B`, `C` находок нет (у каждого `fanIn = 1`). Тест `Three_modules_cannot_be_B7`: те же связи, но модулей три — правило молчит.

Тест `Impl_hub_without_contract_is_magnet_B7`: `A`, `B`, `C` ссылаются на модуль реализации `Hub`, у которого нет контрактной сборки. `fanIn(Hub) = 3 >= 3` — находка `fan-in/out outlier: Hub`. Тест `Shared_with_fan_in_and_contract_is_not_magnet_B7`: тот же рисунок связей, но модуль `Kernel` состоит из сборки `Kernel` с ролью `shared` и `Kernel.Contracts` с ролью `contract` — находки нет, хотя `fanIn = 3`; каждого из двух признаков достаточно по отдельности.

Пример ближе к практике: пять учитываемых модулей. `Orchestrator` ссылается на контракты четырёх остальных — `fanOut = 4 >= 4`, B7. `SharedKernel` с `fanIn = 4` магнитом не считается из-за роли `shared`. Модуль `Account` из сборок `Account` и `Account.Contracts` с `fanIn = 4` магнитом не считается из-за контрактной сборки. Модуль `Helpers` из одной сборки реализации с `fanIn = 4` — магнит.

## Где смотреть в отчёте

- **Вкладка Findings** — строка `B7 | trigger | Orchestrator | | fan-in/out outlier: Orchestrator | ` с заполненной колонкой From и пустыми To и Evidence. Та же запись — в `findings.json`.
- **Вкладка Metrics, таблица Modules** — колонки Fan-in и Fan-out для каждого модуля; число строк таблицы — это `N`. Те же числа лежат в `metrics.json` под ключом `fanInOut` (`{ "fanIn": …, "fanOut": … }`) и повторяются в таблице Martin как `afferent` и `efferent`.
- **Вкладка Metrics, заголовки модулей** — под таблицей Contracts для каждого модуля перечислены его сборки с ролями; здесь видно, есть ли у модуля сборка `contract` или `shared`.
- **`gate-report.json`** — тот же объект с `"class": "trigger"`, если отпечатка нет в `knownFindings`.
- **Вкладка Matrix** показывает связи между компонентами из `rules`, а не между модулями, поэтому полностью заполненная строка или колонка матрицы — подсказка, а не критерий; см. [отличие DSM от графа модулей](../glossary.md#dsm-vs-modules).

## Как исправить

1. Определите ветвь по таблице Modules: `Fan-out = N − 1` — модуль-«бог», `Fan-in = N − 1` — магнит.
2. Для модуля-«бога» уменьшайте число модулей, о которых он знает, а не способ обращения к ним: замена ссылок на реализацию ссылками на контракты того же модуля fan-out **не** меняет, потому что контрактная сборка принадлежит тому же модулю. Работают разделение оркестратора на модули по сценариям, обмен событиями через типы в `shared` (издатель зависит только от `shared`) и порты, которыми владеет оркестратор, а реализуют функциональные модули.
3. Для магнита опубликуйте настоящую границу: сборку `X.Contracts` с портами и DTO, через которую пойдут все внешние обращения, а тело сделайте `internal`. После этого ветвь «магнит» отключается, а [A1](A1.md) и [A2](A2.md) начинают охранять границу. Если модуль по смыслу — общее ядро (примитивы, идентификаторы, время), объявите его `shared` в YAML и следите за ним через [B9](B9.md).
4. Если модуль-«бог» — настоящий корень композиции (регистрация DI, точка входа), дайте ему роль `host` в YAML: такие сборки в граф модулей не входят. Это честно только для корня композиции.
5. Проверьте результат командой `arch-lens map`: строка должна исчезнуть с вкладки Findings.

**Когда допустимо принять.** Единственный «модуль приложения», который по замыслу оркестрирует все функциональные модули и не является корнем композиции, можно принять командой `arch-lens baseline`: отпечаток попадёт в `knownFindings`, и находка замолчит для этого модуля, а любой новый модуль-выброс всё равно всплывёт. Зафиксируйте решение в описании коммита.

## Чего не делать

- Не создавайте пустую сборку `X.Contracts` ради отключения ветви «магнит»: правило формально замолчит, но публичные типы тела продолжит считать [A3](A3.md), а каждое обращение к телу извне — отмечать [A1](A1.md).
- Не объявляйте модуль `shared` в YAML, если он не общее ядро: вес рёбер в него начнёт считать [B9](B9.md), а число его типов покажет чип `shared types`.
- Не ждите, что переход на контракты уменьшит fan-out модуля-«бога»: граф модулей не различает сборки внутри модуля.
- Не дробите и не сливайте модули в YAML только ради изменения `N`: порог `N − 1` сдвинется для всех модулей сразу, а система не изменится.
- Не давайте роль `host` функциональному модулю, чтобы он пропал из графа: вместе с ним из всех метрик семейства B пропадут и его зависимости.
