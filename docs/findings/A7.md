# A7 — InternalsVisibleTo (or friend import) to a non-test assembly

| Field | Value |
|---|---|
| Code | `A7` |
| Class | `invariant` → **[block](../gates/block.md)** |
| Analyzer | `InternalsVisibleToAnalyzer` |
| Commands | `map` and `gate` (unless `knownFindings`) |

## When it fires

Each `ModuleCatalog.Friends` entry (from `[InternalsVisibleTo]` or Swift `@testable import`) whose **friend assembly is in the snapshot** and whose friend role is **not** `test`.

Friends that are **not** among mapped assemblies (e.g. `DynamicProxyGenAssembly2`) are skipped.

**Host as friend is a violation** (“outside tests”).

Message is phrased by mechanism: `InternalsVisibleTo {assembly} -> {friend}` or `@testable import {assembly} -> {friend}`.

Fingerprint: `ForTypeEdge("A7", assemblyName, friendName, [])`.

## Example

```csharp
// Account/AssemblyInfo.cs or csproj
[assembly: InternalsVisibleTo("Account.Infrastructure")] // A7 if Infrastructure is not role test
[assembly: InternalsVisibleTo("Account.Tests")]          // legal
```

```xml
<ItemGroup>
  <InternalsVisibleTo Include="ArchLens.Tests" /> <!-- legal when that assembly is role test -->
</ItemGroup>
```

## How to fix

1. Keep `internal` types visible **only to test assemblies** (`X.Tests`, `X.UnitTests`, `X.IntegrationTests`, or YAML `role: test`).
2. If two product assemblies need to share types, they should share a **contract or shared** type, not `internal` across the boundary.
3. For the tool's own dogfood, `InternalsVisibleTo Include="ArchLens.Tests"` on implementation projects is the supported pattern.

## What not to do

- Do **not** friend a sibling implementation to “fix” [A1](A1.md). You traded a bypass for a secret API.
- Do **not** friend the host so the host can poke internals — host should use public contracts / MEDI.
- Do **not** drop the friend assembly from the solution so A7 skips it; the coupling remains, the catalog just goes blind.

See also [A1](A1.md), [A3](A3.md).
