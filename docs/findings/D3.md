# D3 — Тип по своим связям принадлежит сообществу другого модуля

| Поле | Значение |
|---|---|
| Код | `D3` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `CommunityAnalyzer.Analyze`, вызывается из `StaticMetricsCalculator.Calculate`; распространение меток по неориентированному графу всех учитываемых типов |
| Команды | `arch-lens map` (находка снимка: `findings.json`, вкладка Findings) и `arch-lens gate` (проходит в `gate-report.json`, если отпечатка нет в `knownFindings`) |
| Порог | учитываются кластеры из `>= 4` типов; распространение — не более `50` проходов; не более `20` находок за снимок; константы `MinCluster`, `MaxIterations`, `Cap` зашиты в коде |
| Отпечаток | `ForTypeEdge("D3", typeId, majorityModule, [])` — один на пару «тип, модуль большинства» |
| Сообщение | `cluster pulls toward {majorityModule}`; `FromModule` — модуль, в котором тип лежит сейчас, `ToModule` — модуль большинства; идентификатор типа в сообщении **не печатается** |

## Термины

Понятия [учитываемый модуль](../glossary.md#scored), [идентификатор типа](../glossary.md#type-id), [ребро между типами](../glossary.md#edge-kinds) и [ordinal-порядок](../glossary.md#ordinal) определены в словаре.

**Граф соседства типов** — неориентированный граф, узлы которого — все учитываемые типы решения (из всех модулей сразу), а связь между двумя типами есть, если между ними существует хотя бы одно ребро любого вида в любом направлении. Вес и число видов не важны: соседство либо есть, либо нет. Рёбра внутри модуля и рёбра между модулями входят на равных. Типы сборок `host` и `test` в графе отсутствуют.

**Распространение меток** (label propagation) — способ найти в графе сообщества, то есть группы узлов, которые связаны между собой гуще, чем с остальными. Каждому типу выдают метку — сначала его собственный идентификатор. Затем типы по очереди смотрят на метки своих соседей и берут ту, что встречается чаще всего. Метки «побеждают» по соседству: плотно связанная группа быстро сходится к одной общей метке, а редкие связи наружу не в силах её перетянуть. Процесс повторяют, пока за целый проход ни одна метка не изменилась.

**Кластер** (сообщество) — множество типов, у которых после остановки алгоритма одна и та же метка. **Модуль большинства** кластера — модуль, которому принадлежит больше всего его типов. **Смещённый тип** — член кластера, чей модуль не совпадает с модулем большинства.

## Когда срабатывает

Алгоритм в `CommunityAnalyzer.Analyze` работает так. Строится граф соседства по всем учитываемым типам, типы сортируются по идентификатору в ordinal-порядке, и каждому присваивается метка, равная его идентификатору. Затем выполняется до `50` проходов: типы обходятся в том же порядке, тип без соседей пропускается и навсегда остаётся со своей меткой, а для остальных выбирается самая частая метка среди соседей (при равенстве — меньшая по ordinal). Новая метка записывается **сразу**, и следующие типы того же прохода уже видят её; проход без изменений завершает алгоритм. После этого типы группируются по метке, кластеры меньше `4` типов отбрасываются, для остальных определяется модуль большинства, и каждый член кластера из другого модуля становится находкой. Находки сортируются по идентификатору типа, затем по модулю большинства, и берутся первые `20`.

```text
neighbors(t)   = типы, связанные с t хотя бы одним ребром в любую сторону
label(t)       = самая частая метка среди neighbors(t); ничья разрешается по ordinal
cluster(L)     = { t : label(t) == L } после сходимости или 50 проходов
majority(C)    = модуль с наибольшим числом типов в C; ничья разрешается по ordinal

D3 для типа t из кластера C, если |C| >= 4 и module(t) != majority(C); не более 20 находок
```

Обратите внимание на то, чего в правиле нет. Веса рёбер не учитываются: сто вызовов и один параметр — одно и то же соседство. Ограничение в `20` находок применяется после сортировки по имени типа, а не по значимости: при большом числе смещённых типов отсекаются те, чьи идентификаторы стоят дальше по алфавиту. Отпечаток и `FromModule`/`ToModule` различают находки, но само сообщение содержит только модуль большинства.

## Пример

Юнит-тест `Misplaced_type_in_foreign_majority_cluster_is_D3`: четыре типа `Account::Account.A0`, `Account::Account.A1`, `Account::Account.A2` и `Gameplay::Gameplay.Foreign` попарно связаны рёбрами (клика). Проход первый, в ordinal-порядке: у `A0` соседи `A1`, `A2`, `Foreign` носят три разные метки по одному разу — ничья, побеждает наименьшая `Account::Account.A1`; у `A1` то же самое, метка остаётся `A1`; у `A2` соседи `A0` и `A1` уже носят метку `A1` — большинство, `A2` берёт `A1`; у `Foreign` все три соседа с меткой `A1`. Второй проход ничего не меняет. Кластер из четырёх типов, модуль большинства — `Account` (три типа против одного), смещённый тип — `Gameplay::Gameplay.Foreign`. Находка: `FromModule = Gameplay`, `ToModule = Account`, сообщение `cluster pulls toward Account`, отпечаток `ForTypeEdge("D3", "Gameplay::Gameplay.Foreign", "Account", [])`.

Тест `Cluster_of_three_is_not_D3`: та же картина с тремя типами не даёт ничего — кластер меньше четырёх. Тест `More_than_twenty_misplaced_types_are_capped_at_twenty`: двадцать одна клика по четыре типа, в каждой один чужой, дают ровно двадцать находок; отсечён тип `Gameplay::Gameplay.M20`, последний по ordinal.

Как это выглядит в коде:

```csharp
// сборка Catalog (модуль Catalog)
internal sealed class PriceRounding                      // все связи — в модуль Billing
{
    public Money Round(Invoice invoice, TaxTable taxes)  // parameter → Billing::Invoice, Billing::TaxTable
        => Money.Of(taxes.Apply(invoice.Total));         // call → Billing::TaxTable, return/call → Billing::Money
}
// Billing::Invoice, Billing::TaxTable, Billing::Money связаны между собой и сходятся к одной метке;
// PriceRounding перенимает её (все три соседа — из Billing) и попадает в кластер из четырёх и более типов,
// где большинство — Billing → D3: From = Catalog, To = Billing, «cluster pulls toward Billing»
```

## Где смотреть в отчёте

- **Вкладка Findings** — строка `D3 | trigger | Catalog | Billing | cluster pulls toward Billing |`; колонка Evidence пуста. Несколько смещённых типов одного модуля, тянущихся к одному соседу, дают одинаковые на вид строки, различимые только отпечатком в `findings.json`.
- **Какой именно тип** — в отчёте не показывается. Чтобы его найти, возьмите в `graph.json` типы модуля `From`, у которых рёбра ведут в основном в типы модуля `To`; часто на них же указывают свидетельства [A1](A1.md)/[A2](A2.md) или находка [P1](P1.md) для всего модуля.
- **`gate-report.json`** — та же находка при `arch-lens gate`, если отпечатка нет в `knownFindings`.

## Как исправить

1. Установите тип по описанному выше способу и посмотрите, чем он занимается. Если он работает исключительно с данными и сервисами модуля `To`, он принадлежит этому модулю: перенесите его туда (в тело или, если это абстракция, в контракт). Идентификатор типа изменится, и находка исчезнет вместе с отпечатком.
2. Если тип должен остаться на месте, сократите его связи с чужим модулем: обращайтесь к контракту `To.Contracts`, а не к внутренним типам, и передавайте данные в виде DTO контракта. Когда соседей из `To` станет меньше, чем соседей из своего модуля, метка перестанет перетягиваться.
3. Если смещённых типов несколько и они связаны между собой, перед вами, возможно, целая подфича, живущая не в том модуле, — проверьте [D2](D2.md) и [P1](P1.md) для модуля `From` и переносите группу целиком.
4. Повторите `arch-lens map`; убедитесь, что перенос не породил [A1](A1.md) и не изменил [B1](B1.md).

**Когда допустимо принять.** Адаптеры и антикоррупционные слои по замыслу разговаривают почти только с чужим модулем: тип `BillingGateway` в `Catalog`, который переводит понятия `Billing` в понятия каталога, будет тянуться к `Billing`, и это правильно. Зафиксируйте находку командой `arch-lens baseline`; отпечаток привязан к типу и модулю большинства, поэтому принятие точечное.

## Чего не делать

- Не переименовывайте типы, чтобы изменить ordinal-порядок и вытеснить находку за ограничение в `20` строк или переиграть ничью: алгоритм детерминирован, и следующий запуск покажет ту же картину под другими именами.
- Не считайте, что смещённых типов ровно столько, сколько строк: `20` — верхняя граница вывода. Исправьте показанные и запустите `map` снова.
- Не увеличивайте веса связей со своим модулем лишними вызовами: соседство считается без весов, и это ничего не изменит.
- Не переносите тип механически, если в новом модуле он станет зависеть от контракта прежнего: так рождаются циклы [B1](B1.md).
