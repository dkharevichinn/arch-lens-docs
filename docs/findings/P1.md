# P1 — Feature envy

| Field | Value |
|---|---|
| Code | `P1` |
| Class | `trigger` |
| Analyzer | `SizeBalanceAnalyzer` |
| Commands | `map` and `gate` (unless `knownFindings`) |

## When it fires

On `ModuleGraph` for a source module with total outgoing inter-module weight `W ≥ 5`, if the heaviest cell `max_cell / W ≥ 0.7`, envy toward that target. Ties on weight pick the Ordinal-min target.

Fingerprint: `ForTypeEdge("P1", fromModule, toModule, [])`. Message: `feature envy: {from} -> {to}`.

A 2-cycle is [B1](B1.md), not P1. There is **no P2** rule.

## Example

`Home` has outgoing weight 10, of which 8 goes to `Account` and 2 to `SharedKernel`. 8/10 ≥ 0.7 and W ≥ 5 → P1 Home→Account. Home probably belongs with Account or should depend on a slimmer `Account.Contracts` surface.

## How to fix

Move the envious types into the envied module, or shrink the coupling to a small contract. If Home is only a UI over Account, consider whether Home should be Account.UI (same module id).

## What not to do

- Do **not** add junk edges to a third module to drop the ratio below 70%.
- Do **not** split one heavy edge into many kinds — weights still sum in the cell.

See also [fanInOut](../metrics/fanInOut.md), [D3](D3.md), [B7](B7.md).
