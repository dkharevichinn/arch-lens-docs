# P1 — Feature envy: почти весь исходящий вес модуля уходит в одного соседа

| Поле | Значение |
|---|---|
| Код | `P1` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `SizeBalanceAnalyzer.TryP1`, вызывается из `StaticMetricsCalculator.Calculate`; читает рёбра [графа модулей](../glossary.md#module-graph) `ModuleGraph.InterEdges` |
| Команды | `arch-lens map` (находка снимка: `findings.json`, вкладка Findings) и `arch-lens gate` (проходит в `gate-report.json`, если отпечатка нет в `knownFindings`) |
| Метрика | прямой метрики нет; ближайшие — [fanInOut](../metrics/fanInOut.md) (число соседей) и веса рёбер в `graph.json` |
| Порог | суммарный исходящий вес `W >= 5` и доля самой тяжёлой клетки `maxCell / W >= 0.7`; константы зашиты в коде |
| Отпечаток | `ForTypeEdge("P1", fromModule, toModule, [])` — один на пару модулей |
| Сообщение | `feature envy: {from} -> {to}` |

## Термины

Понятия [граф модулей](../glossary.md#module-graph), [вес ребра](../glossary.md#weight), [fan-out](../glossary.md#fan) и [ordinal-порядок](../glossary.md#ordinal) определены в словаре.

**Клетка** (`cell`) — ребро графа модулей `from → to` со своим весом: сумма весов всех рёбер между типами модуля `from` и типами модуля `to`, всех видов вместе. Слово взято из матрицы зависимостей, но речь о графе модулей: модуль-цель считается целиком, независимо от того, в его контракт или в его реализацию ведут рёбра.

**Исходящий вес модуля** (`W`) — сумма весов всех клеток, у которых `from` — этот модуль. Рёбра внутри модуля и рёбра в сборки `host` и `test` в граф модулей не входят и в `W` не считаются.

**Самая тяжёлая клетка** (`maxCell`) — клетка модуля с наибольшим весом; модуль на её другом конце в коде называется `envied`, «предмет зависти». При равенстве весов выбирается модуль с меньшим ordinal-именем.

**Feature envy** (зависть к чужому модулю) — ситуация, когда типы модуля заняты преимущественно данными и операциями другого модуля: код формально лежит в одном месте, а по смыслу принадлежит другому.

## Когда срабатывает

```text
W       = Σ вес(from → x) по всем клеткам графа модулей, где from == module
maxCell = max вес(from → x); ничья разрешается по ordinal-имени x

P1 для module в сторону envied, если W >= 5 и maxCell / W >= 0.7
```

Сравнения нестрогие: `7` из `10` (`0.7`) срабатывает, `6` из `10` — нет. Порог `5` — абсолютный минимум массы: модуль с двумя упоминаниями соседа не может быть «завистником», сколько бы процентов эти два упоминания ни составляли. Доля `0.7` — граница, начиная с которой связи считаются направленными в одну сторону. Обе константы общие с [C4](C4.md) и в `arch-lens.yaml` не выносятся.

Из формулы вытекают следствия, которые стоит знать до того, как удивляться таблице Findings.

- Модуль с **единственным** соседом по исходящим рёбрам при `W >= 5` срабатывает всегда: его доля равна `1`. Это касается и модуля, который зависит только от `Account.Contracts`, и модуля, который зависит только от `shared`: цель в `shared` не исключается.
- Цель считается на уровне модуля: пять упоминаний контракта и пять упоминаний реализации одного соседа — одна клетка веса `10`.
- Участники цикла из правила не исключаются: пара модулей может одновременно дать [B1](B1.md) и две находки P1 в обе стороны.
- Правила P2 не существует: коды семейства P — это P1 и [P3](P3.md).

## Пример

Юнит-тест `Heavy_single_cell_is_P1_feature_envy`: модуль `A` ссылается на `B` с весом `7` и на `C` с весом `3`. `W = 10`, `maxCell = 7`, `7 / 10 = 0.7 >= 0.7`, находка `feature envy: A -> B` с `FromModule = A`, `ToModule = B` и отпечатком `ForTypeEdge("P1", "A", "B", [])`. Тест `Balanced_outgoing_weight_is_not_P1`: веса `6` и `4` дают долю `0.6` — тишина.

Пример из практики: модуль `Home` имеет исходящий вес `10`, из которых `8` уходит в `Account` и `2` — в `SharedKernel`. Доля `0.8` и `W = 10` дают `feature envy: Home -> Account`. Скорее всего, `Home` — это либо часть `Account`, либо код, которому нужен более узкий контракт `Account.Contracts`.

Как это выглядит в коде:

```csharp
// сборка Home (модуль Home)
internal sealed class DashboardBuilder
{
    private readonly IAccounts _accounts;                        // Home → Account: fieldType 1
    public Dashboard Build(AccountId id)                         // Home → Account: parameter 1
    {
        var profile = _accounts.Profile(id);                     // Home → Account: call 1
        var limits  = _accounts.Limits(id);                      // Home → Account: call 1
        var badges  = _accounts.Badges(id);                      // Home → Account: call 1
        return new Dashboard(profile, limits, badges, Clock.UtcNow()); // Home → SharedKernel: call 1; new Dashboard — внутри Home, в граф не входит
    }
}
// W = 6, maxCell(Home → Account) = 5, 5 / 6 ≈ 0.83 → P1 «feature envy: Home -> Account»
```

Все типы `IAccounts`, `AccountId` лежат в `Account.Contracts`, то есть путь легальный с точки зрения [A1](A1.md); P1 говорит не о запретности рёбер, а об их сосредоточенности.

## Где смотреть в отчёте

- **Вкладка Findings** — строка `P1 | trigger | Home | Account | feature envy: Home -> Account |`; здесь, в отличие от большинства правил семейств C и D, заполнена колонка To. Колонка Evidence пуста.
- **Вкладка Metrics, таблица Modules** — колонка Fan-out показывает **число** модулей-целей, а не веса. Fan-out, равный `1`, при заметном числе типов почти гарантирует P1.
- **`graph.json`** — веса по типам; сгруппировав рёбра по модулям источника и цели, вы получите клетки `W` и `maxCell`.
- **Вкладка Matrix** показывает похожую картину по компонентам из `rules`, но разбиение другое (см. [отличие DSM от графа модулей](../glossary.md#dsm-vs-modules)); тяжёлая клетка в строке компонента — подсказка, не доказательство.
- **`gate-report.json`** — та же находка при `arch-lens gate`, если отпечатка нет в `knownFindings`.

## Как исправить

1. Разберитесь, чем занят модуль-источник. Если его типы в основном вызывают операции соседа и складывают его данные, перенесите их в модуль-цель: пусть `Home` станет частью `Account` или его UI-сборкой `Account.UI` с тем же идентификатором модуля — тогда рёбра станут внутренними и уйдут из графа модулей.
2. Если модуль самостоятелен, но ему нужен сосед, сузьте связь: попросите у соседа один порт или одно DTO в контракте вместо десятка обращений, соберите данные один раз, а не в каждом методе.
3. Если исходящий вес честно распределён по нескольким соседям, а срабатывание вызвано единственной зависимостью маленького модуля, задайте вопрос о самостоятельности такого модуля: тонкая обёртка над одним соседом — это либо его адаптер, либо лишняя граница.
4. Повторите `arch-lens map` и убедитесь, что перенос не породил [A1](A1.md), [B1](B1.md) или новую P1 в обратную сторону.

**Когда допустимо принять.** Адаптеры, API-шлюзы (gateway) и фасады по замыслу целиком обращены к одному модулю: `Billing.Api`, который переводит HTTP в вызовы `Billing.Contracts`, или антикоррупционный слой над унаследованной подсистемой всегда будут «завистниками». Зафиксируйте находку командой `arch-lens baseline`: отпечаток привязан к паре модулей и не меняется от роста веса.

## Чего не делать

- Не добавляйте рёбра в третий модуль, чтобы разбавить долю: зависимость станет шире, зависть — не меньше.
- Не пытайтесь «раскидать» одну тяжёлую связь по видам рёбер (вызовы, параметры, поля): веса всех видов складываются в одну клетку.
- Не заворачивайте обращения к соседу через `host` или через `shared`-«помощник»: первое — обход, который заметят [A1](A1.md)/[A2](A2.md), второе — рост [sharedGravity](../metrics/sharedGravity.md) и [B9](B9.md).
- Не путайте P1 с [D3](D3.md): D3 говорит об отдельном типе по числу соседей без весов, P1 — о модуле целиком по весам.

См. также [fanInOut](../metrics/fanInOut.md), [D3](D3.md), [B7](B7.md), [P3](P3.md), [C4](C4.md).
