# E4 — Дублирующееся понятие: публичные типы разных модулей с одинаковыми или почти одинаковыми именами

| Поле | Значение |
|---|---|
| Код | `E4` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `DuplicateConceptAnalyzer.Analyze`, вызывается из `StaticMetricsCalculator.Calculate` |
| Команды | `map` (находка снимка: `findings.json`, вкладка Findings), `baseline` (отпечаток попадает в `knownFindings`), `gate` (находка проходит фильтр `knownFindings`) |
| Пороги | совпадение имён без учёта регистра при любой длине; иначе оба имени длиной не меньше `8` (`FuzzyMinLength`) и расстояние Левенштейна не больше `2` (`FuzzyMaxDistance`); константы зашиты в коде |
| Кап | не больше 20 пар на снимок (`Cap = 20`): по возрастанию расстояния, затем по ordinal идентификаторов `A` и `B` |
| Отпечаток | `ForTypeEdge("E4", A, B, [])`, где `A <= B` по ordinal — пара упорядочена, поэтому отпечаток не зависит от порядка обхода |
| Сообщение | `duplicate concept: {A} ~ {B}` |

## Термины

Базовые понятия — [идентификатор типа](../glossary.md#type-id), [публичность](../glossary.md#public), [учитываемый модуль](../glossary.md#scored), [ordinal-порядок](../glossary.md#ordinal) — определены в словаре. Для E4 нужны ещё три.

**Короткое имя** типа — часть идентификатора после последнего символа `.`. Для `Account.Contracts::Account.Contracts.Address` это `Address`; для вложенного типа `Orders::Orders.Report.Row` — `Row`, потому что вложенные типы записываются через точку. Обобщённые типы хранятся по открытому определению вместе с параметрами типа (`Widget<T>`), и параметры входят в короткое имя; суффикс арности в стиле метаданных вида `` `1 ``, если он встречается в снимке, отбрасывается (тест `Arity_suffix_is_stripped_before_name_compare`).

**Расстояние Левенштейна** — минимальное число вставок, удалений и замен одного символа, превращающих одну строку в другую. Перестановка двух соседних символов стоит две операции (замена и замена). Расстояние считается после приведения обоих имён к верхнему регистру, поэтому `OrderProcessor` и `orderprocessor` дают `0`, а `Processor` и `Processer` — `1`.

**Пара разных модулей.** Сравниваются типы из разных **модулей**, а не разных сборок: `Account.Contracts` и `Account` принадлежат одному модулю `Account`, и одноимённые типы внутри него правило не трогает. Сравниваются только публичные типы, потому что `internal` тип — деталь реализации, которая для соседних модулей не существует и понятием предметной области наружу не является.

## Когда срабатывает

```text
rows = публичные типы учитываемых модулей: (Id, Module, ShortName)
для каждой пары (L, R), L.Module ≠ R.Module:
  match ⇔ Equals(L.Name, R.Name, OrdinalIgnoreCase)                   → distance = 0
        ∨ (|L.Name| >= 8 ∧ |R.Name| >= 8
           ∧ Levenshtein(Upper(L.Name), Upper(R.Name)) <= 2)           → distance ∈ {1, 2}
  (A, B) = пара, упорядоченная по ordinal идентификаторов
пары сортируются по distance, затем A, затем B; берутся первые 20
```

Точное совпадение ловится при любой длине: `Id`, `Row`, `Options`. Приблизительное — только у имён из восьми и более символов, чтобы короткие слова, отличающиеся на одну-две буквы (`User` и `Users`, `Foo` и `Fob`), не считались опечатками. Поля находки: `FromModule` — модуль типа `A`, `ToModule` — модуль типа `B`, `Evidence` пуст.

**Что означает кап 20.** Пары с расстоянием `0` идут первыми, поэтому при большом числе точных совпадений приблизительные вообще не попадут в отчёт, пока точные не будут разобраны. Двадцать строк E4 — это «не меньше двадцати», а `baseline` фиксирует отпечатки только видимых пар.

Смысл правила: одно имя в двух модулях означает либо одно понятие, скопированное дважды (тогда у него должен быть один владелец), либо два разных понятия под неоднозначным именем (тогда хотя бы одно надо переименовать по его ограниченному контексту). Оба случая — предмет ревью, поэтому класс `trigger`.

## Пример

Юнит-тест `Same_short_name_across_modules_is_E4`: публичные типы `Account::Account.Foo` и `Home::Home.Foo` дают находку `duplicate concept: Account::Account.Foo ~ Home::Home.Foo` с `FromModule = Account`, `ToModule = Home`. Тест `Near_miss_long_names_across_modules_is_E4`: `Processor` и `Processer` (девять символов, расстояние `1`) — находка. Тест `Short_unequal_names_are_not_E4`: `Foo` и `Fob` — тишина, потому что имена короче восьми символов. Тесты `Same_module_similar_names_is_not_E4` и `Internal_types_are_not_E4` подтверждают фильтры по модулю и публичности. Тест `Fingerprint_orders_type_ids_A_before_B`: пара `Home::Home.Foo`, `Account::Account.Foo` даёт тот же отпечаток, что и пара в обратном порядке, — `A` всегда меньше `B` по ordinal. Тест `More_than_twenty_pairs_are_capped_at_twenty`: из 21 совпадающей пары в отчёт попадают двадцать.

```csharp
// Account.Contracts — публичный тип модуля Account
public sealed record Address(string City, string Street);
// Shipping.Contracts — публичный тип модуля Shipping
public sealed record Address(string Line1, string PostalCode);
// короткие имена равны без учёта регистра → distance 0
// → E4 «duplicate concept: Account.Contracts::Account.Contracts.Address ~ Shipping.Contracts::Shipping.Contracts.Address»

public sealed class Customer { }   // модуль Billing:  CUSTOMER
public sealed class Costumer { }   // модуль Support:  COSTUMER — две замены, distance 2, длина 8 → E4

public sealed class OrderLine { }  // модуль Orders
public sealed class OrderLink { }  // модуль Catalog — distance 1 → E4, хотя понятия разные
```

## Где смотреть в отчёте

- **Вкладка Findings** — строка `E4 | trigger | {модуль A} | {модуль B} | duplicate concept: {A} ~ {B} |`; колонка Evidence пуста. Тот же объект в `findings.json`.
- **`graph.json`** — записи `types` с `"accessibility": "public"`: по ним можно проверить, действительно ли оба типа публичны, и посмотреть их `publicApi`, чтобы понять, одно это понятие или два.
- **Вкладка Metrics, таблица Contracts** — колонка `Surface` по контрактным сборкам: дубликаты в контрактах увеличивают поверхность обоих модулей.
- **Вкладка Metrics, таблица Modules** — колонка `Public impl`: публичный тип в сборке реализации, участвующий в E4, одновременно учитывается метрикой [publicInImplementation](../metrics/publicInImplementation.md).
- **`gate-report.json`** — та же находка, если её отпечатка нет в `knownFindings`.

## Как исправить

1. Решите, одно перед вами понятие или два. Сравните публичные члены (`publicApi` в `graph.json`) и места использования: одинаковые поля и одинаковые правила — одно понятие; одинаковое имя при разных полях — два.
2. Для одного понятия назначьте владельца. Общий примитив (идентификатор, деньги, адрес в его инфраструктурном смысле) переносится в `shared`; понятие, принадлежащее одному модулю, остаётся в его контрактной сборке, а второй модуль начинает зависеть от этого контракта — такое ребро разрешено правилами [A1](A1.md) и [A2](A2.md).
3. Для двух понятий переименуйте хотя бы одно по его ограниченному контексту: `BillingAddress` и `ShippingAddress`, `SupportTicketCustomer` вместо второго `Customer`. Имя должно уточнять смысл, а не просто отличаться.
4. Если тип не должен быть частью API модуля, сделайте его `internal`: правило сравнивает только публичные типы. Это допустимо лишь тогда, когда снаружи он действительно никому не нужен.
5. Повторите `arch-lens map`: убедитесь, что пара исчезла и что на её место из-под капа не поднялась другая с тем же корнем проблемы.

**Когда допустимо принять.** Конвенционные имена, которые есть в каждом модуле по замыслу (`Options`, `Startup`, `ModuleRegistration`, `Constants`), а также разные понятия с устоявшимися одинаковыми именами, которые переименовывать дороже, чем терпеть (`Order` в продажах и `Order` в сортировке). Зафиксируйте пары командой `arch-lens baseline`: отпечаток содержит оба идентификатора, поэтому переименование любого из двух типов вернёт находку как новую, а появление третьего одноимённого модуля даст новые пары.

## Чего не делать

- Не переименовывайте ради обхода расстояния: `Processor` и `Processor2` отличаются на один символ и останутся находкой; имена вида `FooX` ничего не говорят читателю.
- Не делайте тип `internal`, если он нужен соседнему модулю: соседу придётся продублировать его, и понятие размножится ещё раз.
- Не сваливайте все совпавшие типы в `shared` без разбора: общее ядро должно содержать общие понятия, а рост его притяжения увидят [B9](B9.md) и чип `shared types`.
- Не объединяйте два разных понятия в один тип только потому, что совпали имена: правило сигнализирует о неоднозначности имени, а не требует единого типа.
