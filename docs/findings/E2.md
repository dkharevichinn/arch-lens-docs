# E2 — Мёртвый тип реализации: ни одного входящего ребра и ни одной регистрации в DI

| Поле | Значение |
|---|---|
| Код | `E2` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `TypeSmellAnalyzer.AddDeadTypes`, вызывается из `StaticMetricsCalculator.Calculate` |
| Команды | `map` (находка снимка: `findings.json`, вкладка Findings), `baseline` (отпечаток попадает в `knownFindings`), `gate` (находка проходит фильтр `knownFindings`) |
| Условие | роль сборки `implementation` или `infrastructure`; ноль входящих рёбер от учитываемых типов; тип не является потребителем контейнера |
| Кап | не больше 20 находок на снимок (`Cap = 20`), по ordinal идентификатора типа |
| Отпечаток | `ForTypeEdge("E2", typeId, "", [])` — идентификатор типа, пустая цель, пустой список видов |
| Сообщение | `dead type: {typeId}` |

## Термины

Базовые понятия — [сборка, модуль и роль](../glossary.md#module), [учитываемый модуль](../glossary.md#scored), [виды рёбер между типами](../glossary.md#edge-kinds), [порт и потребитель контейнера](../glossary.md#binding-edge) — определены в словаре. Для E2 важны три уточнения.

**Входящее ребро** здесь — ребро любого вида (`call`, `parameter`, `fieldType`, `implementation`, `inheritance`, `genericArgument`, `attribute`, `return`) из **учитываемого** типа, то есть из типа сборки с ролью не `host` и не `test`. Источник может лежать в том же модуле или в чужом — это не важно. Вес ребра не важен тоже: одного упоминания достаточно. Рёбра из типов сборок `host` и `test` в этот счётчик **не входят**: анализатор собирает соседей только среди учитываемых типов, и корень композиции для него не существует как источник.

**Потребитель контейнера** (`BindingSemantics.IsContainerConsumer`) — тип, который встречается как сервис (`service`) или как реализация (`implementation`) хотя бы в одной регистрации DI, сделанной **не** из тестовой сборки. Регистрация — это извлечённый вызов Microsoft.Extensions.DependencyInjection: `AddSingleton<IFoo, Foo>()`, `AddScoped<Foo>()`, фабрика `AddTransient<Foo>(sp => …)` (реализация неизвестна, но сервис `Foo` записан), `TryAdd…`, дескриптор, а также непрозрачная (`opaque`) обёртка `Add*`/`TryAdd*` над `IServiceCollection`. Список регистраций лежит в `graph.json` в разделе `bindings.registrations`; у каждой записи есть `registrar` — тип, в котором сделан вызов, и именно по его сборке проверяется роль `test`.

**Роль сборки** ограничивает кандидатов: E2 смотрит только на типы из сборок `implementation` и `infrastructure`. Типы контрактных сборок существуют для внешних потребителей, которых в снимке может не быть; типы `ui` создаются фреймворком; типы `shared` — общее ядро; `host` и `test` не учитываются вовсе.

## Когда срабатывает

```text
E2 для T ⇔ role(assembly(T)) ∈ { implementation, infrastructure }
         ∧ |incoming[T]| == 0          — входящие считаются только от учитываемых типов
         ∧ ¬IsContainerConsumer(T)     — нет регистрации DI с registrar вне тестовых сборок
```

Вид типа не важен: под правило попадают классы, интерфейсы, записи, структуры, перечисления и делегаты. Кандидаты сортируются по ordinal идентификатора и берутся первые двадцать; поля находки — `FromModule` равен модулю типа, `ToModule` и `Evidence` пусты.

Из формулы следуют четыре ситуации, которые надо понимать до того, как удалять код.

1. **Тип используется напрямую из `host` без регистрации.** `Program` в корне композиции пишет `new Account.Migrator().Run()`: ребро `call` из `host` в `Account.Migrator` существует в `graph.json`, но в счётчик `incoming` не попадает, потому что источник не учитываемый. Регистрации тоже нет. Для E2 такой тип **мёртвый**. Это осознанное ограничение правила, а не ошибка извлечения.
2. **Тип используется только из тестов.** Ребро из тестовой сборки не учитывается, регистрация из тестового `Startup` не делает тип потребителем контейнера (тест `Test_only_registration_does_not_save_E2`). Тип выглядит мёртвым — и это верный сигнал: продуктовый код без продуктовых пользователей.
3. **Тип создаётся фреймворком по конвенции.** Контроллеры ASP.NET, обнаруживаемые через `AddControllers()`, конфигурации EF Core, подхватываемые `ApplyConfigurationsFromAssembly`, обработчики, регистрируемые сканированием сборок, — всё это не даёт ни рёбер, ни индивидуальных регистраций. Такие типы будут находками E2, пока вы их не примете.
4. **Контейнер не Microsoft.Extensions.DependencyInjection.** Если решение собирает граф зависимостей через Autofac, сканирование или рефлексию, экстрактор регистраций не увидит, `IsContainerConsumer` вернёт `false` для всех типов, и каждый тип, который связан с остальными только через контейнер, окажется в E2. Признак — ноль в строке `registrations` раздела Runtime (DI) на вкладке Metrics.

**Что означает кап 20.** Сортировка по ordinal означает, что при сотне мёртвых типов вы увидите первые двадцать по алфавиту идентификаторов, и после их удаления появятся следующие двадцать. Двадцать строк E2 — это «не меньше двадцати», а `baseline` фиксирует отпечатки только видимых.

## Пример

Юнит-тест `Unreferenced_impl_not_in_bindings_is_E2`: единственный тип `M::M.Orphan` в модуле реализации `M`, без рёбер и без регистраций, даёт находку `dead type: M::M.Orphan` с `FromModule = M`. Тест `ImplementationTypeId_in_non_test_registration_is_not_E2`: регистрация `ISvc → Impl` спасает `Impl`. Тест `ServiceTypeId_in_non_test_registration_is_not_E2`: регистрация с сервисом `Svc` и неизвестной реализацией (фабрика) спасает `Svc`. Тест `Incoming_product_edge_is_not_E2`: одно входящее ребро от типа того же модуля — и находки нет. Тест `Contract_ui_and_shared_fan_in_zero_are_not_E2`: изолированные типы в сборках `contract`, `ui` и `shared` не находки. Тест `Unreferenced_infrastructure_is_E2`: тип `I::I.Db` в сборке `infrastructure` — находка. Тест `E2_cap_is_twenty_by_typeId_ordinal`: из типов `Z00`…`Z20` в отчёт попадают `Z00`…`Z19`.

```csharp
// Account/LegacyCsvImporter.cs — сборка Account, роль implementation
internal sealed class LegacyCsvImporter { public void Run() { /* … */ } }
// Ни один учитываемый тип на него не ссылается, регистрации нет
// → E2 «dead type: Account::Account.LegacyCsvImporter»

// App.Host/Program.cs — роль host
new LegacyCsvImporter().Run();                 // ребро host → Account не считается: E2 остаётся

// App.Host/Program.cs — регистрация делает тип потребителем контейнера
services.AddSingleton<LegacyCsvImporter>();    // теперь E2 молчит
```

## Где смотреть в отчёте

- **Вкладка Findings** — строка `E2 | trigger | {модуль} | | dead type: {typeId} |`; колонки To и Evidence пусты. Тот же объект в `findings.json`.
- **`graph.json`** — проверка вручную: записи `edges` с `"to"` равным идентификатору типа (обратите внимание на сборку источника — `host` и `test` не считаются) и записи `bindings.registrations`, где `service` или `implementation` равен идентификатору типа, а `registrar` лежит вне тестовой сборки.
- **Вкладка Metrics, раздел Runtime (DI)** — строка `registrations`. Ноль означает, что регистраций DI в снимке нет вовсе, и E2 будет срабатывать на каждый тип, живущий только в контейнере.
- **Вкладка Metrics, таблица Modules** — колонка `Types` включает мёртвые типы; после их удаления число уменьшится.
- **`gate-report.json`** — та же находка, если её отпечатка нет в `knownFindings`.

## Как исправить

1. Убедитесь, что тип действительно не используется: поищите обращения через рефлексию, сканирование сборок, строковые имена в конфигурации и атрибуты фреймворков. Экстрактор таких связей не видит.
2. Если тип мёртв — удалите его вместе с тестами, которые проверяли только его. Это единственное исправление, которое уменьшает объём кода и не меняет архитектуру.
3. Если тип нужен только корню композиции (мигратор, инициализатор, фоновая задача), зарегистрируйте его в контейнере и получайте из него, а не создавайте через `new` в `Program`: тип станет потребителем контейнера, а заодно попадёт в поле зрения [R2](R2.md).
4. Если тип используется только тестами — перенесите его в тестовый проект; продуктовой сборке он не нужен.
5. Если тип — публичный API для потребителей вне решения (вы поставляете библиотеку), перенесите его в контрактную сборку модуля, а не оставляйте в реализации: там его публичность проверяют [A4](A4.md) и [A5](A5.md), а не E2.

**Когда допустимо принять.** Типы, которые создаёт фреймворк по конвенции (контроллеры, конфигурации EF Core, обработчики, найденные сканированием), точки входа плагинов и типы, которые корень композиции сознательно использует напрямую, — это законные исключения. Зафиксируйте их командой `arch-lens baseline`: отпечатки попадут в `knownFindings`. Отпечаток привязан к идентификатору типа, поэтому переименование или перенос в другое пространство имён вернёт находку. Если в решении не Microsoft.Extensions.DependencyInjection, примите E2 целиком как неинформативное правило для этого репозитория и укажите причину в описании коммита с `baseline.json`.

## Чего не делать

- Не добавляйте фиктивную регистрацию `services.AddSingleton<X>()` только чтобы тип стал потребителем контейнера: контейнер начнёт создавать объект, который никому не нужен, а причина находки останется.
- Не создавайте ложную ссылку из другого типа («чтобы было входящее ребро») — это связность ради тишины.
- Не переносите тип в контрактную сборку ради выхода из-под правила: конкретный класс в контракте — это [A5](A5.md), рост поверхности — [A4](A4.md), а единственный внешний потребитель нового публичного типа — [G2](G2.md).
- Не переносите тип в сборку с ролью `host`: он станет неучитываемым для всех правил, а не только для E2.
- Не читайте двадцать строк E2 как «в модуле двадцать мёртвых типов»: это первые двадцать по алфавиту.
