# B5 — Наибольшая циклическая компонента достигла размера `coreSizeMin`

| Поле | Значение |
|---|---|
| Код | `B5` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet`; сама по себе находка не блокирует |
| Кто выдаёт | `StaticMetricsCalculator.Calculate` по результату `CorePathAnalyzer.Compute(graph)` |
| Команды | `map` — находка снимка, попадает в `findings.json` и на вкладку Findings; `gate` — проходит в `gate-report.json`, если её отпечатка нет в `knownFindings` |
| Метрики | [`coreSize`](../metrics/coreSize.md) и [`coreShare`](../metrics/coreShare.md), чипы **coreSize** и **coreShare** на вкладке Metrics; состав компонент — раздел **Cycles** |
| Порог | `gate.coreSizeMin` в `arch-lens.yaml`, по умолчанию `3` (`GateOptions.CoreSizeMin`); условие `coreSize >= coreSizeMin` |
| Отпечаток | `ForTypeEdge("B5", "A,B,C", "", [])` — идентификаторы модулей наибольшей компоненты в ordinal-порядке через запятую без пробела; `FromModule` и `ToModule` пусты, `Evidence` пуст; не больше одной находки на снимок |
| Сообщение | `core SCC: A, B, C` — те же идентификаторы через запятую с пробелом |

## Термины

Базовые понятия — [граф модулей](../glossary.md#module-graph), [компонента сильной связности](../glossary.md#scc) и [ordinal-порядок](../glossary.md#ordinal) — определены в словаре; подробное объяснение компонент и того, почему одиночный модуль циклом не считается, есть на странице [B1](B1.md).

**Ядро** (`core`) — наибольшая по числу модулей циклическая компонента графа модулей, то есть наибольшее множество модулей, каждый из которых прямо или через цепочку зависит от каждого другого. Такое множество нельзя собрать, понять, протестировать или развернуть по частям: любое изменение в одном из его модулей потенциально возвращается в него же по кругу. Слово «ядро» здесь описательное — компонента не обязана быть чем-то центральным по замыслу, чаще это несколько функциональных модулей, случайно сросшихся взаимными ссылками.

**`coreSize`** — число модулей в ядре, `0`, если циклических компонент нет. При двух компонентах одинакового размера ядром считается та, у которой строка из идентификаторов, соединённых через `"\0"`, ordinal-меньше (тест `Equal_size_cyclic_sccs_pick_ordinal_min_member_join`: из `{M, N}` и `{A, B}` выбирается `{A, B}`).

**`coreShare`** — доля модулей графа, попавших в ядро: `coreSize / N`, где `N` — число модулей графа; `0`, если ядра нет. Правила на эту долю не завязаны, она нужна для чтения масштаба: ядро из трёх модулей в системе из двенадцати — это `0.25`, а пара модулей в решении из двух — `1.0`.

## Когда срабатывает

`CorePathAnalyzer.Compute` находит компоненты тем же `StronglyConnectedComponents.Find`, что и метрика `cycles`, и выбирает ядро:

```text
cyclicSccs = компоненты графа модулей с числом модулей >= 2
core       = компонента наибольшего размера (при равенстве — с ordinal-минимальной строкой join("\0", …))
coreSize   = |core|, или 0, если циклических компонент нет
coreShare  = coreSize == 0 ? 0 : coreSize / N
```

Находка добавляется при одном условии:

```text
coreSize >= gate.coreSizeMin  и  ядро непусто
```

Порог берётся из YAML (`gate.coreSizeMin`), по умолчанию `3`; сравнение нестрогое (`>=`). Пара взаимозависимых модулей при пороге по умолчанию B5 не даёт — это территория [B1](B1.md); при `coreSizeMin: 2` B5 срабатывала бы и на пару (тест `Calculator_honors_core_size_min_override`).

Три следствия, важные на практике.

1. Находка **одна** и относится только к наибольшей компоненте. Если в графе две компоненты по три модуля, отчёт назовёт одну из них (ordinal-минимальную), а вторая останется без строки B5, хотя её видно в разделе Cycles и на неё сработает B1.
2. Отпечаток включает состав ядра. Если ядро выросло с `{A, B, C}` до `{A, B, C, D}` или сменило состав, отпечаток меняется, и запись в `knownFindings` перестаёт его глушить. Это встроенная защита: принятое ядро может быть только таким, каким его приняли.
3. Класс `trigger`: сама по себе находка даёт вердикт `triggers` (код выхода 4). Но гейт на том же графе почти всегда выдаёт для той же компоненты ещё и [B1](B1.md) класса `invariant`, если её нет в `knownCycles`, и тогда вердикт — `block`.

### Чем B5 отличается от соседей по семейству

| Правило | Вопрос, на который оно отвечает | Механизм принятия |
|---|---|---|
| [B1](B1.md) | Есть ли компонента, отсутствующая в `knownCycles`? Любого размера, класс `invariant`, только гейт. | `knownCycles` |
| [B2](B2.md) | Выросла ли доля веса внутри циклов? | порог `ratchets.tanglePct` |
| **B5** | Достигло ли **наибольшее** ядро абсолютного размера `coreSizeMin`? Класс `trigger`, находка снимка. | `knownFindings` (по составу ядра) или порог в YAML |
| [B6](B6.md) | Насколько длинна самая длинная цепочка после стягивания циклов? Цикл эту цепочку **укорачивает**. | `knownFindings` или порог в YAML |

## Пример

Юнит-тест `Three_cycle_emits_B5_with_ordinal_joined_ids`: три модуля реализации с рёбрами `C → A`, `A → B`, `B → C`. `coreSize = 3`, `maxModulePath = 0` (весь граф стянулся в один узел конденсации), ядро — `["A", "B", "C"]`. Находка класса `trigger` с отпечатком `ForTypeEdge("B5", "A,B,C", "", [])`, сообщением `core SCC: A, B, C`, пустыми `FromModule`, `ToModule` и `Evidence`.

Тест `Two_cycle_is_below_default_core_size_min` из `CorePathAnalyzerTests`: пара `A ↔ B` даёт `coreSize = 2`, `coreShare = 1.0`, компоненту `["A", "B"]` в `cycles` и **не** даёт B5. Тест `New_B5_fingerprint_is_triggers_not_block` из `GateEvaluatorTests`: если компонента уже есть в `knownCycles`, а отпечаток B5 из `knownFindings` убран, гейт выдаёт единственную находку B5 и вердикт `triggers`.

Пример ближе к практике: `Account` ссылается на `Gameplay.Contracts`, `Gameplay` — на `Home.Contracts`, `Home` — на `Account.Contracts`. Ни одно ребро не нарушает [A1](A1.md), но три модуля образуют компоненту `{Account, Gameplay, Home}`: чип `coreSize` покажет `3`, при двенадцати модулях чип `coreShare` — `25%`, а на вкладке Findings появится строка `core SCC: Account, Gameplay, Home`.

## Где смотреть в отчёте

- **Вкладка Findings** — строка `B5 | trigger | | | core SCC: Account, Gameplay, Home | ` с пустыми колонками From, To и Evidence; код правила — ссылка на эту страницу. Та же запись лежит в `findings.json`.
- **Вкладка Metrics, чипы `coreSize` и `coreShare`** — размер ядра целым числом и его доля в процентах (`25%`); в `metrics.json` — ключи `coreSize` и `coreShare` (доля от 0 до 1).
- **Вкладка Metrics, раздел Cycles** — все циклические компоненты; ядро — самая длинная строка (при равенстве — ordinal-меньшая).
- **`gate-report.json`** — тот же объект с `"class": "trigger"`, если отпечатка нет в `knownFindings`; рядом, скорее всего, будет B1 для той же компоненты.
- **`arch-lens.yaml`, ключ `gate.coreSizeMin`** — действующий порог; если ключа нет, действует `3`.

## Как исправить

1. Возьмите состав ядра из сообщения и найдите его рёбра: строки [A1](A1.md)/[A2](A2.md) на вкладке Findings, колонки Fan-in и Fan-out таблицы Modules, при необходимости `graph.json`.
2. Отделяйте модули с края. Выберите модуль, у которого меньше всего рёбер внутрь ядра, и разорвите их: зависимостью от контракта вместо тела (если ребро шло в реализацию), портом, которым владеет нижний модуль, или выносом общего типа в `shared`. Каждый отделённый модуль уменьшает `coreSize` на единицу либо раскалывает ядро на меньшие компоненты.
3. Помните, что раскол ядра даёт **новые** компоненты: `{A, B, C}` → `{A, B}` — это другое множество, и [B1](B1.md) на него сработает, пока `knownCycles` не обновлён. Разбирайте до конца или обновляйте baseline после каждого шага.
4. Если несколько модулей ядра нуждаются в одном понятии, вынесите его в `shared` или в отдельный модуль, который ни от одного из них не зависит.
5. Проверьте результат командой `arch-lens map`: чип `coreSize` должен стать меньше порога, а в идеале — `0`.

**Когда допустимо принять.** Если ядро — унаследованное состояние с планом разбора, выполните `arch-lens baseline`: отпечаток B5 попадёт в `knownFindings`, компонента — в `knownCycles`. Благодаря отпечатку по составу принятие действует ровно на это ядро: любой новый участник снова поднимет B5. Порог `coreSizeMin` для принятия менять не нужно.

## Чего не делать

- Не поднимайте `gate.coreSizeMin` до заведомо недостижимого значения, чтобы «отключить» правило: это скроет рост ядра, ради которого правило и существует.
- Не объединяйте модули ядра в один идентификатор через YAML (`module:`), если это не один модуль по смыслу: ядро исчезнет из отчёта, но его сборки продолжат зависеть друг от друга, а [C1](C1.md) отметит разбухший модуль.
- Не считайте, что принятие B5 через `knownFindings` покрывает [B1](B1.md), или наоборот: B1 глушится только через `knownCycles`, B5 — только через `knownFindings`, и списки не связаны.
- Не читайте отсутствие B5 как отсутствие циклов: пары модулей при пороге по умолчанию правило не видит, их показывает раздел Cycles.
- Не «укорачивайте» длинную цепочку из [B6](B6.md), замыкая её в цикл: путь в конденсации станет короче, а ядро — больше.
