# R2 — Незарегистрированный порт: порт внедряется в потребителей контейнера, но ни одной регистрации вне тестов у него нет

| Поле | Значение |
|---|---|
| Код | `R2` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `RuntimeAnalyzer.AnalyzeR2`, вызывается из `StaticMetricsCalculator.Calculate` |
| Команды | `map` (находка снимка: `findings.json`, вкладка Findings), `baseline` (отпечаток попадает в `knownFindings`), `gate` (находка проходит фильтр `knownFindings`) |
| Метрика | [`runtime`](../metrics/runtime.md): строка `unboundPorts` равна числу находок R2 в снимке, строка `ports` — числу портов-кандидатов |
| Отпечаток | `ForTypeEdge("R2", portTypeId, "", [])` — идентификатор порта, пустая цель, пустой список видов |
| Сообщение | `port {typeName} injected in {n} types, no DI registration`, где `typeName` — идентификатор порта без префикса `Сборка::`, а `n` — число типов-потребителей |
| Свидетельства | по одной записи на потребителя: `потребитель → порт (parameter:1)` |
| Поля | `FromModule` — модуль сборки, в которой объявлен порт (пусто, если сборка не привязана к модулю); `ToModule` пуст |

## Термины

Базовые понятия — [порт, потребитель контейнера и ребро `binding`](../glossary.md#binding-edge), [сборка, модуль и роль](../glossary.md#module), [идентификатор типа](../glossary.md#type-id) — определены в словаре. Для R2 они нужны в точной формулировке.

**Порт** (`BindingSemantics.IsPort`) — интерфейс или абстрактный класс из графа кода решения. Записи, включая `abstract record`, портами не считаются (тест `R2_skips_abstract_record_even_when_catalog_contains_injection`). Внешние интерфейсы — `ILogger<T>`, `IOptions<T>`, `IHttpClientFactory` — в граф не входят, портами не являются и R2 не порождают.

**Внедрение** (`Injection`) — пара «потребитель, порт», извлечённая из параметров явно объявленных конструкторов, включая первичные конструкторы; аргументы обобщённых типов раскрываются, поэтому `IEnumerable<IHandler>`, `Lazy<IFoo>` и `Func<IFoo>` дают внедрение соответствующего порта. Параметры методов внедрениями не считаются. Обобщённые порты хранятся по открытому определению: `IRepository<Order>` и `IRepository<Payment>` — один порт `IRepository<T>`, и регистрация любого закрытого варианта связывает его целиком.

**Потребитель контейнера** (`BindingSemantics.IsContainerConsumer`) — тип, который встречается как `service` или `implementation` в регистрации DI, сделанной не из тестовой сборки. Для R2 потребитель, кроме того, сам не должен лежать в тестовой сборке (`RuntimeAnalyzer.IsConsumed`). **Почему незарегистрированный класс невидим.** Контейнер создаёт только те объекты, о которых знает; класс без регистрации собирается вручную через `new` или фреймворком, и контейнер его конструктор не разрешает. Если бы правило считало внедрения таких классов, каждый вручную собираемый объект с параметром-интерфейсом давал бы ложное «незарегистрированный порт». Поэтому анализ времени выполнения — R2, [R1](R1.md), рёбра `binding`, метрика `runtime` — начинается с потребителя контейнера (тест `R2_requires_container_consumer`). Обратная сторона: класс, который создаёт фреймворк по конвенции или `ActivatorUtilities`, для R2 не существует, и его незарегистрированные порты правило не увидит. Потребители из сборки `host` учитываются наравне с остальными, если зарегистрированы.

**Связывающая регистрация** — любая регистрация с `service`, равным идентификатору порта, у которой `registrar` (тип, где сделан вызов) лежит вне тестовой сборки. Форма регистрации не важна: `generic` (`AddScoped<IFoo, Foo>()`), `factory` (реализация неизвестна), `instance`, `descriptor` и `opaque`. Непрозрачная регистрация (`opaque`) — вызов `Add*` или `TryAdd*` над `IServiceCollection`, который не является базовым методом Microsoft.Extensions.DependencyInjection и среди аргументов типа которого есть тип решения; первый такой тип записывается как сервис, реализация остаётся неизвестной. Так `services.AddRefitClient<IPaymentsApi>()` связывает порт `IPaymentsApi`, хотя реализацию генерирует библиотека. Регистрация, сделанная только из тестовой сборки, порт не связывает.

## Когда срабатывает

```text
consumed(C) ⇔ C не в тестовой сборке ∧ IsContainerConsumer(C)
ports       = { S : есть внедрение (C, S), S есть в графе, IsPort(S), consumed(C) }
для каждого S ∈ ports по ordinal:
  consumers = { C : внедрение (C, S), consumed(C) }, по ordinal
  bound(S)  ⇔ есть регистрация с service == S и registrar вне тестовой сборки
  R2(S)     ⇔ |consumers| > 0 ∧ ¬bound(S)
runtime.ports        = |ports|
runtime.unboundPorts = число находок R2
```

Смысл: контейнер при первом разрешении такого потребителя завершится ошибкой `Unable to resolve service for type …`, если только порт не приходит из источника, который экстрактор не видит. R2 — это предупреждение о падении при старте или при первом обращении, полученное без запуска приложения.

Ограничения экстракции DI (README, раздел «DI bindings»): порядок регистраций и `Replace` не моделируются, ключевые сервисы не поддерживаются, вызовы локатора сервисов не считаются внедрениями, регистрации под `#if` записываются как скомпилированные. Регистрации через сканирование сборок или циклы с рефлексией экстрактор не распознаёт — порты, связанные так, будут выглядеть незарегистрированными. Коллекция `IEnumerable<IPlugin>` без единой регистрации законна для Microsoft.Extensions.DependencyInjection (разрешится пустой), но для R2 это незарегистрированный порт.

## Пример

Юнит-тест `R2_unbound_port_from_non_test_consumer`: `C::C.Consumer` зарегистрирован сам на себя (потребитель контейнера) и внедряет интерфейс `P::P.IFoo` из контрактной сборки `P`; регистраций `IFoo` нет. Находка: сообщение `port P.IFoo injected in 1 types, no DI registration`, `FromModule = P`, отпечаток `ForTypeEdge("R2", "P::P.IFoo", "", [])`, свидетельство `C::C.Consumer → P::P.IFoo (parameter:1)`. Тест `R2_requires_container_consumer`: тот же потребитель без регистрации — тишина, с регистрацией — находка. Тест `Test_only_registration_still_R2_opaque_clears_test_consumer_does_not`: регистрация `IFoo` из `T::T.Reg` тестовой сборки не спасает; непрозрачная регистрация из продуктового кода спасает; потребитель из тестовой сборки находку не порождает. Тест `Evidence_is_sorted_by_from_then_to`: два потребителя дают одну находку с `n = 2` и свидетельствами по ordinal.

```csharp
// Games.Contracts — порт
public interface IGameRepository { Game? Find(GameId id); }

// Games.UI — роль ui
public sealed class GameSetupViewModel(IGameRepository games) { /* … */ }   // внедрение (GameSetupViewModel, IGameRepository)

// App.Host — корень композиции
services.AddTransient<GameSetupViewModel>();   // потребитель контейнера
// регистрации IGameRepository нет
// → R2 «port Games.Contracts.IGameRepository injected in 1 types, no DI registration», FromModule = Games

services.AddScoped<IGameRepository, EfGameRepository>();   // любая регистрация вне тестов — R2 молчит
services.AddRefitClient<IPaymentsApi>();                   // opaque: порт IPaymentsApi связан, реализация неизвестна
```

## Где смотреть в отчёте

- **Вкладка Findings** — строка `R2 | trigger | {модуль порта} | | port {typeName} injected in {n} types, no DI registration | C1 → S (parameter:1), C2 → S (parameter:1)`. Тот же объект в `findings.json`.
- **Вкладка Metrics, раздел Runtime (DI)** — строки `ports` (порты, внедряемые в потребителей контейнера), `unboundPorts` (число находок R2 в снимке — `knownFindings` это число не уменьшает), `registrations`, `opaque`, `unresolved`. В `metrics.json` — `runtime.ports`, `runtime.unboundPorts`, `runtime.registrations.*`. Ноль в `registrations` при ненулевых `ports` означает, что регистрации не извлечены вовсе, и R2 сработает на каждый порт.
- **`graph.json`** — `bindings.injections` (`consumer`, `service`) показывает, кто внедряет порт; `bindings.registrations` (`service`, `implementation`, `shape`, `registrar`, `location`) — есть ли регистрация и откуда она сделана.
- **`gate-report.json`** — та же находка, если её отпечатка нет в `knownFindings`.

## Как исправить

1. Зарегистрируйте порт в корне композиции с нужной реализацией и временем жизни: `services.AddScoped<IGameRepository, EfGameRepository>()`. Это единственное исправление, которое устраняет причину, а не сигнал.
2. Если реализацию предоставляет внешняя библиотека через свой метод расширения (`AddRefitClient<T>()`, `AddHttpClient<TClient, TImplementation>()`), убедитесь, что порт передаётся ему аргументом типа: тогда экстрактор запишет регистрацию как `opaque` или как базовую, и порт будет связан.
3. Если регистрация выполняется сканированием сборок или циклом с рефлексией, замените её явной регистрацией для портов, которые внедряются в продуктовый код, либо примите находку — экстрактор такую регистрацию не увидит.
4. Если порт необязателен, зарегистрируйте явную пустую реализацию (null object) вместо расчёта на отсутствие регистрации.
5. Если потребитель порта на деле не используется (собирается только в тестах), удалите потребителя или порт; проверьте заодно [E2](E2.md) и [E3](E3.md).
6. Повторите `arch-lens map` и убедитесь, что `unboundPorts` равен нулю.

**Когда допустимо принять.** Порты, которые связываются способом, невидимым для экстрактора (сканирование сборок, сторонний контейнер, регистрация в другом решении, если корень композиции живёт отдельно), и коллекции `IEnumerable<T>`, для которых пустое разрешение — норма. Зафиксируйте командой `arch-lens baseline`: отпечаток привязан к идентификатору порта, поэтому переименование порта вернёт находку, а появление нового потребителя — нет. Строка `unboundPorts` на вкладке Metrics продолжит показывать принятые порты: метрика считает находки снимка до фильтрации по `knownFindings`.

## Чего не делать

- Не регистрируйте порт только в тестовом `Startup`: продуктовая композиция останется без регистрации, и R2 не изменится.
- Не заменяйте порт в конструкторе конкретным классом, чтобы внедрение перестало быть внедрением порта: между модулями это даст [A1](A1.md), а внутри модуля уничтожит шов, ради которого порт создавался.
- Не добавляйте фиктивную регистрацию вида `AddSingleton<IFoo>(_ => null!)`: для R2 порт станет связанным, а во время выполнения потребитель получит `null`.
- Не принимайте R2 для порта, который внедряется продуктовым кодом, не выяснив, откуда возьмётся реализация: это отложенное падение при первом разрешении.
