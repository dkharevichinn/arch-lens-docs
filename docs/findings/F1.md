# F1 — Тесты обращаются к модулям мимо контрактов (`testsPastContract`)

| Поле | Значение |
|---|---|
| Код | `F1` |
| Класс | двойственный. На `map` — `trigger` со свидетельствами. На `gate` — либо `trigger` с сообщением `new ratchet F1` (ключ в baseline отсутствует), либо `ratchet` → вердикт **[block](../gates/block.md)**, код выхода 5 (доля строго выросла) |
| Кто выдаёт | доля и свидетельства — `TestTopologyAnalyzer.Analyze`; находка снимка — `StaticMetricsCalculator.Calculate`; находка гейта — `GateEvaluator.AddTestsPastContractRatchet` |
| Команды | `arch-lens map` пишет F1 в `findings.json`, если есть хотя бы одно ребро мимо контракта; `arch-lens gate` **всегда** отбрасывает F1 снимка и синтезирует собственную по `baseline.ratchets.testsPastContract`, поэтому `knownFindings` на F1 гейта не влияет |
| Метрика | [testsPastContract](../metrics/testsPastContract.md), чип `testsPastContract` на вкладке Metrics |
| Порог | `baseline.ratchets.testsPastContract` — порог в `baseline.json`, который запрещено ухудшать; отсутствие ключа означает «порог не зафиксирован», а не ноль |
| Отпечаток | всегда `ForTypeEdge("F1", "", "", [])` — один на весь репозиторий, и на `map`, и на `gate` |
| Сообщение | на `map`: `testsPastContract {value}`; на `gate`: `new ratchet F1` либо `testsPastContract {cur} > baseline {bas}` (числа с точкой, инвариантная культура) |

## Термины

Понятия [роль сборки](../glossary.md#module), [учитываемый модуль](../glossary.md#scored), [вес ребра](../glossary.md#weight), [ratchet](../glossary.md#ratchet) и [свидетельства](../glossary.md#finding) определены в словаре.

**Тестовое ребро** — ребро из типа сборки с ролью `test` в тип **учитываемого** модуля. Рёбра из тестов в другие тестовые сборки и в сборки `host` тестовыми не считаются и в расчёт не входят вообще.

**Ребро мимо контракта** (`past`) — тестовое ребро, у которого роль целевой сборки не `contract` и не `shared`: тест напрямую трогает тип из `implementation`, `infrastructure` или `ui`. Обращение к контракту или к общему ядру ребром мимо контракта не считается.

**Доля `testsPastContract`** — отношение веса рёбер мимо контракта к весу всех тестовых рёбер: число от `0` до `1`, которое чип на вкладке Metrics показывает в процентах. Сохранённое в `baseline.json` значение этой доли и есть `ratchet` правила — порог, который гейт не даёт увеличить и который при улучшении сам не переписывается.

## Когда срабатывает

Сначала общая для обеих команд арифметика в `TestTopologyAnalyzer.Analyze`:

```text
total = Σ вес(ребро) по рёбрам из типов сборок test в типы учитываемых модулей
past  = Σ вес(ребро) по тем из них, у которых роль целевой сборки не contract и не shared
testsPastContract = total == 0 ? 0 : past / total
```

### На `map`: находка снимка со свидетельствами

Если `past > 0`, в `findings.json` попадает одна находка класса `trigger` с пустыми `FromModule` и `ToModule`, сообщением `testsPastContract {value}` (например, `testsPastContract 0.5`) и до **десяти** свидетельств — пар «тип теста → тип продукта» с разбивкой веса по видам рёбер, упорядоченных по убыванию суммарного веса (при равенстве — по `From`, затем по `To` в ordinal-порядке). Если ни одного ребра мимо контракта нет, находки на `map` нет, даже когда тестов много.

### На `gate`: собственная находка по baseline

Гейт (`GateEvaluator.Evaluate`) обрабатывает F1 иначе, чем любое другое правило снимка: проходя по находкам снимка, он **пропускает каждую F1 до проверки `knownFindings`**, так что находка со свидетельствами в `gate-report.json` не попадает никогда. Затем он синтезирует свою:

```text
если baseline.ratchets.testsPastContract отсутствует (null):
    F1, класс trigger, сообщение «new ratchet F1»            → вердикт triggers
иначе если current.testsPastContract > baseline.ratchets.testsPastContract:
    F1, класс ratchet, «testsPastContract {cur} > baseline {bas}» → вердикт block
иначе:
    тишина
```

Сравнение строгое и без допуска: равенство — тишина, любое увеличение в последнем знаке — `block`. Уменьшение доли ничего не пишет и baseline не «подтягивает». Отсутствующий ключ даёт `trigger` даже при текущей доле `0`: смысл сигнала — «порог ещё не зафиксирован, запустите `baseline`». Команда `arch-lens baseline` всегда записывает текущее значение, поэтому ключ отсутствует только в файлах, написанных вручную.

## Пример

Юнит-тест `Mix_one_past_and_one_contract_is_half`: `M.Tests::T.Specs` ссылается на `M.Contracts::C.IFoo` (вес `1`, к контракту) и на `M::M.Foo` (вес `1`, мимо контракта). `total = 2`, `past = 1`, доля `0.5`; на `map` появляется `F1 | trigger | | | testsPastContract 0.5 | M.Tests::T.Specs → M::M.Foo (call:1)`. Тест `Weights_sum_in_the_fraction`: вес `1` к контракту и `3` к реализации дают `0.75`. Тест `Test_to_host_edges_are_ignored_in_numerator_and_denominator`: ребро веса `100` из теста в `App.Host` долю не меняет. Тест `F1_map_evidence_is_heaviest_past_edges_capped_at_ten`: двенадцать рёбер весами от `1` до `12` дают десять свидетельств, начиная с самого тяжёлого.

Гейт: тест `TestsPastContract_above_baseline_is_block_F1` — доля `0.3` при пороге `0.2` даёт `ratchet` с сообщением `testsPastContract 0.3 > baseline 0.2` и вердикт `block`. Тест `TestsPastContract_below_baseline_is_pass_without_auto_tighten` — доля `0.2` при пороге `0.3` даёт `pass` без находок, и порог остаётся `0.3`. Тесты `Missing_baseline_F1_is_triggers_not_block` и `Missing_baseline_F1_triggers_when_current_is_zero` — при отсутствующем ключе гейт выдаёт `trigger` `new ratchet F1` и при доле `0.5`, и при доле `0`.

Как рёбра выглядят в коде:

```csharp
// Account.Tests (роль test)
public sealed class LoginTests
{
    private readonly IAuth _auth;                           // → Account.Contracts::IAuth: fieldType 1 — в total, не past
    private readonly AccountService _svc;                   // → Account::AccountService: fieldType 1 — past

    public LoginTests()
    {
        _auth = new FakeAuth();                             // FakeAuth лежит в тестовой сборке: ребро test → test не считается
        _svc = new AccountService(_auth);                   // → Account::AccountService: call 1 — past
    }

    [Fact] public void Logs_in() => _svc.Login("u", "p");   // → Account::AccountService: call 1 — past
}
// total = 1 + 1 + 2 = 4, past = 3 → testsPastContract = 0.75
// Инициализаторы полей экстрактор не обходит: `new` даёт ребро call только внутри тела метода, конструктора или аксессора.
```

## Где смотреть в отчёте

- **Вкладка Findings отчёта `map`** — строка `F1 | trigger | | | testsPastContract 0.37 | …` с до десяти свидетельствами вида `From → To (kind:weight)`. Это единственное место, где перечислены конкретные пары «тест → реализация».
- **Вкладка Metrics, чип `testsPastContract`** — доля в процентах с округлением до двух знаков (`37.04%`); в `metrics.json` то же число лежит как доля (`0.3704…`).
- **`gate-report.json`** — объект `"rule": "F1"` с `"class": "trigger"` и `"message": "new ratchet F1"` либо с `"class": "ratchet"` и сообщением сравнения; `fromModule`, `toModule` и `evidence` пусты.
- **`baseline.json`, ключ `ratchets.testsPastContract`** — действующий порог.

## Как исправить

1. Откройте свидетельства F1 в отчёте `map`: каждая строка называет тестовый тип и тип реализации, к которому он обращается, с весом. Начните с самых тяжёлых.
2. Переведите тест на контракт: работайте через интерфейс из `X.Contracts`, а реализацию получайте через один тип-сборщик в тестовой инфраструктуре, а не через `new` конкретного класса в каждом тесте. Один сборщик, знающий о реализации, даёт одно ребро мимо контракта вместо десятков.
3. Если тест намеренно проверяет внутренний алгоритм, спросите, не должен ли этот алгоритм стать портом контракта; если нет — оставьте тест, помня, что он входит в долю.
4. Когда доля снизилась, зафиксируйте улучшение командой `arch-lens baseline` и закоммитьте `baseline.json`: автоматически порог не подтягивается.

**Когда допустимо принять.** Рост доли бывает оправдан — например, при появлении нового модуля, который пока тестируется через реализацию. Единственный способ принять его — осознанно поднять порог командой `arch-lens baseline` и объяснить причину в коммите. Занести отпечаток F1 в `knownFindings` бесполезно: гейт F1 снимка отбрасывает всегда, а собственную находку по этому списку не проверяет. Сообщение `new ratchet F1` исчезает после первого же `arch-lens baseline`, записавшего ключ.

## Чего не делать

- Не удаляйте тесты, чтобы снизить долю: удаление тестов контракта её **повышает**, а удаление тестов реализации оставляет модуль без покрытия и приближает [F2](F2.md).
- Не переназначайте сборки реализации в роль `contract` в `arch-lens.yaml`: доля упадёт, но тесты останутся привязанными к внутренностям, а таблица разрешённых рёбер [A1](A1.md) потеряет смысл.
- Не прогоняйте тесты через `App.Host`, чтобы рёбра исчезли из расчёта: вместе с ними исчезнет признак покрытия, и модуль получит [F2](F2.md).
- Не оставляйте ключ `testsPastContract` отсутствующим «чтобы не блокировало»: `trigger` `new ratchet F1` будет появляться при каждом запуске, а рост доли останется незамеченным.
- Не ждите свидетельств в `gate-report.json`: они есть только у находки `map`.
