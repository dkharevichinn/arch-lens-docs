# D2 — Несвязанные острова типов внутри одного модуля

| Поле | Значение |
|---|---|
| Код | `D2` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `CohesionAnalyzer.Analyze`, вызывается из `StaticMetricsCalculator.Calculate`; считает `CohesionMetrics.Islands` обходом в ширину по неориентированному графу типов модуля |
| Команды | `arch-lens map` (находка снимка: `findings.json`, вкладка Findings) и `arch-lens gate` (проходит в `gate-report.json`, если отпечатка нет в `knownFindings`) |
| Метрика | [cohesion](../metrics/cohesion.md), поле `islands`; таблица Cohesion на вкладке Metrics |
| Порог | только модули с `N >= 4` типов; `islands >= 2` и второй по размеру остров содержит `>= 3` типов; константы `MinTypes` и `MinSecondIsland` зашиты в коде |
| Отпечаток | `ForTypeEdge("D2", module, "", [])` — один на модуль |
| Сообщение | `disconnected islands: {module}` |

## Термины

Понятия [учитываемый модуль](../glossary.md#scored), [ребро между типами](../glossary.md#edge-kinds) и [компонента сильной связности](../glossary.md#scc) определены в словаре; последнее здесь нужно только для контраста.

**Неориентированный граф типов модуля** — граф, узлы которого — все учитываемые типы модуля (из всех его сборок, кроме `host` и `test`), а связи — внутренние рёбра модуля с забытым направлением. Если `A` ссылается на `B`, то в этом графе `A` и `B` просто соседи; вес и вид ребра не важны, рёбра в чужие модули не учитываются.

**Слабосвязная компонента** — максимальное множество типов, в котором от любого типа до любого другого можно дойти по соседям, не обращая внимания на направление стрелок. Слово «слабо» противопоставляет её компоненте **сильной** связности, где требуется путь по стрелкам в обе стороны. Для оценки того, «одна ли это вещь», направление зависимости не важно, поэтому правило пользуется именно слабой связностью. Тип без единого внутреннего ребра образует компоненту из себя одного.

**Остров** (`islands`) — слабосвязная компонента графа типов модуля. Число островов равно числу компонент, включая одиночные типы. **Второй по размеру остров** (`secondLargest`) — компонента, следующая по числу типов за самой большой; если компонента одна, эта величина равна `0`.

## Когда срабатывает

```text
N            = число учитываемых типов модуля
islands      = число слабосвязных компонент неориентированного графа типов модуля
secondLargest = размер второй по величине компоненты (0, если компонента одна)

модуль с N < 4 пропускается: ни строки в таблице Cohesion, ни находки
D2 срабатывает, если islands >= 2 и secondLargest >= 3
```

Смысл порога `3`: одиночный забытый перечислитель или пара вспомогательных типов без связей — не повод считать модуль двумя модулями. А вот вторая группа из трёх и более взаимосвязанных типов — уже самостоятельная фича, которая живёт под чужой крышей. Число островов само по себе не ограничено: модуль из одного большого острова и десяти одиночек даёт `islands = 11`, но D2 молчит.

Обход выполняется в ширину от каждого ещё не посещённого типа в ordinal-порядке идентификаторов; результат — число компонент и их размеры — от порядка не зависит.

D2 и [D1](D1.md) считаются вместе и часто срабатывают парой: модуль из двух островов, как правило, ещё и разрежен. Однако это разные вопросы — D1 спрашивает «сколько связей на тип», D2 — «на сколько несвязанных частей распадается модуль».

## Пример

Юнит-тест `Second_island_of_three_types_is_D2`: модуль `M` из шести типов с рёбрами `T0 → T1`, `T1 → T2`, `T3 → T4`, `T4 → T5`. Получаются две цепочки по три типа, `islands = 2`, `secondLargest = 3`, находка `disconnected islands: M`. Одновременно `R = 4`, `h = 5 / 6 ≈ 0.83`, поэтому в том же снимке будет и `sparse cohesion: M` от D1.

Юнит-тест `Five_plus_isolated_type_is_not_D2`: цепочка `T0 → T1 → T2 → T3 → T4` и одинокий `T5` дают `islands = 2`, но `secondLargest = 1` — находки нет. Тест `Second_island_of_two_types_is_not_D2`: цепочка из трёх и пара из двух дают `secondLargest = 2` — тоже нет. Тест `Directed_intra_edge_is_undirected_for_islands`: цепочка `T0 → T1 → T2 → T3` — один остров, хотя от `T3` по стрелкам никуда не дойти.

Как это выглядит в коде:

```csharp
// модуль Account, сборка Account
internal sealed class LoginHandler   { private readonly SessionStore _sessions; }   // остров 1: fieldType → SessionStore
internal sealed class SessionStore   { public Session Open(string login) => …; }     // остров 1: return → Session
internal sealed class Session        { … }                                            // остров 1

internal sealed class InvoiceBuilder { private readonly TaxTable _taxes; }            // остров 2: fieldType → TaxTable
internal sealed class TaxTable       { public decimal RateFor(Region r) => …; }       // остров 2: parameter → Region
internal sealed class Region         { … }                                            // остров 2
// ни один тип второй группы не упоминает первую: islands = 2, secondLargest = 3 → D2
```

Здесь под именем `Account` живут аутентификация и выставление счетов. Само по себе это может быть незаметно, пока обе группы лежат в одном проекте.

## Где смотреть в отчёте

- **Вкладка Findings** — строка `D2 | trigger | Account | | disconnected islands: Account |`; колонки To и Evidence пусты.
- **Вкладка Metrics, таблица Cohesion** — колонка `islands` по каждому модулю с `N >= 4`. Число `1` означает единый граф, `2` и больше — есть разрывы; сколько типов во втором острове, отчёт не печатает.
- **`metrics.json`** — `cohesion.{module}.islands`.
- **Состав островов** отчёт не выводит. Его восстанавливают по `graph.json`: возьмите рёбра, у которых оба типа принадлежат сборкам модуля, и соберите компоненты. Если пространства имён модуля отображены в отдельные компоненты правилами `rules`, вкладка Matrix покажет пустые клетки между ними.

## Как исправить

D2 — это готовый план разделения: острова уже не связаны, резать между ними ничего не нужно.

1. Определите, какой остров даёт модулю имя, а какой — «квартирант». Обычно у квартиранта другое пространство имён или другая предметная лексика.
2. Вынесите меньший остров в отдельный модуль. Если его типы нужны снаружи, заведите ему контрактную сборку `X.Contracts` и опубликуйте интерфейсы и DTO там; если весь остров используется только внутри — это просто новая сборка реализации нового модуля.
3. Перенесите тесты вместе с типами, иначе новый модуль получит [F2](F2.md), а старый — лишние рёбра из тестов.
4. Если острова должны были быть одной фичей, а разрыв — недоделка, добавьте недостающую настоящую связь (например, обработчик, который действительно пользуется обеими частями), а не заглушку.
5. Повторите `arch-lens map`: у каждого затронутого модуля `islands` должно стать `1` или второй остров — меньше трёх типов.

**Когда допустимо принять.** Модуль `shared` по замыслу состоит из независимых примитивов (деньги, время, идентификаторы), и острова в нём естественны. То же верно для модуля, который намеренно объединяет несколько мелких фич под общим владением команды. Зафиксируйте находку командой `arch-lens baseline`; отпечаток зависит только от имени модуля.

## Чего не делать

- Не добавляйте фиктивный `AccountFacade`, который ссылается на тип из каждого острова, чтобы соединить граф: `islands` станет `1`, а два независимых механизма по-прежнему будут делить один модуль.
- Не игнорируйте D2, потому что D1 уже сработала: D1 говорит, что связей мало, D2 — где именно проходит разрез.
- Не сливайте острова через общий базовый класс или общий «контекст» ради связности: вы получите зависимость, которой не было, и, возможно, тип-«бог» ([E1](E1.md)).
- Не выносите одиночные типы в отдельные модули: порог `3` намеренно не считает их островами, заслуживающими внимания.
