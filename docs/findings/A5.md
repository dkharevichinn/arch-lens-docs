# A5 — Логика в контрактной сборке: конкретный класс или вызов между контрактами

| Поле | Значение |
|---|---|
| Код | `A5` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если нет ни одной находки классов `invariant` и `ratchet` |
| Кто выдаёт | `ContractQualityAnalyzer.Analyze`: два независимых сигнала — `AddConcreteClasses` (конкретный класс в контрактной сборке) и `AddContractCalls` (ребро `call`, оба конца которого лежат в контрактных сборках) |
| Команды | `map` — находка снимка (`findings.json`, вкладка Findings); `gate` — проходит в `gate-report.json`, если отпечатка нет в `knownFindings` |
| Отпечаток | конкретный класс: `ForTypeEdge("A5", typeId, "", [])`; вызов: `ForTypeEdge("A5", fromTypeId, toTypeId, ["call"])` |
| Сообщение | конкретный класс: `concrete class in contract: {typeId}`; вызов: `contract call {fromTypeId} -> {toTypeId}` |

## Термины

**Контрактная сборка** — сборка с ролью `contract` ([сборка, модуль и роль](../glossary.md#module)). Её назначение — описывать форму API модуля: интерфейсы, DTO, события, перечисления. Поведение в ней не живёт: поведение принадлежит реализации.

**Вид типа** (`CodeType.Kind`) — строка, которую экстрактор присваивает каждому типу: `class`, `interface`, `struct`, `enum`, `delegate` или `record`. Записи (`record`, `record struct`, `abstract record`) получают вид `record`, а не `class`, поэтому для A5 запись — не класс. Дополнительно у типа есть флаги `IsAbstract` и `IsStatic`.

**Конкретный класс** в терминах A5 — тип с `Kind == "class"`, у которого `IsAbstract == false` и `IsStatic == false`. Доступность не проверяется: `internal sealed class` в контрактной сборке — тоже конкретный класс.

**Ребро `call`** — вызов метода другого типа или создание его экземпляра (`new`) в теле метода, конструктора или аксессора ([виды рёбер](../glossary.md#edge-kinds)). Внутри контрактной сборки тела есть у методов расширения, статических помощников, членов интерфейса с реализацией по умолчанию, конструкторов и методов записей и структур, свойств с телом аксессора.

## Когда срабатывает

**Сигнал 1 — конкретный класс.** Для каждого типа снимка, чья сборка имеет роль `contract`:

```text
type.Kind == "class" && !type.IsAbstract && !type.IsStatic  →  A5
```

Не срабатывают: интерфейсы, записи, структуры, перечисления, делегаты, статические и абстрактные классы (тесты `Record_in_contract_is_not_A5`, `Static_class_in_contract_is_not_A5`, `Abstract_class_in_contract_is_not_A5`, `Interface_in_contract_is_not_A5`). Конкретный класс в сборке реализации — не A5 (`Concrete_class_in_implementation_is_not_A5`). Находка получает `FromModule` — модуль контракта, `ToModule = null`, пустые свидетельства.

**Сигнал 2 — вызов между контрактами.** Для каждого ребра вида `call`, у которого оба типа найдены, обе сборки есть в каталоге и **обе имеют роль `contract`** — того же модуля или разных — создаётся находка с `FromModule`, `ToModule` и одним свидетельством `from → to (call:N)`. Граф хранит по одному ребру на тройку `(источник, цель, вид)`, поэтому на пару типов приходится одна находка, а `N` — число вызовов.

Что **не** является сигналом 2: вызов из контракта в `shared` (роль цели не `contract`), вызов из контракта в чужую реализацию (это [A2](A2.md), класс `invariant`), вызов из реализации в контракт (`Call_from_impl_to_contract_is_not_A5`). Сигнатурные виды рёбер между контрактами разных модулей — область [A6](A6.md); ребро `call` в A6 не входит (`Contract_call_to_foreign_non_shared_is_not_A6`).

Оба сигнала дают класс `trigger`: гейт не блокируется, но вердикт становится `triggers`, пока отпечаток не окажется в `knownFindings` (тесты `New_A5_fingerprint_is_triggers_not_block`, `Known_A5_fingerprint_is_pass`). Отпечаток сигнала 1 содержит только идентификатор типа и переживает любые изменения внутри класса; отпечаток сигнала 2 фиксирует пару типов и вид `call`, поэтому рост числа вызовов его не меняет.

## Пример

Тест `Concrete_class_in_contract_is_A5`: тип `Account.Contracts::A.Handler` в сборке `Account.Contracts` (роль `contract`, модуль `Account`) даёт находку `From = Account`, `To` пусто, сообщение `concrete class in contract: Account.Contracts::A.Handler`, отпечаток `ForTypeEdge("A5", "Account.Contracts::A.Handler", "", [])`.

```csharp
// Сборка Account.Contracts, роль contract, модуль Account
public sealed class AuthHandler                  // A5: concrete class in contract
{
    public void Login() { }
}
public abstract class AuthBase { }               // не A5: абстрактный
public static class AuthDefaults { }             // не A5: статический
public sealed record LoginRequest(string User);  // не A5: Kind == "record"
public interface IAuth { void Login(LoginRequest request); } // не A5
```

Тест `Call_with_both_ends_contract_is_A5`: `Gameplay.Contracts::G.IScore` вызывает `Account.Contracts::A.IAuth` — находка `From = Gameplay`, `To = Account`, сообщение `contract call Gameplay.Contracts::G.IScore -> Account.Contracts::A.IAuth`, свидетельство `(call:1)`, отпечаток `ForTypeEdge("A5", "Gameplay.Contracts::G.IScore", "Account.Contracts::A.IAuth", ["call"])`. В тесте `Call_within_same_module_contracts_is_A5` оба типа лежат в `Account.Contracts`, и `From = To = Account`.

```csharp
// Сборка Gameplay.Contracts, роль contract, модуль Gameplay
public static class ScoreExtensions              // сам класс не A5: статический
{
    public static void LoginAndScore(this Account.Contracts.IAuth auth)
        => auth.Login(new Account.Contracts.LoginRequest("x"));
    // call в IAuth и call в LoginRequest: две находки A5 «contract call …»;
    // параметр типа IAuth из чужого контракта — ещё и A6
}
```

Тест `Calculator_one_arg_overload_still_applies_defaults` показывает побочный эффект: модуль, единственный тип которого — конкретный класс в контракте, получает не только A5, но и [B8](B8.md) с сообщением `contract not abstract`, потому что доля интерфейсов и абстрактных классов среди типов модуля с контрактом падает ниже `0.5`.

## Где смотреть в отчёте

- **Вкладка Findings отчёта `map`** — для сигнала 1 строка `A5 | trigger | Account |  | concrete class in contract: Account.Contracts::A.Handler |` с пустыми колонками To и Evidence; для сигнала 2 строка `A5 | trigger | Gameplay | Account | contract call … | Gameplay.Contracts::G.IScore → Account.Contracts::A.IAuth (call:1)`.
- **`findings.json`** — те же поля и `fingerprint`.
- **`gate-report.json`** — объект `"rule": "A5"`, `"class": "trigger"`, если отпечатка нет в `knownFindings`; в консоли `verdict=triggers`, код выхода 4.
- **Вкладка Metrics, таблица Contracts** — конкретный класс с публичными членами увеличивает `Surface` своей сборки ([A4](A4.md)); таблица Martin показывает пониженную `abstractness` модуля.

## Как исправить

1. Для конкретного класса определите его природу. Если это носитель данных — сделайте его `record` или `struct`; если это база для реализаций — `abstract class` с объявленным поведением, а не пустышка; если это обработчик, сервис или маппер — вынесите его в сборку реализации, а в контракте оставьте интерфейс.
2. Для вызова между контрактами перенесите тело туда, где ему место: валидацию, маппинг, конвейеры и «удобные» методы расширения — в реализацию модуля, которому принадлежит логика, либо в `shared`, если это действительно общий примитив. Контракт описывает форму, а не граф вызовов.
3. Если метод расширения над чужим контрактом нужен потребителям, он должен жить в сборке потребителя или в реализации владельца контракта, где вызов контракта законен.
4. Запустите `arch-lens map` и проверьте, что строки исчезли; для сигнала 2 убедитесь, что пропали все вызовы между парой типов, а не только часть.

**Когда допустимо принять.** В контрактах законно живут типы, которые по природе являются конкретными классами: собственные исключения (`class AccountException : Exception`) и атрибуты (`class RequiresSessionAttribute : Attribute`). Такие находки принимаются осознанно — командой `arch-lens baseline` или добавлением отпечатка из `findings.json` в `knownFindings`; отпечаток сигнала 1 зависит только от идентификатора типа и остаётся стабильным, пока тип не переименован и не перемещён. Вызов между контрактами принимать не следует: это признак логики в границе, а не оформления.

## Чего не делать

- Не объявляйте класс `abstract` без абстрактных членов только ради тишины A5: класс с поведением всё равно лежит в неправильной сборке.
- Не оставляйте «просто DTO» конкретным классом: сделайте запись. Конкретный класс в контракте притягивает логику, и через полгода он перестаёт быть DTO.
- Не переводите сборку из роли `contract` в `implementation` или `shared` через YAML, чтобы убрать A5: вместе с A5 исчезнут проверки [A1](A1.md), [A2](A2.md), [A4](A4.md) и [A6](A6.md), которые защищают эту границу.
- Не заносите отпечатки A5 в `knownFindings` по умолчанию: список предназначен для осознанных исключений вроде исключений и атрибутов, а не для каждого нового класса.

См. также [A4](A4.md), [A6](A6.md), [A2](A2.md), [B8](B8.md), [contractSurface](../metrics/contractSurface.md).
