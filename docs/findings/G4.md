# G4 — Модули меняются вместе в истории git, но не связаны статическим ребром

| Поле | Значение |
|---|---|
| Код | `G4` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `GitCouplingAnalyzer.Analyze` через `GitCouplingAnalyzer.MaybeMerge`: `ArchLensPipeline` вызывает его после `StaticMetricsCalculator.Calculate` и дописывает находки к находкам снимка (`WithAppendedFindings`) с пересортировкой по отпечатку |
| Команды | `map`, `baseline` и `gate` — только если `gate.coChange.maxCommits > 0` **и** вход является рабочей копией git: путь к решению внутри репозитория либо `graph.json` с параметром `--source <каталог>`, указывающим на рабочую копию. Это находка снимка: она попадает в `findings.json`, на вкладку Findings и проходит фильтр `knownFindings` в гейте |
| Пороги | `gate.coChange.maxCommits` — размер окна истории, по умолчанию `0` (правило выключено); `gate.coChange.minPair` — минимальное число совместных коммитов, по умолчанию `3`; сравнение нестрогое (`count >= minPair`) |
| Отпечаток | `ForTypeEdge("G4", A, B, [])`, где `A < B` по ordinal — пара модулей, пустой список видов |
| Сообщение | `{A} and {B} co-changed {n} times without a static module edge` |
| Поля | `FromModule = A`, `ToModule = B`, `Evidence` пуст |

## Термины

Базовые понятия — [граф модулей](../glossary.md#module-graph), [учитываемый модуль](../glossary.md#scored), [настройки в `arch-lens.yaml`](../glossary.md#yaml), [что глушит `knownFindings`](../glossary.md#known-findings) — определены в словаре. Для G4 нужны ещё три.

**Затронутые модули коммита.** Анализатор читает историю командой `git log --name-only --pretty=format:%H --max-count={maxCommits}` в корне репозитория и получает список путей файлов для каждого коммита. В окно входят все последние `maxCommits` коммитов, в том числе коммиты слияния, для которых `git log` в этом режиме файлов не выводит, — они лишь занимают место в окне. Каждый путь отображается на сборку: для .NET — по ближайшему каталогу вверх по дереву, в котором лежит файл `*.csproj` (имя файла без расширения считается именем сборки; при нескольких берётся первый по ordinal); для снимков других фронтендов — по корням `sourceRoots`, записанным в `graph.json`. Затем сборка отображается на учитываемый модуль. Файлы сборок `host` и `test`, файлы вне проектов (документация, YAML, конвейер) и файлы проектов, которых нет в снимке, ни на какой модуль не отображаются и в подсчёте не участвуют.

**Совместное изменение** (co-change) — коммит, в котором затронуты как минимум два учитываемых модуля. Для каждой пары модулей такого коммита счётчик увеличивается на единицу: коммит с четырьмя затронутыми модулями даёт шесть пар. Счётчик считает коммиты, а не файлы.

**Статическое ребро** — ребро графа модулей `A → B` или `B → A` с весом больше нуля, то есть хотя бы одно упоминание типа одного модуля в типах другого в любом направлении, включая зависимость от контракта. Одного упоминания достаточно, чтобы пара для G4 считалась связанной.

## Когда срабатывает

```text
включено    ⇔ gate.coChange.maxCommits > 0 ∧ вход — рабочая копия git
commits     = последние maxCommits коммитов; c — множество путей коммита
touched(c)  = { модуль(сборка(path)) : path ∈ c, сборка учитываемая }
для каждого c с |touched(c)| >= 2, для каждой пары {A, B} ⊂ touched(c), A < B по ordinal:
  count[A, B] += 1
G4(A, B)    ⇔ count[A, B] >= minPair ∧ weight(A → B) == 0 ∧ weight(B → A) == 0
```

Если какое-то из условий включения не выполнено — `maxCommits` равен нулю, путь не является рабочей копией git, корень репозитория не определён или `git log` завершился ошибкой — анализатор возвращает метрики без изменений, и G4 отсутствует молча: по отчёту нельзя отличить «связей нет» от «правило не работало».

Смысл правила — эволюционная связность. Два модуля, которые раз за разом меняются в одном коммите, но не ссылаются друг на друга, связаны чем-то невидимым для компилятора: продублированной логикой, общим неявным протоколом (таблица базы данных, формат сообщения, строковые константы статусов), двойной записью. Статический граф в таком месте лжёт умолчанием, и правило предлагает сделать связь явной либо устранить её.

Набор находок G4 зависит от окна истории: пара исчезнет сама, когда совместные коммиты выйдут за пределы последних `maxCommits`, и появится, когда наберётся `minPair` новых. Отпечаток привязан к паре модулей, поэтому он стабилен между запусками и нормально ложится в `knownFindings`. Команда `baseline` запишет отпечатки G4 только если сама была запущена с включённым правилом на рабочей копии git.

## Пример

Юнит-тест `Repeated_unconnected_pair_is_G4`: модули реализации `Account` и `Gameplay` без рёбер между ними; три коммита, каждый затрагивает оба модуля; `minPair = 3`. Счётчик пары равен `3`, статических рёбер нет — находка `Account and Gameplay co-changed 3 times without a static module edge` с `FromModule = Account`, `ToModule = Gameplay` и отпечатком `ForTypeEdge("G4", "Account", "Gameplay", [])`. При двух коммитах находки нет. Тесты `Static_edge_suppresses_G4` и `Reverse_static_edge_also_suppresses_G4`: одно ребро `Account → Gameplay` или `Gameplay → Account` с весом `1` глушит правило. Тест `Unordered_pair_is_emitted_with_ordinal_A_before_B`: порядок модулей в коммите не важен, `A` всегда меньше `B` по ordinal.

Тесты про отображение путей: `Test_only_files_do_not_couple_product_modules` — коммит из `tests/Account.Tests/FooTests.cs` и `tests/Gameplay.Tests/BarTests.cs` не затрагивает ни одного учитываемого модуля; `Host_files_do_not_couple_product_modules` — файл `src/App.Host/Program.cs` отброшен, остаётся только `Account`; `Product_files_still_couple_when_a_commit_also_touches_tests` — продуктовые файлы считаются, даже если рядом изменён тест. Тесты `MaxCommits_zero_does_not_read_the_log` и `Missing_git_tree_skips_G4` фиксируют условия включения; `Enabled_co_change_merges_G4_and_re_sorts_findings` — что `maxCommits` передаётся в `git log` как есть и что находки снимка после дописывания снова отсортированы по отпечатку.

Как это выглядит в жизни: модуль `Billing` добавляет новый статус счёта, и в том же коммите правится `Notifications`, где шаблон письма выбирается по строковому имени статуса. Пять из последних пятидесяти коммитов затрагивают оба модуля, статического ребра нет: `Billing and Notifications co-changed 5 times without a static module edge`. Причина — `Notifications` воспроизводит перечисление статусов `Billing` строковыми константами.

```yaml
gate:
  coChange:
    maxCommits: 200   # окно истории; 0 выключает правило
    minPair: 3        # минимум совместных коммитов в окне
```

## Где смотреть в отчёте

- **Вкладка Findings** — строка `G4 | trigger | {A} | {B} | {A} and {B} co-changed {n} times without a static module edge |`; колонка Evidence пуста. Тот же объект в `findings.json`. Строк нет и при отсутствии связей, и при выключенном правиле — проверьте `arch-lens.yaml`.
- **Шапка отчёта, чип `commit`** — заполнен, если рабочая копия git распознана; пустой чип означает, что git не прочитан, и G4 сработать не могла.
- **Вкладка Metrics, таблица Modules** — колонки `Fan-in` и `Fan-out` обоих модулей; статической связи между ними нет по определению находки. В `metrics.json` — раздел [`fanInOut`](../metrics/fanInOut.md).
- **`arch-lens.yaml`** — `gate.coChange.maxCommits` и `gate.coChange.minPair`.
- **`gate-report.json`** — та же находка, если её отпечатка нет в `knownFindings`.

## Как исправить

1. Выясните, что именно меняется вместе: `git log --name-only` по каталогам обоих модулей за окно `maxCommits`. Ищите параллельные перечисления и константы, DTO-близнецы, общую таблицу или формат сообщения, вызовы одного внешнего сервиса.
2. Сделайте связь явной и направленной: модуль-владелец публикует понятие в своём контракте (событие, перечисление, DTO), второй модуль начинает от него зависеть. Появится статическое ребро, G4 замолчит, а правила [A1](A1.md) и [A2](A2.md) проверят, что направление допустимо.
3. Если понятие не принадлежит ни одному из двух модулей, вынесите его в `shared`; рост притяжения общего ядра отслеживает [B9](B9.md).
4. Если модули меняются вместе, потому что одна функция разрезана между ними, перенесите код так, чтобы она жила в одном модуле; на ту же проблему часто указывают [D3](D3.md) и [P1](P1.md).
5. Повторите `arch-lens map`: находка исчезнет сразу после появления статического ребра, а неверно направленная зависимость проявится как A1, A2, [G1](G1.md) или [B1](B1.md).

**Когда допустимо принять.** Два адаптера к одному внешнему API, которые меняются вместе по воле поставщика; пара, попавшая в окно из-за одного массового механического рефакторинга, — такая находка сама выйдет из окна со временем. Принимайте командой `arch-lens baseline`, запущенной с включённым правилом на рабочей копии git: отпечаток пары модулей попадёт в `knownFindings`. Если правило систематически шумит, поднимите `minPair` или сузьте `maxCommits` в `arch-lens.yaml`; выключение (`maxCommits: 0`) — тоже решение, но осознанное.

## Чего не делать

- Не добавляйте фиктивную ссылку на проект или бессмысленное упоминание типа ради статического ребра: G4 замолчит, скрытая связь останется, а неверное направление увидит A1.
- Не задавайте `minPair` так высоко или `maxCommits` так низко, чтобы правило не срабатывало никогда — калибруйте по истории.
- Не путайте G4 с [G3](G3.md): G3 сравнивает два снимка `graph.json` и не читает git, G4 читает git и не сравнивает снимки.
- Не запускайте `baseline` с входом без рабочей копии git, если рассчитываете зафиксировать отпечатки G4: они просто не будут вычислены.
- Не читайте отсутствие строк G4 как отсутствие скрытой связности: правило по умолчанию выключено.
