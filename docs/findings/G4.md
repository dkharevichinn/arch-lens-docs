# G4 — Co-change without a static edge

| Field | Value |
|---|---|
| Code | `G4` |
| Class | `trigger` |
| Analyzer | `GitCouplingAnalyzer` (merged after metrics via `MaybeMerge`) |
| Commands | `map` / `gate` when `gate.coChange.maxCommits > 0` and the input is a **git working tree** (not a bare `graph.json`) |

## When it fires

YAML:

```yaml
gate:
  coChange:
    maxCommits: 0   # 0 = off (default)
    minPair: 3
```

`git log --name-only` for N commits. Paths map to assemblies (csproj walk or `sourceRoots`) then to scored modules. Each commit’s module set: every pair `{A,B}` (A < B Ordinal) increments a counter. G4 if count ≥ `minPair` **and** `ModuleGraph` has **no** edge A→B or B→A.

Fingerprint: `ForTypeEdge("G4", A, B, [])`. Message: `{A} and {B} co-changed {n} times without a static module edge`.

## Example

`Account` and `Gameplay` files land in the same commits 5 times, but there is no static module edge — hidden coupling (copy-paste, dual writes, implicit protocol).

## How to fix

Introduce a real dependency on a **contract**, extract shared, or stop changing them together (split the feature). The goal is to make the static graph match the evolutionary one.

## What not to do

- Do **not** add a dummy project reference to create a static edge.
- Do **not** leave `maxCommits: 0` forever if you wanted this signal; it is off until you opt in.
- Do **not** use G4 as a substitute for [G3](G3.md) snapshot blast radius.

See also [G3](G3.md), [P1](P1.md), [D3](D3.md).
