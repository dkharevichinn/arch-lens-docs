# F2 — Модуль без единого ребра из тестовых сборок

| Поле | Значение |
|---|---|
| Код | `F2` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `TestTopologyAnalyzer.Analyze`, вызывается из `StaticMetricsCalculator.Calculate`; сравнивает множество учитываемых модулей с множеством модулей, в которые ведёт хотя бы одно тестовое ребро |
| Команды | `arch-lens map` (находка снимка: `findings.json`, вкладка Findings) и `arch-lens gate` (проходит в `gate-report.json`, если отпечатка нет в `knownFindings`) |
| Метрика | прямой метрики нет; смежная — [testsPastContract](../metrics/testsPastContract.md), которую считает тот же анализатор |
| Порог | порога нет: срабатывает при полном отсутствии входящих рёбер из сборок с ролью `test`; модуль `shared` не исключается |
| Отпечаток | `ForTypeEdge("F2", module, "", [])` — один на модуль |
| Сообщение | `untested module: {module}` |

## Термины

Понятия [роль сборки](../glossary.md#module), [учитываемый модуль](../glossary.md#scored) и [ребро между типами](../glossary.md#edge-kinds) определены в словаре.

**Тестовое ребро** — ребро любого вида и веса из типа сборки с ролью `test` в тип учитываемого модуля. Роль `test` сборка получает по конвенции (суффиксы `.Tests`, `.UnitTests`, `.IntegrationTests`) или явно в `arch-lens.yaml`; тестовый проект с именем вне конвенции, например `Account.Specs`, получит роль `implementation`, и его рёбра тестовыми не будут.

**Протестированный модуль** (`testedModules`) — модуль, в **любую** сборку которого ведёт хотя бы одно тестовое ребро: в контракт, в реализацию, в инфраструктуру, в UI или в `shared`. Одного ребра достаточно; вес и вид не важны. Обращение теста к контракту модуля делает модуль протестированным и одновременно **не** увеличивает долю [F1](F1.md).

**Непротестированный модуль** — учитываемый модуль с хотя бы одним типом, в который не ведёт ни одно тестовое ребро. Правило измеряет наличие связи, а не покрытие строк: оно ничего не знает о том, сколько тестов и что именно они проверяют.

## Когда срабатывает

```text
scoredModules = модули, у которых есть хотя бы один тип в сборке с ролью, отличной от host и test
testedModules = модули, в типы которых ведёт хотя бы одно ребро из типа сборки с ролью test

F2 для каждого модуля из scoredModules, которого нет в testedModules
```

Рёбра из тестов в другие тестовые сборки и в сборки `host` не учитываются: тест, который поднимает приложение через `App.Host` и работает с модулем только через HTTP или контейнер, статических рёбер в модуль не создаёт, и модуль остаётся непротестированным с точки зрения правила. Принадлежность тестовой сборки модулю по имени значения не имеет: `Billing.Tests` без ссылок на типы `Billing` модуль не спасает, а `Account.Tests`, ссылающийся на `Billing.Contracts`, — спасает.

Находки упорядочены по имени модуля в ordinal-порядке; на каждый модуль — не больше одной.

## Пример

Юнит-тест `Module_with_no_test_inbound_edge_is_F2`: модули `Untested` и `Covered`, тестовая сборка `Covered.Tests` с одним ребром `Covered.Tests::T.Specs → Covered::C.Foo`. Снимок содержит ровно одну находку F2: `untested module: Untested` с `FromModule = Untested`, пустым `ToModule`, отпечатком `ForTypeEdge("F2", "Untested", "", [])` и без свидетельств. Заодно в том же снимке есть F1 со свидетельством, потому что единственное тестовое ребро ведёт в реализацию.

Тест `Module_with_one_test_to_type_edge_is_not_F2`: одного ребра `M.Tests::T.Specs → M::M.Foo` достаточно, чтобы `M` не считался непротестированным. Тест `Test_to_test_edges_are_ignored`: тестовая сборка, ссылающаяся только на собственный вспомогательный тип `M.Tests::T.Helper`, оставляет модуль `M` в списке F2. Тест `Host_and_test_modules_are_not_F2`: решение из сборок `App.Host` и `M.Tests` без учитываемых модулей находок не даёт.

Как это выглядит в коде:

```csharp
// Billing.Tests (роль test) — проект есть, но тесты ходят через хост
public sealed class InvoiceEndpointTests
{
    private readonly TestServer _server = new App.Host.Program().Start();  // → App.Host: ребро в host, не учитывается
    // ни одного упоминания типов Billing, Billing.Contracts или Billing.Infrastructure
}
// Billing не попадает в testedModules → F2 «untested module: Billing»

// достаточно одного типа контракта, чтобы находка исчезла:
public sealed class InvoiceContractTests
{
    private readonly IInvoices _invoices = …;   // → Billing.Contracts::IInvoices: fieldType, Billing протестирован, F1 не растёт
}
```

## Где смотреть в отчёте

- **Вкладка Findings** — строка `F2 | trigger | Billing | | untested module: Billing |`; колонки To и Evidence пусты.
- **Вкладка Metrics, заголовки модулей** — под таблицей Contracts перечислены сборки каждого модуля с ролями; если среди них нет сборки `(test)`, ищите тесты в других модулях или их отсутствие.
- **Вкладка Matrix** — включите флажок роли `test` (по умолчанию роли `host` и `test` выключены): заполненные клетки в строках тестовых компонентов показывают, куда ведут тестовые рёбра. Пустая строка напротив модуля подтверждает F2.
- **`graph.json`** — рёбра с источником в тестовых сборках; по ним можно перечислить `testedModules` вручную.
- **`gate-report.json`** — та же находка при `arch-lens gate`, если отпечатка нет в `knownFindings`.

## Как исправить

1. Заведите тестовую сборку с именем по конвенции (`Billing.Tests`) или пропишите роль `test` в `arch-lens.yaml`, если имя нестандартное.
2. Напишите тесты через **контракт** модуля: работайте с интерфейсами и DTO из `Billing.Contracts`, получая реализацию через сборщик в тестовой инфраструктуре. Так модуль станет протестированным, а доля [F1](F1.md) не вырастет.
3. Для модуля `shared` заведите отдельный небольшой тестовый проект на примитивы: общее ядро используется всеми, и его поведение стоит фиксировать напрямую.
4. Если тесты для модуля уже есть, но лежат в проекте, который инструмент не считает тестовым, исправьте роль, а не пишите новые тесты.
5. Повторите `arch-lens map`: строка F2 для модуля должна исчезнуть.

**Когда допустимо принять.** Модуль из одних сгенерированных или декларативных типов (например, контракты событий без поведения) или модуль, который проверяется только сквозными тестами через `host`, может остаться без статических тестовых рёбер. Зафиксируйте находку командой `arch-lens baseline`; отпечаток зависит только от имени модуля. Для нового модуля принятие имеет смысл лишь на короткий срок — пока пишутся первые тесты.

## Чего не делать

- Не создавайте в тестовой сборке фиктивный тип с полем типа `Billing.Contracts.IInvoices` ради одного ребра: правило замолчит, покрытие не появится, а ревьюер увидит подлог.
- Не принимайте F2 для каждого нового модуля как политику: правило существует именно как напоминание подключить тесты, пока фича не окаменела.
- Не переводите все тесты на сквозной прогон через `App.Host`, чтобы «упростить»: рёбра в `host` не считаются, и все модули разом станут непротестированными для инструмента.
- Не добавляйте тесты через реализацию только чтобы закрыть F2, если есть контракт: закроете F2, но поднимете долю [F1](F1.md) и, возможно, получите `block` на гейте.
- Не путайте F2 с [P3](P3.md): P3 говорит об отсутствии связей с другими **модулями**, F2 — об отсутствии связей из **тестов**; модуль может быть в одном списке и не быть в другом.
