# P3 — Изолированный («мёртвый») модуль без связей в графе модулей

| Поле | Значение |
|---|---|
| Код | `P3` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `SizeBalanceAnalyzer.Analyze`, вызывается из `StaticMetricsCalculator.Calculate`; читает `FanInOut` и `ModuleSize` модуля |
| Команды | `arch-lens map` (находка снимка: `findings.json`, вкладка Findings) и `arch-lens gate` (проходит в `gate-report.json`, если отпечатка нет в `knownFindings`) |
| Метрика | [fanInOut](../metrics/fanInOut.md) (колонки Fan-in и Fan-out таблицы Modules), [moduleSize](../metrics/moduleSize.md) (колонка Types) |
| Порог | `fanIn == 0` и `fanOut == 0` и `types > 0`; модуль `shared` не исключается |
| Отпечаток | `ForTypeEdge("P3", module, "", [])` — один на модуль |
| Сообщение | `dead module: {module}` |

## Термины

Понятия [учитываемый модуль](../glossary.md#scored), [граф модулей](../glossary.md#module-graph) и [fan-in / fan-out](../glossary.md#fan) определены в словаре. Здесь важно помнить, из чего граф модулей **не** строится.

**Fan-in** модуля — число других учитываемых модулей, у которых есть хотя бы одно ребро в его типы; **fan-out** — число учитываемых модулей, в которые ведёт хотя бы одно его ребро. Оба числа считаются по графу модулей, а в этот граф не входят типы сборок с ролями `host` и `test` — ни как источники, ни как цели. Не входят в него и рёбра `binding`, выведенные из регистраций DI.

**Изолированный модуль** — модуль, у которого оба числа равны нулю: ни один учитываемый модуль на него не ссылается, и сам он ни на один не ссылается. Слово «мёртвый» в сообщении означает «мёртвый с точки зрения графа модулей», а не «неиспользуемый в программе»: см. ниже про `host`.

**Почему модуль, нужный только корню композиции, выглядит мёртвым.** Типичный сценарий: `App.Host` регистрирует `ReportScheduler` из модуля `Reporting` в контейнере и запускает его как фоновую службу, а больше никто из модулей `Reporting` не касается. Ребро `App.Host → Reporting` существует в графе типов, но `App.Host` имеет роль `host`, поэтому в граф модулей это ребро не попадает, и fan-in модуля `Reporting` равен нулю. Если при этом `Reporting` сам ни от одного учитываемого модуля не зависит (например, пользуется только BCL и NuGet-пакетами, которые экстрактор отбрасывает как внешние типы), fan-out тоже нулевой — и правило срабатывает, хотя программа модуль использует. Роли `host` и `test` вынесены из графа намеренно: иначе корень композиции связал бы все модули в одну компоненту, и метрики семейства B потеряли бы смысл. Плата за это — P3 на модулях, живущих только благодаря `host`.

## Когда срабатывает

```text
fanIn  = число учитываемых модулей с ребром в module
fanOut = число учитываемых модулей, в которые ведёт ребро из module
types  = ModuleSize[module].Types

P3 срабатывает, если fanIn == 0 и fanOut == 0 и types > 0
```

Условие `types > 0` — защитное: в граф модулей попадают только модули, у которых есть хотя бы один учитываемый тип, поэтому на практике оно выполняется всегда. Модуль `shared` из проверки не исключён: общее ядро, которым никто не пользуется, получает находку наравне с остальными. В решении из единственного учитываемого модуля P3 срабатывает неизбежно — соседей, с которыми можно быть связанным, просто нет.

Изолированным выглядит также модуль, на который ссылаются только тесты (рёбра из `test` в граф не входят), и модуль, который подключается через рефлексию, плагины или регистрацию по строковому имени — таких рёбер экстрактор не видит.

## Пример

Юнит-тест `Isolated_module_with_types_is_P3_including_shared`: два модуля — `Iso` с ролью `implementation` и `Kernel` с ролью `shared`, по одному типу в каждом, рёбер нет. Обе строки таблицы Modules показывают `Fan-in 0`, `Fan-out 0`, и снимок содержит две находки: `dead module: Iso` с отпечатком `ForTypeEdge("P3", "Iso", "", [])` и `dead module: Kernel`. Тест `Connected_module_is_not_P3`: одно ребро `A::A.T → B::B.T` даёт `A` fan-out `1`, а `B` — fan-in `1`, и ни один из них не изолирован.

Сценарий с корнем композиции:

```csharp
// App.Host (роль host)
internal static class Composition
{
    public static void Register(IServiceCollection services)
    {
        var scheduler = new Reporting.ReportScheduler();  // App.Host → Reporting: ребро call есть в графе типов,
        services.AddSingleton(scheduler);                 // но источник — host, в граф модулей оно не входит
    }
}

// Reporting (роль implementation)
public sealed class ReportScheduler : BackgroundService    // BackgroundService — внешний тип, ребра нет
{
    // внутри — только типы Reporting и BCL
}
// fanIn(Reporting) = 0, fanOut(Reporting) = 0, types > 0 → P3 «dead module: Reporting»
```

Достаточно одного настоящего потребителя, чтобы находка исчезла: если `Home` начнёт обращаться к `Reporting.Contracts::IReports`, fan-in станет `1`.

## Где смотреть в отчёте

- **Вкладка Findings** — строка `P3 | trigger | Reporting | | dead module: Reporting |`; колонки To и Evidence пусты.
- **Вкладка Metrics, таблица Modules** — у изолированного модуля `Fan-in 0` и `Fan-out 0` при ненулевом Types. Ниже, в заголовках модулей, видно, из каких сборок он состоит.
- **`metrics.json`** — `fanInOut.{module}.fanIn`, `fanInOut.{module}.fanOut`, `moduleSize.{module}.types`.
- **Вкладка Matrix** — включите флажок роли `host` (по умолчанию роли `host` и `test` выключены): если в строке компонента `host` появляется заполненная клетка в сторону модуля, значит, его использует корень композиции. Переключатель `resolve DI` покажет и рёбра `binding`, которых в графе модулей нет.
- **`gate-report.json`** — та же находка при `arch-lens gate`, если отпечатка нет в `knownFindings`.

## Как исправить

1. Выясните, кто пользуется модулем: поищите его типы в `graph.json` среди целей рёбер из сборок `host` и `test` и в регистрациях DI. Если потребителей нет вообще — модуль мёртв буквально, и его нужно удалить вместе с тестами и регистрациями.
2. Если модуль используют только через `host`, решите, каким он должен быть. Фоновая служба, точка входа, обработчик очереди — нормальные «модули для хоста»; но если у модуля есть контракт, которым никто не пользуется, контракт либо лишний, либо его потребители ещё не написаны.
3. Если модуль — общее ядро (`shared`), которым пока никто не пользуется, либо начните им пользоваться, либо не выделяйте его заранее.
4. Если модуль подключается через рефлексию или плагины, добавьте статическую связь через контракт (интерфейс плагина в `X.Contracts`, реализуемый модулем) — тогда fan-out станет ненулевым и структура станет видна инструменту.
5. Повторите `arch-lens map`: в таблице Modules у модуля должны появиться ненулевые соседи.

**Когда допустимо принять.** Модули, которые по замыслу общаются с миром только через корень композиции (фоновые службы, адаптеры транспорта, инструментальные утилиты), останутся изолированными на этом уровне детализации, и это нормально. Зафиксируйте находку командой `arch-lens baseline` после того, как убедились, что модуль действительно используется; отпечаток зависит только от имени модуля.

## Чего не делать

- Не добавляйте случайную ссылку из первого попавшегося модуля, чтобы «оживить» изолированный: вы получите ребро без смысла и, возможно, [A1](A1.md) или [P1](P1.md) у соседа.
- Не переназначайте `App.Host` в роль `implementation`, чтобы его рёбра попали в граф: корень композиции ссылается на реализации всех модулей, и каждое такое ребро станет находкой [A1](A1.md), а граф модулей — одной большой компонентой.
- Не путайте P3 с соседями: [E2](E2.md) говорит о мёртвом **типе**, [F2](F2.md) — о модуле без **тестов**. Модуль может быть покрыт тестами и при этом изолирован, и наоборот.
- Не удаляйте модуль, не проверив регистрации в `host` и рефлексивные обращения: инструмент видит только статические рёбра.
