# C4 — Один модуль поглотил почти весь прирост типов между снимками

| Поле | Значение |
|---|---|
| Код | `C4` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `SnapshotDiffer.AddC4`, вызывается из `GateEvaluator.Evaluate` только тогда, когда гейту переданы оба снимка — текущий и предыдущий |
| Команды | только `arch-lens gate --baseline baseline.json --against old-graph.json`; команда `map` эту находку не создаёт, на вкладке Findings она не появляется никогда, и `gate` без `--against` её тоже не создаёт |
| Метрика | [moduleSize](../metrics/moduleSize.md) (поле `types`) в двух снимках |
| Порог | `delta >= 5` и `delta / S >= 0.7`, где `S` — сумма положительных приростов по всем модулям; обе константы зашиты в коде |
| Отпечаток | `ForTypeEdge("C4", module, "", [])` — один на модуль; `ToModule` пуст, `Evidence` пуст |
| Сообщение | `dominant type growth: {module}` |

## Термины

**Предыдущий снимок** — файл `graph.json`, записанный более ранним запуском `arch-lens map` и переданный гейту флагом `--against`. Гейт восстанавливает из него полный снимок архитектуры и сравнивает с текущим. Без этого файла все правила разностного семейства — [G1](G1.md), [G2](G2.md), [G3](G3.md), [A8](A8.md) и C4 — не вычисляются.

**Число учитываемых типов модуля** (`ScoredTypeCounts`) — число типов во всех сборках модуля с ролями, отличными от `host` и `test`; это та же величина, что колонка Types таблицы Modules и `moduleSize.{module}.types` в `metrics.json`. Типы считаются так же, как в [C1](C1.md): все именованные типы, включая вложенные, любой доступности.

**Прирост** (`delta`) модуля — разность текущего и предыдущего числа типов. Модуль, которого в предыдущем снимке не было, считается имевшим `0` типов; модуль, который исчез, получает отрицательный прирост.

**Сумма положительных приростов** (`S`, в коде `positiveSum`) — сложенные приросты только тех модулей, которые выросли. Уменьшение других модулей эту сумму не уменьшает.

## Когда срабатывает

```text
currentTypes[m]  = число учитываемых типов модуля m в текущем снимке
previousTypes[m] = то же в снимке из --against (0, если модуля не было)
delta[m]         = currentTypes[m] - previousTypes[m]
S                = Σ delta[m] по модулям с delta[m] > 0

если S == 0, C4 не вычисляется
C4 для модуля m, если delta[m] >= 5 и delta[m] / S >= 0.7
```

Условия читаются так: между двумя снимками система выросла на `S` типов, и не менее семидесяти процентов этого роста — как минимум пять типов — пришлись на один модуль. Оба сравнения нестрогие: прирост ровно `5` при доле ровно `0.7` срабатывает.

Из формулы следует несколько свойств. За один запуск гейта может быть **не больше одной** находки C4: две доли по `0.7` в сумме дали бы больше `S`. Сокращающиеся модули не срабатывают и не влияют на `S`. Новый модуль, появившийся сразу с пятью и более типами, при отсутствии роста в других местах срабатывает всегда (`delta / S = 1`). Если суммарный рост состоит из одного модуля на три типа, `S = 3`, и правило молчит из-за абсолютного порога.

Откуда пороги. Число `5` — абсолютный минимум, без которого любой маленький коммит (два новых класса в одном модуле — это сто процентов роста) давал бы находку; доля `0.7` — граница, за которой рост считается сосредоточенным в одном месте. Это те же константы, что у [P1](P1.md); ни одна из них в `arch-lens.yaml` не выносится.

Находка синтезируется **после** фильтрации находок снимка по `knownFindings`, поэтому её отпечаток в этом списке не проверяется: занести его туда бесполезно. Класс `trigger` означает, что сама по себе она не блокирует: вердикт будет `triggers`, код выхода 4.

## Пример

Юнит-тест `Dominant_module_growth_is_C4`: в предыдущем снимке `Grower` и `Other` имеют по одному типу, в текущем — `8` и `4`.

```text
delta[Grower] = 8 - 1 = 7
delta[Other]  = 4 - 1 = 3
S             = 7 + 3 = 10
Grower: 7 >= 5 и 7 / 10 = 0.7 >= 0.7  → C4 «dominant type growth: Grower»
Other:  3 < 5                          → тишина
```

Тест `Growth_of_four_types_is_not_C4`: `Grower` вырастает с `1` до `5` типов при неизменном `Other`; доля равна `1`, но прирост `4` меньше пяти. Тест `Growth_below_seventy_percent_of_positive_delta_is_not_C4`: приросты `6` и `5` дают `S = 11` и доли `0.55` и `0.45` — ни одна не дотягивает. Тест `New_module_counts_previous_types_as_zero`: новый модуль `New` из пяти типов при неизменном `Other` даёт `5 / 5 = 1` и находку. Тест `Test_and_host_types_do_not_count_toward_C4`: рост тестовой сборки с `1` до `20` типов и сборки `host` с `1` до `20` не даёт ничего, потому что эти роли не учитываются.

Пример из практики: за спринт `Account` вырос с `40` до `80` типов, `Home` — с `40` до `41`. Тогда `S = 41`, доля `Account` равна `40 / 41 ≈ 0.976`, и гейт печатает `dominant type growth: Account`.

## Где смотреть в отчёте

- **Вкладка Findings отчёта `map` строку C4 не покажет никогда**: правило существует только в гейте с `--against`.
- **`gate-report.json`** — объект с `"rule": "C4"`, `"class": "trigger"`, `fromModule` с именем модуля, пустыми `toModule` и `evidence`. В консоли команда печатает `verdict=triggers` (если нет более тяжёлых находок) и `findings=` с общим числом.
- **Два отчёта `map`** — колонка Types таблицы Modules в старом и новом `dsm.html` или поле `moduleSize.{module}.types` в двух файлах `metrics.json`; разность и есть `delta`.
- **Чипы `median types` и `max types`** на вкладке Metrics нового отчёта подсказывают, не стал ли выросший модуль заодно выбросом по [C1](C1.md).

## Как исправить

C4 — не приговор модулю, а вопрос к итерации: почему вся работа легла в одно место?

1. Сверьте прирост с содержанием изменения. Если в модуль добавили типы, которые по смыслу принадлежат другим фичам (обработчики чужих событий, вспомогательные DTO соседей), перенесите их в модули-владельцы — заодно уменьшится вероятность [P1](P1.md) и [D3](D3.md).
2. Если модуль уже большой (проверьте [C1](C1.md) и таблицу Modules), разделите его сейчас, пока новые типы ещё не переплелись со старыми: [D2](D2.md) покажет острова, если они уже есть.
3. Если рост — начало новой фичи, убедитесь, что у неё есть собственный модуль с контрактом, а не «временная папка» внутри соседа.
4. Держите в CI `--against` направленным на `graph.json` последнего релиза или предыдущего успешного прогона, чтобы правило видело накопленный, а не покоммитный рост.

**Когда допустимо принять.** Осознанная переработка одного модуля или первый скелет новой фичи закономерно дают одну доминирующую дельту. Поскольку `knownFindings` на C4 не влияет, а класс `trigger` не блокирует, принятие сводится к тому, чтобы отнестись к вердикту `triggers` (код выхода 4) как к пункту ревью и зафиксировать причину в описании изменения. На следующем прогоне с обновлённым `--against` находка исчезнет сама, если рост не продолжится в том же модуле.

## Чего не делать

- Не добавляйте фиктивные типы в другие модули, чтобы увеличить `S` и опустить долю ниже `0.7`: это подмена показателя, которая заодно портит [C1](C1.md), [F2](F2.md) и медиану размеров.
- Не убирайте `--against` из команды гейта, чтобы C4 «не существовало»: вместе с ней исчезнут [G1](G1.md), [G2](G2.md), [G3](G3.md) и [A8](A8.md).
- Не заносите отпечаток C4 в `knownFindings`: гейт его не читает.
- Не дробите один прирост на несколько запусков гейта ради формального прохода: правило измеряет структуру роста, а не скорость коммитов.
