# G3 — Радиус изменений (blast radius): между двумя снимками структурно изменилось слишком много модулей

| Поле | Значение |
|---|---|
| Код | `G3` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `SnapshotDiffer.AddG3`; `GateEvaluator.Evaluate` вызывает `SnapshotDiffer.Diff` только когда есть и текущий, и предыдущий снимок |
| Команды | только `arch-lens gate --baseline baseline.json --against old-graph.json`; без `--against` не выдаётся никогда; команды `map` и `diff` её не создают, на вкладке Findings она не появляется |
| Порог | `gate.blastRadiusThreshold` в `arch-lens.yaml`, по умолчанию `4`; сравнение строгое (`n > threshold`) |
| Отпечаток | `ForTypeEdge("G3", "", "", [])` — один на весь репозиторий; `FromModule`, `ToModule` и `Evidence` пусты |
| Сообщение | `blast radius {n} exceeds threshold {threshold}` |

## Термины

Базовые понятия — [сборка, модуль и роль](../glossary.md#module), [учитываемый модуль](../glossary.md#scored), [идентификатор типа](../glossary.md#type-id), [снимок и команды](../glossary.md#commands) — определены в словаре. Для G3 нужны ещё два.

**Состояние модуля** (`ModuleState`) — два множества: идентификаторы типов модуля из учитываемых сборок (типы `Account.Tests` в состояние модуля `Account` не входят) и множество модулей, от которых он зависит (`Outgoing`: модуль `B` входит в него, если есть хотя бы одна межмодульная пара типов из `A` в `B`). Веса рёбер, виды рёбер, число рёбер, строки кода, члены типов и публичный API в состояние **не входят**.

**Радиус изменений (blast radius)** — число учитываемых модулей, у которых состояние в текущем снимке отличается от состояния в снимке из `--against`. Это разность двух снимков `graph.json`, а не история git: G3 ничего не знает о коммитах, файлах и авторах. Правило, которое читает историю git, — [G4](G4.md).

Модуль считается изменившимся, если изменилось множество его типов (тип добавлен, удалён или переименован — переименование пространства имён меняет идентификаторы всех типов) **или** множество модулей, от которых он зависит (появилось первое ребро в новый модуль или исчезло последнее ребро в старый). Модуль считается изменившимся и тогда, когда он есть только в одном из снимков: новый модуль сравнивается с пустым состоянием, удалённый — тоже. Что **не** считается: правка тела метода, добавление члена в существующий тип, новое ребро в модуль, от которого уже была зависимость, изменение веса или вида ребра. Входящие рёбра модуль не меняют: если пять модулей начали зависеть от `shared`, изменились эти пять, а не `shared`.

## Когда срабатывает

```text
TypeIds(M)  = { id типов M из учитываемых сборок }
Outgoing(M) = { N : есть межмодульная пара типов из M в N }
modules     = модули текущего снимка ∪ модули снимка из --against
n           = | { M ∈ modules : TypeIds_cur(M) ≠ TypeIds_prev(M) ∨ Outgoing_cur(M) ≠ Outgoing_prev(M) } |
G3          ⇔ n > gate.blastRadiusThreshold
```

Сравнение строгое: при пороге `4` четыре изменившихся модуля — тишина, пять — находка. Находка одна на весь отчёт, список модулей в ней не приводится.

Смысл правила: изменение, которое структурно затрагивает много модулей сразу, — это либо сквозной рефакторинг (переименование, переход на новый общий примитив), либо признак того, что границы модулей не совпадают с природой изменений: одна задача требует правки в пяти местах. И то и другое — предмет ревью, поэтому класс `trigger`.

Находка синтезируется гейтом после фильтрации по `knownFindings`, поэтому этот список на неё не влияет. Она исчезает, когда снимок в `--against` обновляется: после слияния изменения и публикации нового эталонного `graph.json` разность становится нулевой. Чем старше эталонный снимок, тем больше в нём накопленных различий и тем выше `n` — сравнивать надо со снимком основной ветки, а не с произвольным старым.

## Пример

Юнит-тест `Blast_radius_is_G3_only_when_count_strictly_exceeds_threshold`: шесть модулей — `SharedKernel` с ролью `shared` и модули реализации `A`, `B`, `C`, `D`, `E` — в предыдущем снимке не связаны. В текущем первые `k` модулей получают ребро в `SharedKernel`: их множество `Outgoing` меняется с пустого на `{SharedKernel}`, множества типов не меняются, состояние самого `SharedKernel` тоже не меняется, потому что входящие рёбра не считаются. При `k = 4` и пороге `4` находки нет; при `k = 5` — находка с сообщением `blast radius 5 exceeds threshold 4` и отпечатком `ForTypeEdge("G3", "", "", [])`; при пороге `9` — снова тишина.

Два примера из практики. Переименование корневого пространства имён `Company.Product.*` в `Product.*` меняет идентификаторы всех типов: изменившимся окажется каждый учитываемый модуль, и `n` будет равно числу модулей. Наоборот, введение примитива `UserId` в `shared` и его использование в шести модулях, которые **уже** зависели от `shared`, меняет только состояние `shared` (новый тип): `n = 1`, G3 молчит, хотя файлов затронуто много. Если же три из шести модулей раньше от `shared` не зависели, `n = 4` — ровно порог, всё ещё тишина; четыре новых зависимости — находка.

## Где смотреть в отчёте

- **`gate-report.json`** — единственное место: объект с `"rule": "G3"`, `"class": "trigger"`, пустыми `fromModule`, `toModule`, `evidence` и сообщением с числами `n` и порогом. В консоли — `verdict=triggers`, если ничего не блокирует.
- **Какие модули изменились**, в находке не указано. Сравните два снимка: на вкладке Metrics таблицы Modules (колонка `Types`) и в `metrics.json` разделы [`moduleSize`](../metrics/moduleSize.md) и [`fanInOut`](../metrics/fanInOut.md) (`fanOut`). Разные числа доказывают изменение; равные числа его не исключают — переименование сохраняет число типов, замена одной зависимости другой сохраняет `fanOut`. Точный ответ дают `types` и `edges` двух файлов `graph.json`.
- **`arch-lens.yaml`, ключ `gate.blastRadiusThreshold`** — действующий порог.

## Как исправить

1. Разберитесь, что именно изменилось структурно: переименования и переносы типов или новые межмодульные зависимости. Для этого нужны оба `graph.json`.
2. Если одна прикладная задача потребовала правок в пяти и более модулях, проверьте, не размазано ли понятие по модулям: подсказки дают [D3](D3.md) (тип живёт в чужом сообществе), [P1](P1.md) (модуль тянется к соседу) и [C4](C4.md) (рост сосредоточен в одном модуле). Возможно, границу модуля нужно передвинуть.
3. Разделите изменение на самостоятельные шаги: сначала общий примитив в `shared`, затем переход модулей по одному или по нескольку за шаг. После каждого слияния эталонный снимок обновляется, и следующий шаг сравнивается уже с ним.
4. Сквозной рефакторинг (переименование пространства имён, смена конвенции) выполняйте отдельным изменением без прикладной логики, чтобы ревью могло принять его G3 осознанно.
5. Если команда систематически и обоснованно меняет больше четырёх модулей за раз (модули мелкие, изменений много), поднимите `gate.blastRadiusThreshold` в `arch-lens.yaml` после калибровки по истории — не как первую реакцию на находку.

**Когда допустимо принять.** Осознанный сквозной рефакторинг и запланированный переход на общий примитив — законные причины. Заносить что-либо в `baseline.json` не нужно и бесполезно: G3 не читает `knownFindings`, а `ratchet`-порога у неё нет. Достаточно зафиксировать решение в описании изменения; после слияния и обновления эталонного `graph.json` находка исчезнет. Постоянное изменение порога оформляйте правкой `arch-lens.yaml` с объяснением в коммите.

## Чего не делать

- Не ставьте `gate.blastRadiusThreshold` заведомо недостижимым: правило перестанет что-либо измерять.
- Не путайте радиус изменений с числом затронутых файлов или строк: G3 считает модули с изменённым множеством типов или зависимостей, и большой diff в одном модуле даёт `n = 1`.
- Не дробите изменение на части формально, оставляя систему между ними в противоречивом состоянии: дробление помогает, когда каждый шаг самостоятелен и собирается.
- Не запускайте гейт без `--against`: G3 молчит без предыдущего снимка, и `pass` получается по умолчанию.
- Не сравнивайте с устаревшим эталонным снимком: накопленные различия не имеют отношения к проверяемому изменению.
