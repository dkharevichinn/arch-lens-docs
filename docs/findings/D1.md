# D1 — Реляционная связность модуля вне интервала [1.5, 4]

| Поле | Значение |
|---|---|
| Код | `D1` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `CohesionAnalyzer.Analyze`, вызывается из `StaticMetricsCalculator.Calculate`; считает `CohesionMetrics.H` по внутренним рёбрам модуля |
| Команды | `arch-lens map` (находка снимка: `findings.json`, вкладка Findings) и `arch-lens gate` (проходит в `gate-report.json`, если отпечатка нет в `knownFindings`) |
| Метрика | [cohesion](../metrics/cohesion.md), поле `h`; таблица Cohesion на вкладке Metrics |
| Порог | только модули с `N >= 4` типов; `h < 1.5` — разреженная связность, `h > 4` — плотная; константы `MinTypes`, `HFloor`, `HCeiling` зашиты в коде |
| Отпечаток | `ForTypeEdge("D1", module, "", [])` — **один и тот же** для разреженного и плотного варианта |
| Сообщение | `sparse cohesion: {module}` или `dense cohesion: {module}` |

## Термины

Понятия [учитываемый модуль](../glossary.md#scored), [ребро между типами](../glossary.md#edge-kinds) и [вес ребра](../glossary.md#weight) определены в словаре.

**Внутреннее ребро модуля** — ребро между двумя типами, которые принадлежат одному и тому же модулю. Сборка при этом может быть разной: вызов из класса в `Account` интерфейса из `Account.Contracts` — внутреннее ребро модуля `Account`. Рёбра в типы других модулей, а также любые рёбра из сборок `host` и `test` внутренними не считаются.

**`N`** — число учитываемых типов модуля во всех его сборках, кроме `host` и `test`. **`R`** — сумма весов всех внутренних рёбер модуля, всех видов вместе: три вызова и два параметра между одной парой типов дают вклад `5`.

**Реляционная связность** (`h`, в отчёте колонка `h`) — величина `(R + 1) / N`: сколько единиц внутренних связей приходится в среднем на один тип модуля. Единица в числителе унаследована от классического определения метрики Relational Cohesion, откуда взят и интервал допустимых значений от `1.5` до `4`: без неё модуль из одного типа без связей имел бы связность `0`, с ней — `1`. Отличие Arch Lens от классики в том, что `R` — это сумма **весов**, а не число пар связанных типов. Поскольку модули меньше четырёх типов не оцениваются, практическое следствие единицы одно: модуль без единого внутреннего ребра получает `h = 1 / N`, а не `0`, и пороги в терминах `R` смещаются на единицу.

**Разреженная связность** (`sparse`) — типы модуля почти не ссылаются друг на друга: перед вами мешок независимых вещей. **Плотная связность** (`dense`) — типы связаны так густо, что модуль похож на один большой класс, разрезанный на файлы.

## Когда срабатывает

```text
N = число учитываемых типов модуля
R = Σ вес(ребро) по рёбрам, у которых оба конца — типы этого модуля
h = (R + 1) / N

модуль с N < 4 пропускается: ни строки в таблице Cohesion, ни находки
D1 sparse: h < 1.5    ⟺ R < 1.5 * N - 1
D1 dense:  h > 4      ⟺ R > 4 * N - 1
```

Сравнения строгие: `h`, равное ровно `1.5` или ровно `4`, находки не даёт. Для модуля из четырёх типов это означает: `R <= 4` — разреженный, `R` от `5` до `15` — норма, `R >= 16` — плотный. Для модуля из `40` типов границы — `R < 59` и `R > 159`.

Направление рёбер для `R` не важно, важен вес; при этом каждое ребро считается один раз — по своему весу, а не дважды за оба конца. `R` растёт от каждого упоминания типа своим соседом, поэтому один класс, который вызывает другой сотню раз, способен единолично сделать модуль «плотным».

Отпечаток не содержит тега, в отличие от [C2](C2.md): если модуль перейдёт из разреженного состояния в плотное, отпечаток не изменится, и находка, ранее принятая через `knownFindings`, останется заглушённой.

## Пример

Юнит-тест `Four_unrelated_types_are_below_H_floor`: модуль `M` из четырёх типов без единого внутреннего ребра. `R = 0`, `h = (0 + 1) / 4 = 0.25`, находка `sparse cohesion: M`. В таблице Cohesion у модуля будет `h = 0.25` и `islands = 4`; при этом [D2](D2.md) молчит, потому что второй по размеру остров состоит из одного типа.

Юнит-тест `Four_types_with_R_20_are_above_H_ceiling`: те же четыре типа, но `T0` ссылается на `T1` с весом `20`. `h = 21 / 4 = 5.25`, находка `dense cohesion: M`.

Юнит-тест `H_at_floor_and_ceiling_are_not_D1`: вес `5` даёт `h = 6 / 4 = 1.5` — тишина; вес `15` даёт `h = 16 / 4 = 4` — тишина. Тест `Intra_module_edge_weights_sum_across_kinds`: `call: 7` и `parameter: 5` между одной парой типов складываются в `R = 12`, `h = 3.25`, норма. Тест `Edges_to_other_modules_do_not_count_in_R`: четыре типа, каждый с ребром веса `20` в чужой модуль, дают `R = 0` и `h = 0.25` — внешние связи связности не добавляют.

Как это выглядит в коде:

```csharp
// модуль Billing, N = 6
internal sealed class InvoiceService
{
    private readonly TaxCalculator _tax;                 // fieldType: +1 к R
    public Invoice Build(Order order)                    // parameter Order и return Invoice — оба типа Billing: +2 к R
    {
        var tax = _tax.For(order); _tax.Round(tax);      // два call в TaxCalculator: +2 к R
        return new Invoice(order, tax);                  // call (создание): +1 к R
    }
}
// если остальные пять типов друг на друга не ссылаются: R = 6, h = 7 / 6 ≈ 1.17 → D1 sparse
```

## Где смотреть в отчёте

- **Вкладка Findings** — строка `D1 | trigger | M | | sparse cohesion: M |` или `… | dense cohesion: M |`; колонки To и Evidence пусты.
- **Вкладка Metrics, таблица Cohesion** — колонки `h` и `islands` по каждому модулю с `N >= 4`; дробное `h` печатается с двумя знаками (`0.25`), целое — без дроби. Модули меньше четырёх типов в таблице отсутствуют. Таблица не выводится, если таких модулей нет.
- **`metrics.json`** — `cohesion.{module}.h` и `cohesion.{module}.islands`.
- **Вкладка Matrix** показывает связи между компонентами из `rules`, а не внутри модуля; для разбора внутренних рёбер удобнее `graph.json`, где у каждого ребра есть оба типа, вид и вес.

## Как исправить

1. Для разреженного модуля начните с колонки `islands`: если островов два и больше и [D2](D2.md) сработала, модуль состоит из независимых групп, и каждая крупная группа — кандидат в отдельный модуль. Если остров один, но связей мало, проверьте, не является ли модуль складом DTO и перечислений: такие типы естественно живут в контракте или в `shared`, а не в теле.
2. Для плотного модуля найдите пару типов с самым тяжёлым внутренним ребром (по `graph.json`): чаще всего это тип-«бог» ([E1](E1.md)) и его спутник. Разделите обязанности, уберите сквозные вызовы «каждый с каждым», введите внутренние интерфейсы там, где типы должны знать друг о друге меньше.
3. После переноса типов проверьте `arch-lens map`: `h` каждого затронутого модуля должно оказаться внутри интервала, а [A1](A1.md)/[A2](A2.md) — не появиться.

**Когда допустимо принять.** Модуль общих примитивов (`shared`) или модуль, который по замыслу собирает независимые мелкие вещи, будет разреженным всегда; узкий алгоритмический модуль из нескольких тесно работающих классов может быть плотным по природе. Зафиксируйте находку командой `arch-lens baseline`. Помните, что отпечаток общий для обоих вариантов: принимая «разреженность», вы заодно заглушите будущую «плотность» того же модуля.

## Чего не делать

- Не добавляйте искусственные внутренние вызовы и не создавайте «фасад», который ссылается на все типы модуля, чтобы поднять `h`: связность вырастет на бумаге, острова останутся.
- Не прячьте рёбра через `dynamic`, рефлексию или строковые имена типов, чтобы понизить `h`: экстрактор их не увидит, компилятор — тоже.
- Не сливайте два разреженных модуля ради изменения `N`: сумма двух мешков — мешок побольше.
- Не гоняйте `h` в интервал переносом случайных типов между модулями: интервал — ориентир для ревью, а не цель.
