# E1 — Тип-«бог»: слишком много соседей среди типов решения

| Поле | Значение |
|---|---|
| Код | `E1` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `TypeSmellAnalyzer.AddGodTypes`, вызывается из `StaticMetricsCalculator.Calculate` |
| Команды | `map` (находка снимка: `findings.json`, вкладка Findings), `baseline` (отпечаток попадает в `knownFindings`), `gate` (находка проходит фильтр `knownFindings`) |
| Порог | `max(10, 2 × медиана)`; константа `DegreeFloor = 10` зашита в коде и в `arch-lens.yaml` не настраивается |
| Кап | не больше 20 находок на снимок (`Cap = 20`): по убыванию степени, ничья разрешается по ordinal идентификатора типа |
| Отпечаток | `ForTypeEdge("E1", typeId, "", [])` — идентификатор типа, пустая цель, пустой список видов |
| Сообщение | `god type: {typeId}` |

## Термины

Базовые понятия — [идентификатор типа](../glossary.md#type-id), [виды рёбер между типами](../glossary.md#edge-kinds), [учитываемый модуль](../glossary.md#scored), [медиана](../glossary.md#median) и [ordinal-порядок](../glossary.md#ordinal) — определены в словаре. Для E1 нужны ещё три понятия.

**Учитываемый тип** — тип из сборки, роль которой не `host` и не `test`. Только такие типы могут получить находку E1, и только они считаются соседями: ребро из типа сборки `host` или `test` в учитываемый тип его степень не увеличивает, как и ребро из учитываемого типа в тип сборки `host` или `test`.

**Степень типа** (в коде `score`) — число различных учитываемых типов, у которых есть хотя бы одно ребро **в** данный тип (входящие соседи, множество `incoming`), плюс число различных учитываемых типов, в которые есть хотя бы одно ребро **из** данного типа (исходящие соседи, множество `outgoing`). Считаются соседи, а не рёбра и не веса: двадцать вызовов одного и того же класса — это один сосед; рёбра `call`, `parameter` и `return` к одному и тому же типу — тоже один сосед. Тип, связанный с данным в обе стороны, учитывается дважды: один раз как входящий и один раз как исходящий сосед. Рёбра `binding`, выводимые из регистраций DI, в графе кода отсутствуют и в степень не входят; сама регистрация `services.AddSingleton<IFoo, Foo>()` тоже не порождает рёбер, потому что вызванный метод принадлежит внешней сборке. В отличие от [fan-in и fan-out](../glossary.md#fan) модуля, здесь считаются типы, а не модули, и соседи из своего модуля учитываются наравне с соседями из чужих.

**Порог по медиане.** Абсолютное число соседей ничего не говорит без контекста: десять соседей в решении из сорока типов и десять соседей в решении из четырёх тысяч типов — разные вещи. Поэтому порог привязан к медиане степеней **связанных** типов, то есть типов со степенью больше нуля: она описывает «обычный» тип данного решения. Тип-«бог» — это тип, у которого соседей как минимум вдвое больше, чем у обычного. Нижняя граница `10` защищает от шума в маленьких или слабо связанных графах: при медиане от `1` до `4` удвоение дало бы порог от `2` до `8`, и в «богов» попали бы рядовые сервисы. Типы со степенью `0` из медианы исключены, чтобы множество изолированных DTO и перечислений не тянуло медиану к нулю.

## Когда срабатывает

```text
scoredTypes  = типы сборок с ролью, отличной от host и test
incoming[T]  = { S ∈ scoredTypes : есть ребро S → T любого вида, S ≠ T }
outgoing[T]  = { D ∈ scoredTypes : есть ребро T → D любого вида, D ≠ T }
score(T)     = |incoming[T]| + |outgoing[T]|
median       = медиана множества { score(T) : score(T) > 0 }   (0, если таких типов нет)
threshold    = max(10, 2 × median)
E1 для T     ⇔ score(T) >= threshold
```

Сравнение нестрогое: степень, равная порогу, — уже находка. Кандидаты сортируются по убыванию степени, при равенстве — по ordinal идентификатора типа, и берутся первые двадцать. Поля находки: `FromModule` — модуль типа, `ToModule` пуст, `Evidence` пуст.

У порога по медиане есть два практических следствия. Во-первых, порог один на весь снимок, и он может сдвинуться из-за изменений в другой части решения: если после дробления нескольких крупных классов медиана связанных типов вырастет с `4` до `6`, порог поднимется с `10` до `12`, и тип с одиннадцатью соседями перестанет быть находкой, хотя его никто не трогал. Во-вторых, верно и обратное: массовое появление мелких типов со степенью `1`–`2` опускает медиану, и порог упирается в нижнюю границу `10`.

**Что означает кап 20.** Анализатор никогда не выдаёт больше двадцати находок E1, даже если порог превысили пятьдесят типов. Поэтому двадцать строк E1 в отчёте значат «не меньше двадцати», а не «ровно двадцать». Команда `baseline` записывает в `knownFindings` отпечатки только видимых двадцати; когда один из них будет исправлен, на его место поднимется двадцать первый тип, отпечатка которого в `knownFindings` нет, и гейт покажет его как новую находку. Это ожидаемое поведение, а не регрессия.

## Пример

Юнит-тест `High_type_degree_is_E1`: тип `M::M.God` в модуле реализации `M`, и десять типов `M::M.N00`…`M::M.N09`, каждый из которых ссылается на него. Степень `God` равна `10` (десять входящих соседей, ни одного исходящего), степень каждого листа — `1`. Положительных степеней одиннадцать: десять единиц и одна десятка; медиана равна `1`, удвоенная медиана — `2`, порог — `max(10, 2) = 10`. Условие `10 >= 10` выполнено: находка `god type: M::M.God`, `FromModule = M`. Тест `Nine_neighbors_is_not_E1` проверяет, что при девяти соседях находки нет.

Тест `Threshold_follows_twice_median_when_that_exceeds_ten` показывает работу медианы. Двенадцать типов `C00`…`C11` образуют кольцо, в котором каждый ссылается на три следующих: у каждого три исходящих и три входящих соседа, степень `6`. Отдельный тип `Hub` собирает двенадцать листьев (степень `12`), каждый лист имеет степень `1`. Положительных степеней 25: двенадцать единиц, двенадцать шестёрок и одна двенадцатка; медиана — тринадцатое значение, `6`; порог — `max(10, 12) = 12`. `Hub` со степенью `12` — находка, типы кольца со степенью `6` — нет. Если бы у `Hub` было одиннадцать листьев, находки не было бы, хотя `11 > 10`.

Тест `Degree_counts_distinct_neighbors_not_weight_or_kinds`: тип `Other` ссылается на `Hot` рёбрами `call` с весом `20` и `parameter` с весом `20`; степень `Hot` равна `1`. Тест `Derived_di_registration_does_not_count_as_E1_degree`: десять регистраций DI, в которых участвует один тип, степени ему не дают. Тест `More_than_twenty_E1_candidates_emits_highest_score_first`: 21 тип со степенями от `10` до `30` при пороге `10` даёт ровно двадцать находок, начиная с самой высокой степени; тип со степенью `10` отсекается капом.

Как это выглядит в коде:

```csharp
// Orders/OrderWorkflow.cs — сборка Orders, роль implementation
internal sealed class OrderWorkflow(
    IOrderRepository orders, IPaymentGateway payments, IInventory inventory,
    IPricing pricing, IDiscounts discounts, INotifier notifier, IAuditLog audit,
    ICalendar calendar, IOrderValidator validator)          // parameter: девять исходящих соседей
{
    public OrderResult Place(PlaceOrder command) { /* … */ } // parameter и return: ещё два соседа
}
// OrderWorkflow вызывают пять обработчиков и два контроллера того же модуля: семь входящих соседей.
// score = 11 + 7 = 18 >= 10 → E1 «god type: Orders::Orders.OrderWorkflow»
```

## Где смотреть в отчёте

- **Вкладка Findings** — строка `E1 | trigger | {модуль} | | god type: {typeId} |`; колонки To и Evidence пусты. Тот же объект лежит в `findings.json`.
- **Степень типа в отчёте не показывается** — ни таблицы, ни чипа для неё нет. Чтобы проверить число, откройте `graph.json`: отберите записи `edges`, у которых `from` или `to` равен идентификатору типа, отбросьте рёбра, второй конец которых лежит в сборке с ролью `host` или `test`, и посчитайте различные идентификаторы на противоположном конце — отдельно для входящих и для исходящих.
- **Вкладка Metrics** к E1 отношения не имеет: чипы `median types` и `max types` считают типы в модулях, а не соседей типа.
- **Вкладка Matrix** показывает компоненты, а не типы, поэтому тип-«бог» на ней не виден; косвенный признак — строка компонента, у которой заполнены почти все клетки в обе стороны.
- **`gate-report.json`** — та же находка, если её отпечатка нет в `knownFindings`.

## Как исправить

1. Определите направление перегруза по `graph.json`: преобладают входящие соседи (тип нужен всем — «универсальный помощник» или фасад) или исходящие (тип знает обо всём — оркестратор).
2. Для оркестратора выделите шаги в отдельные типы с собственными соседями: проверка, расчёт, сохранение, уведомление. У координатора должны остаться только порты шагов, а не все их зависимости.
3. Для «универсального помощника» разделите его по понятиям предметной области: набор статических методов «на все случаи» превращается в несколько связных типов, и каждый потребитель ссылается только на нужный. В `shared` переносите только действительно общие примитивы, иначе вырастет [sharedGravity](../metrics/sharedGravity.md).
4. Спрячьте группу соседей за одним портом, которым владеет сам тип: вместо шести репозиториев — одна единица работы, вместо четырёх уведомителей — один диспетчер. Один порт — один сосед.
5. Повторите `arch-lens map` и убедитесь, что степень опустилась ниже порога, а у новых типов не появилась своя находка E1.

**Когда допустимо принять.** Некоторые типы — узлы по своей природе: сборщик отчёта, который обходит все типы модели, сериализатор всего снимка, внутренний конвейер, который по определению знает все свои шаги. Если дробление не добавляет ясности, зафиксируйте находку командой `arch-lens baseline`: её отпечаток попадёт в `knownFindings`, и гейт перестанет её показывать. Помните, что отпечаток привязан к идентификатору типа — переименование типа или пространства имён возвращает находку, — и что из-за капа baseline фиксирует только видимые двадцать.

## Чего не делать

- Не прячьте зависимости за `object`, `dynamic`, рефлексией или локатором сервисов (`provider.GetRequiredService<T>()` внутри метода): степень упадёт, потому что таких рёбер экстрактор не строит, а связность останется. Заодно тип станет невидимым для [R1](R1.md) и [R2](R2.md).
- Не дробите тип механически на `Foo1` и `Foo2` с тем же набором соседей: каждая половина сохранит высокую степень, а плотный клубок из новых типов увидит [D1](D1.md).
- Не переносите тип в сборку с ролью `host`, чтобы он перестал быть учитываемым: корень композиции не место для логики, и все остальные метрики модуля исказятся.
- Не читайте двадцать строк E1 как «в решении двадцать типов-„богов“» — это нижняя оценка, ограниченная капом.
