# A2 — Контрактная сборка зависит от неконтрактной роли

| Поле | Значение |
|---|---|
| Код | `A2` |
| Класс | `invariant` → вердикт **[block](../gates/block.md)**, код выхода 5 |
| Кто выдаёт | `BoundaryAnalyzer.Analyze` — тот же проход и та же таблица `IsAllowed`, что у [A1](A1.md); код `A2` присваивается, когда роль сборки-источника равна `contract` |
| Команды | `map` — находка снимка (`findings.json`, вкладка Findings); `gate` — проходит в `gate-report.json`, если отпечатка нет в `knownFindings` |
| Отпечаток | `ForTypeEdge("A2", fromTypeId, toTypeId, kinds)` — SHA-256 от `A2\n{тип-источник}\n{тип-цель}\n{виды рёбер}` |
| Сообщение | `{fromModule} contract depends on {toModule} {toRole}`, где `{toRole}` — имя роли цели в JSON-записи: `implementation`, `infrastructure`, `ui`, `host`, `test` или `shared` |

## Термины

**Контрактная сборка** — сборка с ролью `contract` (по конвенции `X.Contracts` или `role: contract` в YAML). Это публичная граница модуля: интерфейсы-порты, DTO, события, перечисления. Смысл границы в том, что потребители зависят только от неё, а она сама не знает ничего о теле модуля. Роли, модули и правила их назначения описаны в словаре: [сборка, модуль и роль](../glossary.md#module).

**Неконтрактная роль** в контексте A2 — любая роль цели, которая не разрешена контракту таблицей `IsAllowed`: `implementation`, `infrastructure`, `ui`, `host`, `test`, а внутри собственного модуля — ещё и `shared`. Разрешены контракту только другие контракты (своего или чужого модуля) и `shared` другого модуля.

**Ребро между типами** и его виды — см. [словарь](../glossary.md#edge-kinds). Для A2 вид ребра не важен: параметр метода, тип свойства, вызов, наследование и атрибут проверяются одинаково; вид влияет только на отпечаток и свидетельство.

**Почему источники `host` и `test` пропускаются, а контракт — нет.** `BoundaryAnalyzer` отбрасывает рёбра из сборок `host` и `test` до проверки таблицы, потому что корень композиции и тесты обязаны видеть реализации. Контракт же — самая строгая роль: он проверяется и снаружи, и внутри модуля, поскольку зависимость контракта от тела делает тело частью публичного API.

## Когда срабатывает

Проход анализатора описан на странице [A1](A1.md): рёбра группируются по паре типов, веса суммируются по видам, затем для пары проверяется таблица разрешений. Часть таблицы, относящаяся к источнику с ролью `contract`, выглядит так:

```text
источник contract, цель в другом модуле:
    contract | shared                          → разрешено
    implementation | infrastructure | ui | host | test → A2
источник contract, цель в том же модуле:
    contract                                   → разрешено
    любая другая роль                          → A2
```

Внутри модуля контракт может ссылаться только на контрактные сборки того же модуля. Отсюда самый частый случай A2: интерфейс из `Gameplay.Contracts` упоминает класс из `Gameplay` — свой же модуль, но тело. Сообщение при этом называет один и тот же модуль дважды: `Gameplay contract depends on Gameplay implementation`. Если YAML привязал к модулю контракта сборку с ролью `shared`, ссылка на неё внутри модуля тоже даст A2 с ролью `shared` в сообщении: разрешение «контракт → `shared`» действует только между разными модулями.

Одна пара типов никогда не даёт одновременно A1 и A2: код правила определяется ролью источника (тест `Same_type_edge_is_never_both_A1_and_A2`). Класс — `invariant`; отпечаток включает оба идентификатора типов и отсортированный набор видов рёбер, поэтому новый вид зависимости между теми же типами создаёт новый отпечаток.

Соседние правила делят с A2 одну область, и их стоит различать:

| Ситуация | Что срабатывает |
|---|---|
| Контракт упоминает **чужой контракт** в вызове (`call`) | A2 молчит, [A5](A5.md) даёт `trigger` «contract call» |
| Контракт упоминает **чужой контракт** в сигнатуре (`parameter`, `return`, `fieldType`, `genericArgument`, `attribute`) | A2 молчит, [A6](A6.md) даёт `trigger` |
| Контракт упоминает **чужую реализацию** в сигнатуре | A2 (`invariant`) **и** [A6](A6.md) (`trigger`) — две находки с разными отпечатками |
| Контракт упоминает **свою реализацию** | только A2 |
| Контракт упоминает `shared` другого модуля | ничего |

Гейт пропускает A2 из снимка, отбрасывая строки с отпечатком из `knownFindings`; при `gate --against` новая нарушающая пара дополнительно даёт [G1](G1.md) `new violating edge`.

## Пример

Тест `Contract_to_foreign_implementation_is_A2`: `Gameplay.Contracts::G.IScore` (роль `contract`, модуль `Gameplay`) вызывает `Account::A.Cache` (роль `implementation`, модуль `Account`). Находка: `From = Gameplay`, `To = Account`, сообщение `Gameplay contract depends on Account implementation`, отпечаток `ForTypeEdge("A2", "Gameplay.Contracts::G.IScore", "Account::A.Cache", ["call"])`, свидетельство `Gameplay.Contracts::G.IScore → Account::A.Cache (call:1)`.

Тест `Contract_to_same_module_implementation_is_A2`: `Gameplay.Contracts::G.IScore → Gameplay::G.Score` даёт `From = To = Gameplay` и сообщение `Gameplay contract depends on Gameplay implementation`.

```csharp
// Сборка Gameplay.Contracts, роль contract, модуль Gameplay
public interface IScore
{
    void Use(Account.TokenCache cache);     // parameter в чужую реализацию: A2 и A6
    Gameplay.ScoreService Current { get; }  // fieldType в реализацию своего модуля: A2
    void Notify(SharedKernel.Email to);     // shared другого модуля: разрешено
    void Bind(Account.Contracts.IAuth auth); // чужой контракт: A2 молчит, A6 отметит
}
```

## Где смотреть в отчёте

- **Вкладка Findings отчёта `map`** — строка `A2 | invariant | Gameplay | Account | Gameplay contract depends on Account implementation | Gameplay.Contracts::G.IScore → Account::A.Cache (call:1)`. Для утечки внутри модуля колонки From и To совпадают.
- Рядом может стоять строка [A6](A6.md) с той же парой типов, но только с сигнатурными видами рёбер: это не дубликат, а второе правило.
- **`findings.json`** — те же поля и `fingerprint`.
- **`gate-report.json`** — объект `"rule": "A2"`, `"class": "invariant"`; в консоли `verdict=block`.
- **Вкладка Metrics** прямого следа не даёт, но если контракт стал зависеть от чужой реализации, а та — от этого контракта, в разделе Cycles появится циклическая компонента и сработает [B1](B1.md).

## Как исправить

1. По свидетельству найдите тип-цель и по сообщению — его роль. Решите, что контракту действительно нужно от этого типа: форма данных или поведение.
2. Если контракту нужен API другого модуля, ссылайтесь на `Y.Contracts`, а не на `Y`. Если нужного типа в чужом контракте нет, попросите владельцев модуля `Y` опубликовать порт или DTO — это их поверхность, и её рост отметит [A4](A4.md).
3. Для утечки внутри модуля уберите из контракта знание о собственном теле: замените класс реализации интерфейсом, который реализация реализует, или DTO, который контракт объявляет сам. Направление зависимости должно быть «реализация → контракт», никогда наоборот.
4. Типы инфраструктуры и UI (сущности EF, HTTP-клиенты, view-model) в сигнатурах контракта заменяйте DTO или интерфейсами из контракта либо примитивами из `shared`.
5. Запустите `arch-lens map` и проверьте, что строка исчезла вместе с парной строкой A6, если она была.

**Когда допустимо принять.** Практически никогда для нового кода: контракт, знающий хранилище или view-model, делает потребителей зависимыми от тела модуля навсегда. Для унаследованного кода первый `arch-lens baseline` заносит существующие отпечатки в `knownFindings`, и находки остаются видимыми на вкладке Findings как признанный долг. Принимать отдельное новое ребро следует только с записью в описании коммита и планом устранения; помните, что появление нового вида ребра между теми же типами вернёт находку.

## Чего не делать

- Не переносите класс реализации в `X.Contracts`, чтобы A2 замолчала: конкретный класс в контракте — это [A5](A5.md), рост поверхности — [A4](A4.md), а потребители получат зависимость от конкретного типа вместо порта.
- Не присваивайте сборке-цели роль `contract` в YAML лишь потому, что на неё ссылается контракт: роль описывает назначение сборки, а не удобство прохождения гейта.
- Не пытайтесь решить вопрос через `[InternalsVisibleTo]`: A2 смотрит на рёбра между типами во время компиляции, а дружба с нетестовой сборкой — отдельное нарушение [A7](A7.md).
- Не прячьте тип за `object`, `dynamic` или сериализованной строкой: связь никуда не исчезает, просто перестаёт быть видна гейту и людям.
- Не вписывайте отпечатки новых A2 в `knownFindings` «пока не разберёмся»: этот список предназначен для долга первого снимка.
