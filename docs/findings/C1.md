# C1 — Модуль-выброс по числу типов

| Поле | Значение |
|---|---|
| Код | `C1` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `SizeBalanceAnalyzer.Analyze`, вызывается из `StaticMetricsCalculator.Calculate`; сравнивает `ModuleSize.Types` модуля с медианой `medianTypes` |
| Команды | `arch-lens map` (находка снимка: попадает в `findings.json` и на вкладку Findings) и `arch-lens gate` (проходит в `gate-report.json`, если её отпечатка нет в `knownFindings`) |
| Метрика | [moduleSize](../metrics/moduleSize.md) (поле `types`), [medianTypes](../metrics/medianTypes.md); чипы `median types` и `max types` на вкладке Metrics |
| Порог | `types >= 20` и `types >= 3 × medianTypes`; обе константы зашиты в коде и в `arch-lens.yaml` не настраиваются |
| Отпечаток | `ForTypeEdge("C1", module, "", [])` — один на модуль; `ToModule` пуст, `Evidence` пуст |
| Сообщение | `size outlier: {module}` |

## Термины

Базовые понятия — [учитываемый модуль](../glossary.md#scored), [роль сборки](../glossary.md#module) и [медиана](../glossary.md#median) — определены в словаре. Для этого правила нужно уточнить три вещи.

**Тип** для Arch Lens — любой именованный тип из исходного кода решения: класс, интерфейс, структура, перечисление, делегат, запись (`record`), а также каждый вложенный тип по отдельности. Типы из сгенерированных файлов и типы из метаданных (BCL, NuGet) не учитываются. Уровень доступности значения не имеет: `internal` и `private` вложенные типы считаются так же, как `public`.

**Размер модуля** (`ModuleSize.Types`, колонка Types таблицы Modules) — число типов во **всех** сборках модуля с ролями, отличными от `host` и `test`: контракт, реализация, инфраструктура, UI и `shared` складываются вместе. Число строк (`Loc`) в этом правиле не участвует, хотя и выводится рядом.

**Медиана числа типов** (`medianTypes`) — центральное значение набора размеров всех учитываемых модулей, включая сам проверяемый модуль. Набор сортируется по возрастанию; при нечётном числе модулей берётся средний элемент, при чётном — среднее арифметическое двух средних. Поэтому чип `median types` может показывать половинное число: для размеров `4, 5, 6, 60` средние элементы — `5` и `6`, медиана — `5.5`. Медиана, в отличие от среднего арифметического, почти не сдвигается одним огромным модулем: тот же набор имеет среднее `18.75`, а медиану всё те же `5.5`. Именно это делает её пригодной для поиска выброса.

## Когда срабатывает

Медиану считает `StaticMetricsCalculator.Calculate` и передаёт в `SizeBalanceAnalyzer.Analyze`, который проверяет оба условия для каждого модуля графа модулей:

```text
types       = ModuleSize[module].Types
medianTypes = Median(types по всем учитываемым модулям, включая сам module)

C1 срабатывает, если types >= 20 и types >= 3 * medianTypes
```

Абсолютный порог `20` отсекает маленькие решения: модуль из 18 типов не станет выбросом, даже если он в десять раз больше медианы. Относительный порог `3 × medianTypes` отсекает большие решения, где двадцать типов — обычный размер. Сравнения нестрогие: при медиане `6` модуль из ровно `20` типов срабатывает (`20 >= 18`), из `19` — нет.

Из определения медианы следует, что в решении из одного или двух учитываемых модулей C1 не срабатывает никогда: медиана двух чисел — их среднее, и ни одно из них не может быть втрое больше этого среднего. Начиная с трёх модулей правило работает как задумано.

Модуль `shared` не исключается ни из медианы, ни из проверки: разросшееся общее ядро получает C1 наравне с остальными.

## Пример

Юнит-тест `Types_at_triple_median_and_twenty_is_C1` фиксирует границу: модуль `Big` из `20` типов при медиане `6` даёт находку с сообщением `size outlier: Big`, потому что `20 >= 20` и `20 >= 18`. Соседний тест `Types_19_at_triple_median_is_not_C1` проверяет, что `19` типов при той же медиане находки не дают: абсолютный порог не пройден.

Пример с расчётом медианы. Четыре учитываемых модуля имеют размеры `Account = 4`, `Home = 5`, `Catalog = 6`, `Legacy = 60`:

```text
отсортировано: 4, 5, 6, 60
medianTypes  = (5 + 6) / 2 = 5.5
3 * 5.5      = 16.5
Legacy: 60 >= 20 и 60 >= 16.5  → C1 на Legacy
Catalog: 6 < 20                → тишина
```

На вкладке Metrics чипы покажут `median types 5.5` и `max types 60`. Если разнести `Legacy` на три модуля по `20` типов, набор станет `4, 5, 6, 20, 20, 20`, медиана вырастет до `13`, порог — до `39`, и ни один модуль не пройдёт относительное условие.

## Где смотреть в отчёте

- **Вкладка Findings** — строка `C1 | trigger | Legacy | | size outlier: Legacy |` с пустыми колонками To и Evidence. Код правила — ссылка на эту страницу.
- **Вкладка Metrics, чипы `median types` и `max types`** — медиана и максимум размеров модулей. Если `max types` меньше `20` или меньше тройной медианы, C1 в этом снимке невозможна.
- **Вкладка Metrics, таблица Modules** — колонка Types по каждому модулю; по ней видно, кто именно выброс и как далеко он от остальных.
- **`metrics.json`** — `moduleSize.{module}.types`, `medianTypes`, `maxTypes`.
- **`gate-report.json`** — та же находка появляется при `arch-lens gate`, если её отпечатка нет в `knownFindings`; вердикт при отсутствии более тяжёлых находок — `triggers`.

## Как исправить

Крупный модуль — не ошибка сам по себе, а место, где чаще всего прячутся несвязанные ответственности. Правило просит проверить, не срослись ли в одном модуле несколько фич.

1. Откройте таблицу Cohesion на вкладке Metrics и посмотрите на `islands` этого модуля. Если островов два и больше, а [D2](D2.md) уже сработала, план разделения готов: каждый остров — кандидат в отдельный модуль.
2. Просмотрите находки [D3](D3.md) с `From`, равным этому модулю: они указывают на типы, которые по своим связям тянутся в чужие модули.
3. Выделите новый модуль по границе фичи, а не по техническому слою: заведите ему собственную контрактную сборку `X.Contracts`, перенесите типы вместе с тестами и проверьте, что не появились [A1](A1.md)/[A2](A2.md) и не возник цикл [B1](B1.md).
4. Повторите `arch-lens map`: размер модуля должен упасть ниже порога, а медиана — сдвинуться вверх, потому что новых модулей стало больше.

**Когда допустимо принять.** Если модуль большой потому, что таков предмет (единое ядро домена, которое нельзя разрезать без искусственных контрактов), находку можно зафиксировать: `arch-lens baseline` занесёт её отпечаток в `knownFindings`, и гейт перестанет её показывать. Отпечаток зависит только от имени модуля, поэтому принятие действует, пока модуль не переименован, — даже если он вырастет ещё вдвое. Чтобы рост принятого модуля не прошёл незамеченным, запускайте гейт с `--against`: правило [C4](C4.md) отдельно следит за тем, кто поглотил прирост типов.

## Чего не делать

- Не режьте модуль на технические слои `Foo.Core`, `Foo.Domain`, `Foo.Application` внутри той же фичи. Каждый кусок станет меньше `20` типов, но части будут зависеть друг от друга по кругу ([B1](B1.md)) или почти весь их исходящий вес пойдёт в одного соседа ([P1](P1.md)).
- Не удаляйте и не сливайте типы ради числа `19`: одни и те же обязанности в меньшем числе классов — это путь к типу-«богу» ([E1](E1.md)).
- Не раздувайте другие модули пустыми типами, чтобы поднять медиану: порог сдвинется, а модуль-выброс останется таким же.
- Не считайте `knownFindings` исправлением: принятая находка — признанный долг, а не закрытый вопрос.
