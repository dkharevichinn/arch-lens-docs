# E3 — Церемониальный интерфейс: одна реализация и не больше одного потребителя

| Поле | Значение |
|---|---|
| Код | `E3` |
| Класс | `trigger` → вердикт **[triggers](../gates/triggers.md)**, код выхода 4, если в отчёте гейта нет находок классов `invariant` и `ratchet` |
| Кто выдаёт | `TypeSmellAnalyzer.AddCeremonialAbstractions`, вызывается из `StaticMetricsCalculator.Calculate` |
| Команды | `map` (находка снимка: `findings.json`, вкладка Findings), `baseline` (отпечаток попадает в `knownFindings`), `gate` (находка проходит фильтр `knownFindings`) |
| Условие | учитываемый интерфейс; ровно одно ребро `implementation` от учитываемого типа; не больше одного другого учитываемого типа-источника; ни одного потребителя из сборки `host` |
| Кап | не больше 20 находок на снимок (`Cap = 20`), по ordinal идентификатора интерфейса, затем реализации |
| Отпечаток | `ForTypeEdge("E3", interfaceTypeId, implTypeId, [])` — интерфейс, реализация, пустой список видов |
| Сообщение | `ceremonial abstraction: {interfaceTypeId} <- {implTypeId}` |

## Термины

Базовые понятия — [учитываемый модуль](../glossary.md#scored), [виды рёбер между типами](../glossary.md#edge-kinds), [идентификатор типа](../glossary.md#type-id) — определены в словаре. Для E3 нужны четыре уточнения.

**Учитываемый интерфейс** — тип с `Kind == "interface"` из сборки, роль которой не `host` и не `test`. Интерфейсы, объявленные в корне композиции или в тестах, кандидатами не становятся (тест `Host_and_test_interfaces_are_not_E3`).

**Ребро `implementation`** экстрактор строит из типа в каждый интерфейс из его списка базовых типов: `class Foo : IFoo` даёт `Foo → IFoo`, а `interface IBar : IFoo` даёт `IBar → IFoo`, так что интерфейс, который расширяет другой интерфейс, для E3 тоже «реализация». Считаются только рёбра `implementation` от **учитываемых** типов: класс из сборки `host`, реализующий интерфейс, реализацией не считается (тест `Host_implementation_does_not_count_as_the_scored_adapter`), как и подделка из тестовой сборки.

**Другой источник** (в коде множество `otherFrom`) — учитываемый тип, у которого есть к интерфейсу хотя бы одно ребро любого вида, **кроме** `implementation`: параметр конструктора или метода, поле, свойство, возвращаемое значение, вызов метода интерфейса, аргумент обобщённого типа. Считаются различные типы, а не рёбра. В это множество попадает и сама реализация, если у неё есть к интерфейсу ещё какие-то рёбра, кроме `implementation`, — например, декоратор, который принимает `IFoo` в конструктор.

**Потребитель из `host`** (в коде флаг `hostConsumer`) — тип сборки с ролью `host` (в этом репозитории это `ArchLens.Host` и `ArchLens.Cli`, роли заданы в `arch-lens.yaml`), у которого есть к интерфейсу ребро вида, отличного от `implementation`. Один такой потребитель полностью глушит E3 независимо от остальных счётчиков. Смысл в том, что интерфейс, который корень композиции получает в конструктор или вызывает напрямую, — это порт модуля наружу, даже если реализация одна. Регистрация `services.AddSingleton<IFoo, Foo>()` в `host` ребра не создаёт (вызванный метод внешний), поэтому сама по себе она потребителем не считается: нужен параметр, поле или вызов.

Тестовые сборки не участвуют ни в одной роли: подделка `FakeFoo : IFoo` в тестах не делает интерфейс «настоящей абстракцией», а использование интерфейса в тестах не считается потреблением (тест `Test_consumer_does_not_count_as_E3_consumer`).

## Когда срабатывает

```text
для каждого учитываемого типа I с Kind == "interface":
  implCount    = число рёбер implementation → I от учитываемых типов
  implId       = источник такого ребра (при implCount == 1 он единственный)
  otherFrom    = { S учитываемый : есть ребро S → I вида ≠ implementation }
  hostConsumer = есть ребро вида ≠ implementation от типа сборки host
E3(I, implId)  ⇔ ¬hostConsumer ∧ implCount == 1 ∧ |otherFrom| <= 1
```

Молчание в трёх случаях: реализаций ноль (она может лежать вне снимка, в `host` или в тестах), реализаций две и больше (настоящий полиморфизм), других учитываемых источников два и больше (интерфейс — общий шов нескольких типов или модулей). Поля находки: `FromModule` — модуль интерфейса, `ToModule` — модуль реализации, `Evidence` пуст. Кандидаты сортируются по ordinal идентификатора интерфейса, затем реализации, и берутся первые двадцать — двадцать строк E3 означают «не меньше двадцати».

Правило ловит частный приём: «на каждый класс — интерфейс», когда абстракция вводится ради привычки или ради подмены в тестах, а не потому, что у неё есть второй потребитель или вторая реализация. Такой интерфейс удваивает поверхность модуля, размывает [контрактную поверхность](../metrics/contractSurface.md) и ничего не изолирует.

## Пример

Юнит-тест `Single_impl_single_consumer_interface_is_E3`: интерфейс `C::C.IFoo` в контрактной сборке `C`, класс `M::M.Foo` реализует его (`implementation`), класс `M::M.Consumer` вызывает его (`call`). `implCount = 1`, `otherFrom = {M::M.Consumer}`, потребителя из `host` нет — находка `ceremonial abstraction: C::C.IFoo <- M::M.Foo` с `FromModule = C` и `ToModule = M`. Тест `One_impl_and_no_other_consumer_is_E3`: без `Consumer` находка остаётся — ноль других источников тоже удовлетворяет условию `<= 1`.

Тесты на молчание: `Zero_implementations_is_not_E3`, `Two_implementations_is_not_E3`, `Two_other_consumers_is_not_E3` (два учитываемых потребителя), `Host_consumer_of_single_impl_interface_is_not_E3` (у `App.Host::H.Runtime` параметр типа `IFoo`), `Cli_host_role_counts_as_E3_consumer` (вызов из `App.Cli::Cli.Program`, сборка с ролью `host`). Тест `E3_cap_is_twenty_by_interface_then_impl_ordinal`: из 21 пары попадают первые двадцать по идентификатору интерфейса.

```csharp
// Account.Contracts — роль contract
public interface IPasswordHasher { string Hash(string raw); }

// Account — роль implementation
internal sealed class Pbkdf2PasswordHasher : IPasswordHasher { /* … */ }     // implementation → IPasswordHasher
internal sealed class RegisterUserHandler(IPasswordHasher hasher) { /* … */ } // parameter → IPasswordHasher

// App.Host — роль host
services.AddSingleton<IPasswordHasher, Pbkdf2PasswordHasher>();              // рёбер не порождает
// → E3 «ceremonial abstraction: Account.Contracts::Account.Contracts.IPasswordHasher <- Account::Account.Pbkdf2PasswordHasher»
```

Достаточно одного изменения, чтобы E3 замолчала: второй учитываемый потребитель (`LoginHandler(IPasswordHasher hasher)`), вторая реализация в продуктовом коде (`Argon2PasswordHasher : IPasswordHasher`) или потребитель в `host` (`Program` вызывает `hasher.Hash(...)`). Подделка `FakePasswordHasher` в `Account.Tests` ничего не меняет.

## Где смотреть в отчёте

- **Вкладка Findings** — строка `E3 | trigger | {модуль интерфейса} | {модуль реализации} | ceremonial abstraction: {interfaceTypeId} <- {implTypeId} |`; колонка Evidence пуста. Тот же объект в `findings.json`.
- **`graph.json`** — записи `edges` с `"to"` равным идентификатору интерфейса: ребро `kind: "implementation"` — реализация; остальные рёбра — потребители, у которых надо посмотреть сборку источника (`host` глушит, `test` не считается).
- **Вкладка Metrics, таблица Contracts** — колонка `Surface` контрактной сборки: церемониальные интерфейсы в контракте раздувают её без пользы.
- **`gate-report.json`** — та же находка, если её отпечатка нет в `knownFindings`.

## Как исправить

1. Ответьте на вопрос, зачем интерфейс существует: для второй реализации, для потребителей в других модулях или для подмены в тестах. Только третий ответ делает его церемониальным.
2. Если интерфейс объявлен в сборке реализации и его единственный потребитель — класс того же модуля, удалите интерфейс и используйте конкретный тип. Тесты, которым нужна подмена, переводите на тестовый двойник конкретного класса или на тестирование через настоящую реализацию.
3. Если интерфейс лежит в контрактной сборке и задуман как порт модуля, дайте ему потребителя: пусть его получает в конструктор корень композиции или тип другого учитываемого модуля. Перенос интерфейса в `*.Contracts` сам по себе E3 не глушит — правило смотрит на рёбра, а не на роль сборки.
4. Если это шов для второго адаптера, который появится позже, — примите находку до появления адаптера, а не создавайте заготовку впрок.
5. Повторите `arch-lens map` и убедитесь, что строка исчезла и не появилась соседняя (порядок в капе мог сдвинуться).

**Когда допустимо принять.** Порт модуля с одной реализацией, у которого пока один потребитель, но который является частью опубликованного контракта; интерфейс, вводимый ради границы тестирования интеграций (файловая система, часы, сеть), если команда сознательно так тестирует; интерфейс, реализация которого выбирается на этапе сборки для разных конфигураций. Зафиксируйте командой `arch-lens baseline`: отпечаток содержит идентификаторы и интерфейса, и реализации, поэтому переименование любого из них или появление второй реализации вместо первой вернёт находку как новую.

## Чего не делать

- Не добавляйте вторую реализацию-пустышку в продуктовый код, чтобы получить `implCount == 2`: контейнер и читатели кода получат лишний тип без смысла.
- Не создавайте неиспользуемый второй класс-потребитель ради `otherFrom.Count == 2` — он сам станет [E2](E2.md).
- Не протаскивайте интерфейс в `Program` параметром «чтобы был потребитель из `host`», если корню композиции он не нужен по существу.
- Не удаляйте интерфейс, если его реализация лежит в другом модуле и именно интерфейс держит зависимость в правильном направлении: замена на конкретный тип даст [A1](A1.md).
- Не считайте каждую находку E3 ошибкой: правило указывает на кандидатов, решение остаётся за архитектором.
