# B4 — Стоимость распространения изменений (`propagationCost`) выросла

| Поле | Значение |
|---|---|
| Код | `B4` |
| Класс | `ratchet` → вердикт **[block](../gates/block.md)**, код выхода 5 |
| Кто выдаёт | `GateEvaluator.AddScalarRatchet("B4", …)`: сравнение `StaticMetrics.PropagationCost` с `baseline.ratchets.propagationCost` |
| Команды | только `arch-lens gate --baseline`; команда `map` эту находку **не** создаёт, и на вкладке Findings она не появляется никогда |
| Метрика | [`propagationCost`](../metrics/propagationCost.md), чип **propagation** на вкладке Metrics (формат `0.000`) |

| Сообщение | `propagationCost {текущее} > baseline {порог}` — дробные числа с точкой, без округления (например, `0.4444444444444444`) |

## Термины

Базовые понятия — [граф модулей](../glossary.md#module-graph), [учитываемый модуль](../glossary.md#scored) и [ratchet](../glossary.md#ratchet) — определены в словаре. Для этого правила нужны ещё два.

**Достижимость.** Модуль `B` достижим из модуля `A`, если по стрелкам графа модулей существует путь `A → … → B` любой длины; каждый модуль достижим сам из себя по пустому пути. Код (`ReachableCount`) обходит граф в ширину от каждого модуля и считает посещённые узлы, включая стартовый. Веса рёбер и их виды не учитываются: важно только, есть ли ребро. Число достижимых модулей называют далее `reach(m)`.

**Стоимость распространения изменений** (`propagationCost`) — доля упорядоченных пар модулей `(A, B)`, в которых `B` достижим из `A`, среди всех `N²` пар, включая пары вида `(A, A)`. Это средняя по модулям доля графа, до которой может «дотянуться» изменение одного модуля, если считать, что изменение зависимости потенциально затрагивает всех, кто от неё зависит прямо или через цепочку. Здесь `N` — число модулей в графе, то есть учитываемых модулей, у которых есть хотя бы один тип.

## Когда срабатывает

Метрика считается в `StaticMetricsCalculator.Propagation`:

```text
reach(m)        = число модулей, достижимых из m по рёбрам графа модулей, включая сам m
propagationCost = Σ_m reach(m) / N²
propagationCost = 0, если N == 0
```

Границы значения объясняются устройством формулы. **Несвязный граф** (ни одного межмодульного ребра) даёт `1/N`: каждый модуль достигает только себя, сумма равна `N`, и `N / N² = 1/N`. Это минимум при данном `N`. Верхняя граница `1` достигается, когда каждый модуль достигает каждого, то есть когда весь граф — одна циклическая компонента; в ациклическом графе всегда есть сток, который достигает только себя, поэтому для него значение строго меньше единицы. Частный случай: решение с единственным учитываемым модулем даёт `1/1 = 1`.

Ещё два свойства важны на практике. Значение зависит от **транзитивного замыкания**, а не от числа рёбер: ребро, которое уже подразумевалось цепочкой (`A → C` при существующих `A → B → C`), не меняет ни одной пары достижимости и не меняет метрику. И значение зависит от `N`: появление изолированного модуля увеличивает знаменатель сильнее числителя и **снижает** метрику, а удаление модуля-листа или мёртвого модуля может её **повысить** без единой новой зависимости.

Гейт добавляет находку ровно при одном условии:

```text
current.PropagationCost > baseline.Ratchets.PropagationCost
```

Сравнение строгое и без допуска: любое увеличение, даже в последнем знаке, — находка класса `ratchet` и вердикт `block`. Отсутствующий ключ читается как `0`, поэтому у репозитория без записанного порога любое положительное значение блокирует. Находка синтезируется после фильтрации по `knownFindings`; список `knownCycles` на неё не влияет. Вернуть `pass` можно только уменьшив число достижимых пар либо осознанно подняв порог командой `arch-lens baseline`.

## Пример

Юнит-тест `B4_propagation_is_reachable_pairs_over_n_squared`: два модуля, ребро `A → B`. `reach(A) = 2` (`A` и `B`), `reach(B) = 1`; сумма `3`, знаменатель `2² = 4`:

```text
propagationCost = 3 / 4 = 0.75
```

Цепочка из четырёх модулей `A → B → C → D`: `4 + 3 + 2 + 1 = 10`, `10 / 16 = 0.625`. Если добавить «сквозные» рёбра `A → C`, `A → D`, `B → D`, значение **не изменится**: все эти пары уже были достижимы через цепочку. Если же замкнуть цикл ребром `D → A`, каждый достигает каждого: `16 / 16 = 1`. Четыре изолированных модуля дают `4 / 16 = 0.25 = 1/N`.

Влияние `N`: граф `A → B` плюс изолированный модуль `C` даёт `(2 + 1 + 1) / 9 = 0.4444…`. Если удалить мёртвый модуль `C` (например, после находки [P3](P3.md)), значение вернётся к `0.75`, и гейт выдаст `propagationCost 0.75 > baseline 0.4444444444444444` при том, что ни одной новой зависимости не появилось.

Для ориентира: `baseline.json` самого репозитория Arch Lens хранит `0.3888888888888889`, то есть `14 / 36` при шести учитываемых модулях; чип показывает это как `0.389`.

## Где смотреть в отчёте

- **Вкладка Findings отчёта `map` строку B4 не покажет никогда.**
- **Вкладка Metrics, чип `propagation`** — значение с тремя знаками после точки (`0.389`); в `metrics.json` под ключом `propagationCost` лежит полное число (`0.3888888888888889`). Сравнивать с `baseline.json` нужно полные числа: чип округлён, а гейт — нет.
- **Вкладка Metrics, раздел Cycles и таблица Modules** — непустой список Cycles означает, что все участники компоненты достигают друг друга; колонка Fan-out показывает прямых соседей, то есть первый шаг достижимости. Само транзитивное замыкание отчёт не выводит.
- **`gate-report.json`** — объект с `"rule": "B4"`, `"class": "ratchet"`, пустыми `fromModule`, `toModule`, `evidence` и сообщением вида `propagationCost 0.75 > baseline 0.4444444444444444`; в консоли `verdict=block`.
- **`baseline.json`, ключ `ratchets.propagationCost`** — действующий порог.
- **Вкладка Matrix** с сортировкой «dependency layers» подходит как подсказка: строки идут в порядке зависимостей компонент, и длинные «лестницы» клеток под диагональю соответствуют длинным цепочкам. Матрица строится по компонентам из `rules`, а не по модулям; см. [отличие DSM от графа модулей](../glossary.md#dsm-vs-modules).

## Как исправить

1. Выясните, какие пары стали достижимыми. Сравните таблицу Modules (колонки Fan-in и Fan-out) и раздел Cycles с предыдущим снимком либо запустите `gate --against old-graph.json`: находка [G1](G1.md) назовёт новое ребро, если оно замкнуло цикл или нарушило границу, а `graph.json` двух снимков покажет остальные новые межмодульные рёбра.
2. Если появился цикл, разберите его как [B1](B1.md): цикл делает всех участников взаимно достижимыми и «склеивает» всё, что было выше и ниже него.
3. Если цикла нет, укоротите цепочки: модуль верхнего слоя должен зависеть от контрактов и `shared`, а не от цепочки реализаций, каждая из которых тянет следующую; портом, которым владеет нижний модуль, можно развернуть ребро и оборвать путь.
4. Не позволяйте одному модулю быть одновременно и общей зависимостью, и потребителем многих модулей: «утилитный» модуль, который ссылается обратно на функциональные модули, делает достижимым почти всё из почти всего.
5. Проверьте результат командой `arch-lens gate`: значение должно стать не больше порога.

**Когда допустимо принять.** Если рост объясняется изменением `N` (удалён мёртвый модуль, два модуля объединены в один) или появлением нового модуля, которому по замыслу нужны несколько других, зафиксируйте новое значение командой `arch-lens baseline` и закоммитьте `baseline.json` вместе с кодом, объяснив причину. Перед этим убедитесь, что раздел Cycles не изменился: рост из-за нового цикла принимать через baseline не следует, его нужно разбирать.

## Чего не делать

- Не добавляйте пустые или изолированные модули, чтобы увеличить `N` и опустить значение ниже порога: достижимость не изменилась, а мёртвый модуль отметит [P3](P3.md).
- Не считайте уменьшение числа рёбер улучшением метрики: пока транзитивное замыкание то же, значение то же.
- Не читайте падение метрики после удаления модуля как архитектурную победу, а рост после удаления — как регресс, не проверив, изменились ли зависимости между оставшимися модулями.
- Не переносите связывающий код в `host`, чтобы убрать рёбра из графа: сборки `host` не учитываются, и зависимость просто перестаёт быть видна.
- Не заносите отпечаток B4 в `knownFindings` и не ищите B4 на вкладке Findings отчёта `map`: правило живёт только в `gate-report.json`.
