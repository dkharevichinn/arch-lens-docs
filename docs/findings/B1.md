# B1 — Циклическая компонента модулей, которой нет в `knownCycles`

| Поле | Значение |
|---|---|
| Код | `B1` |
| Класс | `invariant` → вердикт **[block](../gates/block.md)**, код выхода 5 |
| Кто выдаёт | `GateEvaluator.Evaluate`: обход списка `StaticMetrics.Cycles` (его считает `StaticMetricsCalculator.Calculate` алгоритмом Тарьяна из `StronglyConnectedComponents.Find`) и сравнение каждой компоненты с записями `baseline.knownCycles` по равенству множеств |
| Команды | только `arch-lens gate --baseline`; команда `map` записывает сами циклы в `metrics.json` (ключ `cycles`) и в раздел Cycles вкладки Metrics, но находку B1 **не** создаёт, и на вкладке Findings она не появляется никогда |
| Метрика | [`cycles`](../metrics/cycles.md), раздел **Cycles** на вкладке Metrics |
| Отпечаток | `ForTypeEdge("B1", "A,B", "", [])` — идентификаторы модулей компоненты в ordinal-порядке через запятую без пробела; `FromModule` и `ToModule` пусты, `Evidence` пуст; по одной находке на каждую компоненту |
| Сообщение | `cyclic modules: A, B` — те же идентификаторы через запятую с пробелом |

## Термины

Базовые понятия — [граф модулей](../glossary.md#module-graph), [учитываемый модуль](../glossary.md#scored) и [компонента сильной связности](../glossary.md#scc) — определены в словаре; здесь они раскрыты настолько, чтобы раздел Cycles читался без догадок.

**Компонента сильной связности (SCC)** — это максимальное множество модулей, в котором из каждого модуля можно дойти по стрелкам зависимостей до каждого другого и вернуться обратно. «Максимальное» означает, что к множеству нельзя добавить ни одного модуля, не нарушив взаимную достижимость; поэтому компоненты не пересекаются и однозначно разбивают граф. Если `A` и `B` ссылаются друг на друга, а `B` и `C` — тоже, это не два цикла, а одна компонента `{A, B, C}`: из `A` через `B` достижим `C`, и обратно. Arch Lens не перечисляет отдельные замкнутые маршруты, он сообщает именно компоненты.

**Почему одиночный модуль не считается циклом.** Формально любой одиночный узел образует компоненту размера один: он достижим сам из себя по пустому пути. Но `ModuleGraph.Build` отбрасывает рёбра между типами одного и того же модуля, поэтому петель «модуль в самого себя» в графе не бывает по построению, и компонента размера один ничего не говорит о зависимостях. Поэтому `StaticMetricsCalculator` оставляет в списке `cycles` только компоненты из двух и более модулей (`g.Count >= 2`) — их и называют **циклическими компонентами**.

**`knownCycles`** — раздел `baseline.json`: список списков идентификаторов модулей. Команда `arch-lens baseline` копирует в него текущий список `cycles` целиком (`BaselineFactory.FromMetrics`). Это единственный механизм, который глушит B1.

## Когда срабатывает

Список циклов считается один раз на снимок:

```text
sccs   = StronglyConnectedComponents.Find(graph.Modules, graph.InterEdges)
cycles = компоненты с числом модулей >= 2,
         каждая отсортирована ordinal, список отсортирован по строке join("\0", компонента)
```

Гейт проходит по `current.Cycles` и для каждой компоненты `S` проверяет одно условие:

```text
существует ли K в baseline.knownCycles такая, что множество K равно множеству S
нет → находка B1 класса invariant
```

Из этого следуют четыре практических правила.

1. Сравнение идёт по **множеству**, порядок элементов не важен: запись `["Y", "X"]` в `knownCycles` покрывает компоненту `X, Y` (тест `Known_cycle_matches_set_equality_order_independently`).
2. Совпадение должно быть **точным**. Если известная компонента `{Account, Gameplay}` вросла в `{Account, Gameplay, Home}`, новое множество не равно старому, и B1 срабатывает снова. Верно и обратное: если `{A, B, C}` сократилась до `{A, B}`, гейт тоже выдаст B1, потому что множества `{A, B}` в списке нет. Уменьшение цикла — повод обновить `knownCycles`, а не ошибка инструмента.
3. Находка синтезируется **после** фильтрации по `knownFindings`, поэтому её отпечаток в этом списке не проверяется: занести его туда бесполезно.
4. Класс `invariant` не имеет «допустимого уровня»: одна новая компонента любого размера даёт вердикт `block`, сколько бы других находок ни было.

Отдельного правила для «болтливой пары» модулей нет: два модуля, ссылающиеся друг на друга, — это и есть B1. Компонента из трёх и более модулей при `gate.coreSizeMin` по умолчанию дополнительно порождает находку снимка [B5](B5.md).

### Чем B1 отличается от соседей по семейству

| Правило | Вопрос, на который оно отвечает | Может ли сработать без B1 |
|---|---|---|
| **B1** | Есть ли в графе модулей циклическая компонента, не совпадающая ни с одной записью `knownCycles`? | — |
| [B2](B2.md) | Выросла ли **доля** межмодульного веса внутри циклических компонент? | да: новые ссылки внутри уже принятой компоненты поднимают долю, а B1 молчит |
| [B3](B3.md) | Вырос ли вес рёбер против порядка слоёв? | да: обратное ребро внутри принятой компоненты потяжелело |
| [B5](B5.md) | Достигла ли наибольшая циклическая компонента размера `coreSizeMin`? | да: компонента принята в `knownCycles`, но отпечатка B5 нет в `knownFindings` |
| [R1](R1.md) | Замыкается ли цикл модулей через рёбра `binding` из регистраций DI? | да: рёбра `binding` в граф модулей не входят, статических циклов может не быть вовсе |

## Пример

Юнит-тест `B1_lists_cycle_groups_and_omits_isolated_modules`: три модуля реализации `A`, `B`, `Iso`; рёбра `A → B` и `B → A`; у `Iso` рёбер нет. В `cycles` попадает ровно одна компонента `["A", "B"]`, изолированный модуль в список не входит. Тест `New_cycle_not_in_knownCycles_is_block` проверяет гейт: при `Cycles = [["Y", "X"]]` и пустом `knownCycles` появляется одна находка с отпечатком `ForTypeEdge("B1", "X,Y", "", [])`, сообщением `cyclic modules: X, Y` и вердиктом `block`. Тест `Two_cycle_is_below_default_core_size_min` из `GateEvaluatorTests` показывает соседство с B5: для пары `A ↔ B` гейт выдаёт B1, а B5 отсутствует, потому что порог `coreSizeMin` по умолчанию равен трём.

Пример из кода. Оба ребра ниже ведут в контрактные сборки, поэтому [A1](A1.md) и [A2](A2.md) молчат, но контрактная сборка принадлежит своему модулю, и на уровне модулей замыкается цикл:

```csharp
// Сборка Account (роль implementation, модуль Account)
public sealed class AccountService(Gameplay.Contracts.IScoreboard scoreboard) // ребро Account → Gameplay, вид parameter
{
    // ...
}

// Сборка Gameplay (роль implementation, модуль Gameplay)
public sealed class ScoreService(Account.Contracts.IAccountLookup accounts)   // ребро Gameplay → Account, вид parameter
{
    // ...
}
```

Раздел Cycles покажет строку `Account, Gameplay`; гейт с пустым `knownCycles` выдаст `cyclic modules: Account, Gameplay` и, поскольку доля `tanglePct` при пороге `0` стала положительной, ещё и [B2](B2.md).

## Где смотреть в отчёте

- **Вкладка Findings отчёта `map` строку B1 не покажет никогда**, а чип `findings` в шапке считает только находки снимка. Отсутствие B1 в таблице ничего не говорит о циклах.
- **Вкладка Metrics, раздел Cycles** — список компонент по одной строке (`Account, Gameplay`) или надпись `no module cycles`; в `metrics.json` тот же список лежит под ключом `cycles` как массив массивов. Каждая строка — кандидат на B1, если её нет в `knownCycles`.
- **`gate-report.json`** — объект с `"rule": "B1"`, `"class": "invariant"`, пустыми `fromModule`, `toModule` и `evidence` и сообщением `cyclic modules: Account, Gameplay`; в консоли команда печатает `verdict=block`.
- **`baseline.json`, ключ `knownCycles`** — принятые компоненты.
- **Какие именно рёбра замыкают цикл**, находка не сообщает. Их ищут по строкам [A1](A1.md)/[A2](A2.md) на вкладке Findings (если цикл проходит через тела модулей), по колонкам Fan-in и Fan-out таблицы Modules, а при `gate --against old-graph.json` — по находке [G1](G1.md) `new cycle-forming edge {from} -> {to}`, которая называет конкретную пару типов.
- **Чип `cycles` в шапке отчёта** относится к компонентам матрицы, а не к модулям, и может отличаться от раздела Cycles в обе стороны; см. [отличие DSM от графа модулей](../glossary.md#dsm-vs-modules).

## Как исправить

1. Определите, какое направление лишнее. Обычно один из модулей по смыслу «ниже» (им пользуются, сам он ничем не пользуется), и ребро из него вверх — ошибка. Найдите типы, через которые оно проходит.
2. Если нижний модуль обращается к верхнему ради данных или вызова, инвертируйте зависимость: нижний модуль объявляет порт (интерфейс) в своей контрактной сборке, верхний его реализует, а связывает их `host` через DI. Ребро из нижнего модуля в верхний исчезает из графа модулей; вместо него появляется ребро `binding`, за которым следит [R1](R1.md).
3. Если оба модуля нуждаются в общем понятии (идентификатор, событие, значение), вынесите его в `shared` или в третий модуль, от которого зависят оба. Учтите, что замена ссылки на реализацию ссылкой на контракт того же модуля цикл **не** разрывает: контрактная сборка входит в тот же модуль.
4. Если два модуля действительно одно целое, объедините их в один модуль явно и навсегда (`modules.assemblies[].module` в YAML), а не «на переходный период».
5. Запустите `arch-lens gate`: строка должна исчезнуть из раздела Cycles, а вердикт — вернуться к `pass`.

**Когда допустимо принять.** Если цикл — замороженное наследие с планом разбора, зафиксируйте его командой `arch-lens baseline` (она скопирует все текущие компоненты в `knownCycles`, а все отпечатки находок снимка — в `knownFindings`) либо впишите `["Account", "Gameplay"]` в `knownCycles` вручную и закоммитьте `baseline.json` с объяснением в описании коммита. Принятая компонента остаётся под наблюдением: рост веса внутри неё увидит [B2](B2.md), рост обратных рёбер — [B3](B3.md), а любое изменение её состава снова даст B1.

## Чего не делать

- Не заносите отпечаток B1 в `knownFindings`: гейт его не читает, находка вернётся на следующем запуске.
- Не «сливайте» два зациклившихся модуля в один идентификатор через YAML, оставляя две сборки, которые ссылаются друг на друга: узел графа переименован, компонента исчезла из отчёта, а зависимость в коде осталась.
- Не заменяйте прямую ссылку получением реализации из контейнера без настоящего порта: статический цикл исчезнет, но появится цикл через рёбра `binding`, и его покажет [R1](R1.md).
- Не переносите связывающий код в `host`, чтобы ребро пропало из графа: сборки `host` не учитываются, и такой перенос скрывает зависимость, а не устраняет её.
- Не читайте `no module cycles` как отсутствие циклов вообще: циклы через DI показывает раздел Runtime (DI), а циклы компонент матрицы — чип `cycles` в шапке.
