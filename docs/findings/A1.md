# A1 — Зависимость от чужого модуля в обход его контракта

| Поле | Значение |
|---|---|
| Код | `A1` |
| Класс | `invariant` → вердикт **[block](../gates/block.md)**, код выхода 5 |
| Кто выдаёт | `BoundaryAnalyzer.Analyze`: проверка каждой пары типов по таблице разрешённых ролей `IsAllowed`; код `A1` присваивается, когда роль сборки-источника **не** `contract` (иначе это [A2](A2.md)) |
| Команды | `map` — находка снимка, попадает в `findings.json` и на вкладку Findings; `gate` — проходит в `gate-report.json`, если её отпечатка нет в `knownFindings` |
| Отпечаток | `ForTypeEdge("A1", fromTypeId, toTypeId, kinds)` — SHA-256 от строки `A1\n{тип-источник}\n{тип-цель}\n{виды рёбер через запятую}` |
| Сообщение | `{fromModule} -> {toModule} bypasses the contract` |

## Термины

**Роль сборки** (`AssemblyRole`) — одно из семи значений `contract`, `implementation`, `infrastructure`, `ui`, `shared`, `host`, `test`, которое Arch Lens присваивает каждой сборке решения. Роль берётся из `arch-lens.yaml` (`modules.assemblies[].role`), а без записи выводится из суффикса имени: `.Contracts` даёт `contract`, `.Infrastructure` — `infrastructure`, `.UI` — `ui`, `.Tests`, `.UnitTests` и `.IntegrationTests` — `test`; сборка без известного суффикса получает роль `implementation`. Таблица смыслов ролей — в словаре: [сборка, модуль и роль](../glossary.md#module).

**Модуль** — группа сборок с одним идентификатором. По конвенции `Account`, `Account.Contracts`, `Account.Infrastructure` и `Account.Tests` образуют модуль `Account`: контракт — его публичная граница, реализация и инфраструктура — тело. Правило A1 защищает эту границу: тело модуля может быть видно снаружи только через контракт. Проверяются [рёбра между типами](../glossary.md#edge-kinds), а не ссылки между проектами: одна пара типов даёт одну находку.

**Почему сборки `host` и `test` не проверяются как источники.** Корень композиции по определению ссылается на реализации всех модулей, чтобы зарегистрировать их в контейнере, а тесты обращаются к телу проверяемого модуля напрямую. Если бы их рёбра проверялись, каждый хост и каждый тестовый проект давали бы десятки находок, за которыми терялись бы настоящие нарушения. Поэтому `BoundaryAnalyzer` пропускает ребро, как только видит, что роль сборки-источника равна `host` или `test`. Как **цель** эти роли не освобождены: ребро из учитываемой сборки в тип `host` или `test` — нарушение.

## Когда срабатывает

Анализатор проходит по всем рёбрам между типами снимка. Ребро пропускается, если один из типов отсутствует в графе или его сборки нет в каталоге модулей (тесты `Skips_edge_when_endpoint_type_is_missing`, `Skips_edge_when_assembly_is_unbound`), а также если роль сборки-источника `host` или `test`. Остальные рёбра группируются по паре `(тип-источник, тип-цель)`, веса суммируются по видам (`call: 2`, `fieldType: 1`), затем для пары определяется, лежат ли оба типа в одном модуле, и проверяется таблица `IsAllowed`:

```text
внутри одного модуля:
    источник не contract                       → разрешено всё
    источник contract                          → разрешён только contract (иначе A2)
между разными модулями:
    implementation | infrastructure | ui       → разрешены contract и shared
    contract                                   → разрешены contract и shared (иначе A2)
    shared                                     → разрешён только shared
    host | test                                → не проверяются как источник
```

Если пара не разрешена и роль источника не `contract`, создаётся находка `A1` класса `invariant`. Практически это два случая: реализация, инфраструктура или UI одного модуля ссылается на реализацию, инфраструктуру, UI, `host` или `test` другого модуля; сборка `shared` ссылается на что угодно, кроме другой сборки `shared`, — в том числе на чужой **контракт**. Во втором случае текст `bypasses the contract` условен: сообщение одно для всех вариантов A1.

Находка содержит `FromModule` и `ToModule` (идентификаторы модулей) и одно свидетельство: пару идентификаторов типов с разбивкой веса по видам. Отпечаток включает оба типа и **набор видов** рёбер, но не вес: рост числа вызовов между теми же типами отпечаток не меняет, а появление нового вида (к `call` добавился `fieldType`) даёт новый отпечаток, и находка, ранее занесённая в `knownFindings`, всплывает снова.

Гейт находку не синтезирует, а пропускает из снимка: строка с отпечатком из `knownFindings` отбрасывается, любая другая попадает в `gate-report.json` и, как `invariant`, даёт вердикт `block`. При `gate --against` та же новая пара типов дополнительно порождает [G1](G1.md) с сообщением `new violating edge`, если в `knownFindings` нет ни отпечатка A1, ни отпечатка G1.

## Пример

Тест `Implementation_to_foreign_implementation_is_A1`: сборки `Gameplay` и `Account` — обе роли `implementation`, разные модули; тип `Gameplay::G.Score` дважды вызывает `Account::A.Cache`.

```csharp
// Сборка Gameplay, роль implementation, модуль Gameplay
public sealed class Score
{
    public void Save()
    {
        var cache = new A.Cache();           // call: создание экземпляра тоже даёт ребро call
        cache.Put(this);                     // call: вес ребра call становится 2
    }
}
```

Результат — одна находка: `From = Gameplay`, `To = Account`, сообщение `Gameplay -> Account bypasses the contract`, свидетельство `Gameplay::G.Score → Account::A.Cache (call:2)`, отпечаток `ForTypeEdge("A1", "Gameplay::G.Score", "Account::A.Cache", ["call"])`. Если добавить в `Score` поле типа `A.Cache`, к свидетельству прибавится `fieldType:1`, находка останется одной, но отпечаток изменится, потому что набор видов стал `call,fieldType` (тест `Aggregates_kinds_on_one_type_pair_into_a_single_finding`).

Законная замена — параметр типа `Account.Contracts::A.IAuth` (`Implementation_to_foreign_contract_is_legal`) или `SharedKernel::S.Email` (`Implementation_to_foreign_shared_is_legal`). Другие срабатывания: `SharedKernel::S.Clock → Account::A.Cache` даёт `SharedKernel -> Account bypasses the contract`; `Gameplay.UI::G.View → Account::A.Cache` даёт `Gameplay -> Account bypasses the contract`, потому что сборка `Gameplay.UI` входит в модуль `Gameplay`. Не срабатывают `App.Host → Account` и `Account.Tests → Gameplay` (источник не проверяется) и `Account → Account.Infrastructure` (один модуль).

## Где смотреть в отчёте

- **Вкладка Findings отчёта `map`** — строка `A1 | invariant | Gameplay | Account | Gameplay -> Account bypasses the contract | Gameplay::G.Score → Account::A.Cache (call:2)`. Колонки From и To содержат идентификаторы модулей, колонка Evidence — [идентификаторы типов](../glossary.md#type-id) и веса по видам; код `A1` — ссылка на эту страницу.
- **`findings.json`** — те же поля плюс `fingerprint`; именно эту строку копируют в `knownFindings`, если находку решено принять.
- **`gate-report.json`** — объект с `"rule": "A1"`, `"class": "invariant"`, если отпечатка нет в `knownFindings`; в консоли `verdict=block`.
- **Вкладка Matrix** показывает связь как клетку между **компонентами** из `rules`, а не между модулями, и по умолчанию скрывает роли `host` и `test`; для диагностики опирайтесь на Evidence (см. [отличие DSM от графа модулей](../glossary.md#dsm-vs-modules)).

## Как исправить

1. Возьмите из свидетельства тип-цель и определите, что нужно источнику: поведение (вызов) или данные (тип поля или параметра). Если подходящий интерфейс или DTO уже есть в `Y.Contracts` целевого модуля, замените зависимость на него.
2. Если нужного типа в контракте нет, добавьте в `Y.Contracts` порт или DTO, реализуйте его в `Y` и зарегистрируйте в `host`. Рост поверхности отметит [A4](A4.md), а [A5](A5.md) и [A6](A6.md) проверят, что в контракт не попали логика и чужие типы.
3. Если ребро — регистрация зависимостей или иная композиция, перенесите код в сборку с ролью `host` (в YAML `role: host`).
4. Если две сборки на самом деле составляют один модуль, дайте им общий идентификатор — по конвенции `X` и `X.Contracts` либо через `module:` в YAML; внутри модуля рёбра из неконтрактных источников разрешены.
5. Запустите `arch-lens map` и убедитесь, что строка исчезла. Частичное исправление не помогает: если из пары убрали `call`, но остался `fieldType`, находка сохранится, причём с новым отпечатком.

**Когда допустимо принять.** Для унаследованного кода первый запуск `arch-lens baseline` заносит отпечатки всех текущих находок A1 в `knownFindings`: это признанный долг, который остаётся видимым на вкладке Findings, но не блокирует гейт. Отдельное новое ребро можно принять, вписав его отпечаток из `findings.json` в `knownFindings` и объяснив причину в описании коммита. Отпечаток включает виды рёбер, поэтому ребро нового вида между теми же типами вернёт находку — и это правильно, потому что связь стала шире.

## Чего не делать

- Не добавляйте `[InternalsVisibleTo]`, чтобы реализация видела `internal`-типы соседа: это [A7](A7.md), если сборка-друг не тестовая.
- Не присваивайте сборке-источнику роль `host` ради тишины: роль `host` предназначена для корня композиции, а такая сборка выпадает из графа модулей и всех метрик.
- Не делайте тип-цель `public` и не называйте это контрактом: A1 сравнивает **роли** сборок, а не доступность C#; заодно вырастет счётчик [A3](A3.md).
- Не переносите тело модуля в `Y.Contracts` целиком: поверхность ([A4](A4.md)) взлетит, [A5](A5.md) отметит конкретные классы, а потребители получат зависимость от того, что вчера было реализацией.
- Не объявляйте сборку-цель `shared` только потому, что на неё ссылаются: `shared` — ядро без зависимостей на модули, и ребро из `shared` куда угодно, кроме `shared`, само является A1.
