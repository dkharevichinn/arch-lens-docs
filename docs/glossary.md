# Словарь терминов

На этой странице собраны понятия, без которых страницы правил и метрик читаются как набор лозунгов. Каждое определение соответствует тому, как понятие реализовано в исходном коде Arch Lens (`src/ArchLens.Analysis`, `src/ArchLens.Shared/Models`), а не тому, как его принято трактовать в литературе. Страницы каталога ссылаются сюда по якорям, поэтому названия разделов не следует переименовывать без переноса ссылок.

## Сборка, модуль и роль { #module }

**Сборка** — это проект .NET (одна `*.csproj`, одно имя сборки). Arch Lens работает на уровне сборок и типов, а не файлов и каталогов.

**Роль сборки** (`AssemblyRole`) — одно из семи значений: `contract`, `implementation`, `infrastructure`, `ui`, `shared`, `host`, `test`. Роль определяется так (`ModuleRoleResolver`):

1. Если сборка перечислена в `arch-lens.yaml` в разделе `modules.assemblies`, берётся указанная там роль `role` и, если задано, имя модуля `module`.
2. Иначе, если включены конвенции (`modules.conventions: true`, это значение по умолчанию), роль выводится из суффикса имени сборки: `.IntegrationTests`, `.UnitTests` и `.Tests` дают роль `test`; `.Infrastructure` — `infrastructure`; `.Contracts` — `contract`; `.UI` — `ui`. Имя модуля в этом случае равно имени сборки без суффикса: сборки `Account`, `Account.Contracts` и `Account.Tests` попадают в один модуль `Account`.
3. Во всех остальных случаях сборка получает роль `implementation`, а модулем становится она сама.

**Модуль** — это группа сборок с одним идентификатором модуля. Обычно модуль состоит из контрактной сборки (`X.Contracts`) и сборки реализации (`X`), иногда ещё из `X.Infrastructure` и `X.UI`. Именно между модулями, а не между сборками, строится граф, о котором идёт речь в семействе правил B.

Смысл ролей для правил семейства A:

| Роль | Что это | Кому разрешено зависеть от неё извне модуля |
|---|---|---|
| `contract` | публичная граница модуля: интерфейсы, DTO, события | всем ролям, кроме `shared` |
| `implementation` | тело модуля: сервисы, обработчики, хранилища | никому (только `host` и `test`, которые не проверяются) |
| `infrastructure` | адаптеры к внешнему миру внутри модуля | никому |
| `ui` | представления и view-model модуля | никому |
| `shared` | общее ядро: примитивы, идентификаторы, время | всем |
| `host` | корень композиции: регистрация DI, точка входа | не проверяется как источник рёбер |
| `test` | тестовые сборки | не проверяется как источник рёбер, но является источником для F1 и F2 |

## Учитываемые модули (scored) { #scored }

**Учитываемым** называется модуль, роль сборки которого не равна `host` и не равна `test` (`ModuleGraph.TryScoredModule`). Типы из сборок с ролями `host` и `test` не входят в граф модулей, не входят в подсчёт размеров, публичных типов, метрик Мартина и связности, не порождают находки семейств B, C, D, E, P и R.

Причина в том, что корень композиции по определению ссылается на реализации всех модулей, а тесты — на всё подряд. Если бы они учитывались, любая система выглядела бы как один большой цикл, а все модули — как «магниты». Исключений два: правила [F1](findings/F1.md) и [F2](findings/F2.md) используют тестовые сборки как **источник** рёбер, а правило [E3](findings/E3.md) учитывает типы `host` как потребителей интерфейса. На вкладке Matrix отчёта роли `host` и `test` по этой же причине выключены по умолчанию.

## Идентификатор типа { #type-id }

Тип идентифицируется строкой вида `ИмяСборки::Пространство.Имён.ИмяТипа`, например `ArchLens.Analysis::ArchLens.Analysis.GateEvaluator`. Обобщённые типы записываются по открытому определению (`IRepository<Order>` и `IRepository<User>` — это один узел `IRepository<T>`). Вложенные типы получают **эффективную** доступность: вложенный `public` внутри `internal` класса считается `internal`. Именно эти строки видны в колонках From и To таблицы Evidence и в файлах `findings.json` и `graph.json`.

## Рёбра между типами и их виды { #edge-kinds }

Экстрактор (`RoslynGraphExtractor`) строит ребро **из типа-источника в тип-цель** для каждого места, где тип упоминает другой тип решения. Внешние типы (BCL, NuGet) отбрасываются целиком: ребро в них не создаётся. Ребро типа в самого себя не создаётся.

| Вид ребра (`EdgeKind`) | Имя в JSON | Откуда берётся |
|---|---|---|
| `Inheritance` | `inheritance` | базовый класс (кроме `object`, `ValueType`, `Enum`, делегатов) |
| `Implementation` | `implementation` | реализуемый интерфейс |
| `FieldType` | `fieldType` | тип поля или свойства |
| `Parameter` | `parameter` | тип параметра метода, конструктора или индексатора |
| `Return` | `return` | тип возвращаемого значения метода |
| `Call` | `call` | вызов метода другого типа или создание его экземпляра (`new`) в теле метода или аксессора |
| `Attribute` | `attribute` | атрибут на типе, методе или свойстве |
| `GenericArgument` | `genericArgument` | аргумент обобщённого типа (`Task<Order>` даёт `genericArgument` на `Order`) |
| `Binding` | `binding` | не извлекается из кода, а выводится из регистраций DI (см. [ниже](#binding-edge)) |

## Вес ребра { #weight }

**Вес** — это число вхождений. Каждое упоминание типа добавляет `1` к ребру `(источник, цель, вид)`. Метод с тремя параметрами типа `Order` даёт `parameter: 3`; пять вызовов методов `OrderService` из одного класса дают `call: 5`. Вес не нормируется и не взвешивается по «важности» вида ребра: `call` и `parameter` считаются одинаково.

Когда речь идёт о **весе между модулями**, суммируются веса всех рёбер между типами двух разных учитываемых модулей, всех видов вместе. Рёбра внутри одного модуля в межмодульный вес не входят.

## Граф модулей (`ModuleGraph`) { #module-graph }

**Граф модулей** — ориентированный взвешенный граф, который строит `ModuleGraph.Build`:

- **узлы** — учитываемые модули, у которых есть хотя бы один тип;
- **ребро A → B** существует, если хотя бы один тип модуля A ссылается на тип модуля B; вес ребра равен сумме весов всех таких рёбер между типами (любых видов);
- рёбра внутри модуля (из типа модуля A в другой тип того же модуля A) в граф не попадают;
- типы сборок с ролями `host` и `test` не участвуют ни как источник, ни как цель.

На этом графе считаются `cycles`, `tanglePct`, `feedbackWeight`, `propagationCost`, `sharedGravity`, `fanInOut`, `coreSize`, `coreShare`, `maxModulePath`, метрики Мартина и правила B1–B9, P1, P3, G4.

### Чем граф модулей отличается от матрицы на вкладке Matrix { #dsm-vs-modules }

Матрица зависимостей (DSM) на вкладке Matrix — это проекция графа типов на **компоненты**, которые задаются правилами `rules` в `arch-lens.yaml` (по шаблонам пространств имён) либо, без конфигурации, пространствами имён. Граф модулей строится по **сборкам и ролям**. Это два разных разбиения одного и того же множества типов, и они могут не совпадать: клетка `Projection → Loading` в матрице может состоять из рёбер в типы сборки `ArchLens.Shared`, которые YAML отнёс к компоненту Loading, тогда как для графа модулей это ребро `Projection → Shared`. Чип `cycles` в шапке отчёта считает циклы **между компонентами матрицы**, а раздел Cycles на вкладке Metrics — циклы **между модулями**. Одно может быть нулём при ненулевом другом.

## Компонента сильной связности (SCC) и цикл модулей { #scc }

**Компонента сильной связности** (strongly connected component, SCC) — это максимальное множество узлов, в котором из каждого узла можно по стрелкам дойти до каждого другого и вернуться. Arch Lens находит компоненты алгоритмом Тарьяна (`StronglyConnectedComponents.Find`).

**Циклической** называется компонента размером два и больше. Одиночный модуль без ребра в самого себя циклической компонентой не считается (а рёбер модуля в самого себя в графе модулей не бывает по построению). Список циклических компонент графа модулей — это метрика [`cycles`](metrics/cycles.md) и основание правила [B1](findings/B1.md). Каждая компонента записывается как отсортированный список идентификаторов модулей.

### Конденсация графа { #condensation }

**Конденсация** — граф, в котором каждая компонента сильной связности (включая одиночные модули) стянута в один узел. Конденсация всегда ациклична. Самый длинный путь в ней, измеренный в **рёбрах**, — это метрика [`maxModulePath`](metrics/maxModulePath.md). Цепочка из четырёх модулей `A → B → C → D` даёт путь длиной 3.

## Fan-in и fan-out { #fan }

Для модуля **fan-in** — это число **различных** модулей, у которых есть хотя бы одно ребро в него; **fan-out** — число различных модулей, в которые у него есть хотя бы одно ребро. Это счётчики соседей, а не суммы весов: ребро с весом 900 и ребро с весом 1 добавляют по единице. Считаются только учитываемые модули. В метриках Мартина эти же числа называются `afferent` (Ca, fan-in) и `efferent` (Ce, fan-out).

## Находка (`Finding`) { #finding }

**Находка** — запись `Finding` с полями:

| Поле | JSON | Смысл |
|---|---|---|
| `Rule` | `rule` | код правила: `A1`, `B2`, `E3` и так далее |
| `Class` | `class` | класс: `invariant`, `ratchet` или `trigger` (см. [ниже](#class)) |
| `Fingerprint` | `fingerprint` | отпечаток для сопоставления с `knownFindings` (см. [ниже](#fingerprint)) |
| `FromModule` | `fromModule` | модуль-источник или `null`, если находка относится ко всему репозиторию |
| `ToModule` | `toModule` | модуль-цель или `null` |
| `Message` | `message` | строка сообщения; её формат фиксирован в коде и приведён на странице каждого правила |
| `Evidence` | `evidence` | список свидетельств: пар `from → to` с разбивкой веса по видам рёбер; для многих правил пуст |

Находки одного запуска отсортированы по отпечатку (ordinal), поэтому порядок строк в таблице Findings и в `findings.json` не зависит от порядка обхода.

## Классы находок и их влияние на вердикт { #class }

| Класс | Влияние на `arch-lens gate` | Смысл |
|---|---|---|
| `invariant` | вердикт `block`, код выхода 5 | нарушение правила, которое не имеет «допустимого уровня»: запретное ребро, новый цикл модулей, `InternalsVisibleTo` в нетестовую сборку |
| `ratchet` | вердикт `block`, код выхода 5 | число стало **строго больше**, чем зафиксировано в `baseline.json` |
| `trigger` | вердикт `triggers`, код выхода 4, если нет ни одной находки классов `invariant` и `ratchet` | запах, выброс, предмет для ревью; не блокирует сам по себе |

Вердикт вычисляется в `GateEvaluator` так: если среди оставшихся находок есть хотя бы одна класса `invariant` или `ratchet` — `block`; иначе, если находки вообще остались — `triggers`; иначе — `pass`. Подробнее на страницах [pass](gates/pass.md), [triggers](gates/triggers.md), [block](gates/block.md).

## Ratchet: порог в baseline, который нельзя ухудшать { #ratchet }

Слово `ratchet` в Arch Lens означает **числовой порог, зафиксированный в `baseline.json`, который запрещено ухудшать**. Гейт сравнивает текущее значение метрики с сохранённым и выдаёт находку класса `ratchet`, когда текущее значение **строго больше** сохранённого. Равенство — не нарушение. Улучшение (текущее значение меньше сохранённого) не переписывает baseline автоматически: чтобы «закрепить» улучшение, нужно осознанно выполнить `arch-lens baseline` и закоммитить новый файл.

Сравнение выполняется оператором `>` без допуска (ε): для дробных метрик (`tanglePct`, `propagationCost`, `sharedGravity`, `testsPastContract`) любое увеличение, даже в последнем знаке, блокирует. Значения записываются в JSON без потери точности, поэтому неизменившийся граф даёт в точности то же число.

Ratchet-порогов семь (`RatchetSet`):

| Ключ в `baseline.ratchets` | Тип | Правило | Что значит отсутствие ключа |
|---|---|---|---|
| `publicInImplementation` | словарь модуль → целое | [A3](findings/A3.md) | новый ключ модуля даёт находку класса `trigger` |
| `contractSurface` | словарь сборка → целое | [A4](findings/A4.md) | новый ключ сборки даёт находку класса `trigger` |
| `tanglePct` | число 0…1 | [B2](findings/B2.md) | читается как `0` |
| `feedbackWeight` | целое | [B3](findings/B3.md) | читается как `0` |
| `propagationCost` | число 0…1 | [B4](findings/B4.md) | читается как `0` |
| `sharedGravity` | число 0…1 | [B9](findings/B9.md) | читается как `0` |
| `testsPastContract` | число 0…1 или отсутствует | [F1](findings/F1.md) | отсутствие даёт находку класса `trigger` с сообщением `new ratchet F1`, а не сравнение с нулём |

Обратите внимание на разницу: для четырёх скалярных порогов графа отсутствие ключа означает ноль, и любое положительное значение сразу блокирует; для `testsPastContract` и для словарей отсутствие ключа — это отдельный сигнал «порог ещё не зафиксирован».

## Отпечаток находки (`Fingerprint`) { #fingerprint }

**Отпечаток** — это SHA-256 (в нижнем регистре, шестнадцатеричная строка из 64 знаков) от UTF-8-строки `правило\nот\nк\nвиды`, где `от` и `к` — идентификаторы типов, модулей или сборок (в зависимости от правила), а `виды` — имена видов рёбер через запятую в ordinal-порядке (`FindingFingerprint.ForTypeEdge`). На странице каждого правила указано, что именно подставляется в эти четыре части. Например, для [B2](findings/B2.md) все три части после кода пусты, и отпечаток один на весь репозиторий; для [A1](findings/A1.md) в отпечаток входят оба типа и набор видов рёбер между ними.

Практическое следствие: у правил, включающих виды рёбер в отпечаток (A1, A2, A5 для вызовов, A6, G1), появление **нового вида** зависимости между теми же двумя типами (например, к `parameter` добавился `call`) даёт **новый** отпечаток, и находка, ранее занесённая в `knownFindings`, всплывает снова.

## `baseline.json`: структура { #baseline }

Файл создаёт команда `arch-lens baseline` (`BaselineFactory.FromMetrics`), читает — команда `arch-lens gate --baseline`:

```json
{
  "version": 1,
  "ratchets": { "publicInImplementation": {}, "contractSurface": {}, "tanglePct": 0, "feedbackWeight": 0, "propagationCost": 0, "sharedGravity": 0, "testsPastContract": 0 },
  "knownFindings": [ "…отпечатки…" ],
  "knownCycles": [ [ "A", "B" ] ]
}
```

- `ratchets` — семь порогов, описанных [выше](#ratchet); при создании в них копируются **текущие** значения метрик.
- `knownFindings` — отпечатки **всех** находок текущего снимка, включая находки классов `trigger` и `invariant`. Это способ «замораживания» уже существующего долга.
- `knownCycles` — список циклических компонент текущего графа модулей.

### Что глушит `knownFindings`, а что — нет { #known-findings }

Гейт (`GateEvaluator.Evaluate`) сначала проходит по находкам снимка и **отбрасывает** те, чей отпечаток есть в `knownFindings`. Затем он **синтезирует** новые находки: [B1](findings/B1.md) из списка циклов, [B2](findings/B2.md), [B3](findings/B3.md), [B4](findings/B4.md), [B9](findings/B9.md), [F1](findings/F1.md), [A3](findings/A3.md), [A4](findings/A4.md) из сравнения с `ratchets`, а при `--against` — [G1](findings/G1.md), [G2](findings/G2.md), [G3](findings/G3.md), [C4](findings/C4.md), [A8](findings/A8.md). Синтезированные находки в `knownFindings` **не проверяются** (исключение — G1, которая сама заглядывает в `knownFindings`). Поэтому:

- занести в `knownFindings` отпечаток B2 или B1 бесполезно — гейт его не читает;
- B1 глушится только через `knownCycles` (совпадение множества модулей);
- ratchet-находки глушатся только возвратом метрики к порогу либо осознанным поднятием порога командой `baseline`;
- находка F1 из снимка гейтом всегда пропускается и заменяется собственной, синтезированной из `testsPastContract`.

## Команды и артефакты { #commands }

| Команда | Что делает | Что пишет |
|---|---|---|
| `arch-lens map <sln>` | извлекает граф, считает метрики и находки снимка | папка `arch-lens-out/ггггММдд-ЧЧммссZ/` с `graph.json`, `dsm.html`, `metrics.json`, `findings.json` |
| `arch-lens baseline <sln>` | считает метрики и фиксирует пороги, отпечатки и циклы | `baseline.json` |
| `arch-lens gate <sln> --baseline baseline.json [--against old-graph.json]` | сравнивает снимок с baseline (и, при `--against`, с предыдущим снимком), выносит вердикт | `gate-report.json` в `-o` (по умолчанию `arch-lens-out`, без подпапки с датой), в консоль `verdict=…`, `findings=…`, `report=…` |
| `arch-lens diff --from … --to …` | визуальное сравнение контрактов | отчёт, открытый на вкладке Contracts, плюс `contract-diff.json`; **не** выносит вердикт и не порождает находки гейта |

**Находки снимка** (их пишет `map` в `findings.json` и показывает вкладка Findings): A1, A2, A5, A6, A7, B5, B6, B7, B8, C1, C2, C3, D1, D2, D3, E1, E2, E3, E4, F1 (как `trigger` со свидетельствами), F2, P1, P3, R1, R2, а также G4, если включён анализ совместных изменений. **Только гейт** синтезирует A3, A4, B1, B2, B3, B4, B9, F1 (как `ratchet`) и, с `--against`, A8, C4, G1, G2, G3. Эти коды никогда не появятся на вкладке Findings отчёта `map`.

Коды выхода: `0` — `pass`, `1` — ошибка использования, `2` — не удалось загрузить решение, `3` — непредвиденная ошибка, `4` — `triggers`, `5` — `block`. Команды `map`, `baseline` и `diff` возвращают только `0`–`3`.

## Настройки в `arch-lens.yaml` { #yaml }

```yaml
docsBaseUrl: https://dkharevichinn.github.io/arch-lens-docs   # адрес этого каталога для ссылок из dsm.html
modules:
  conventions: true            # выводить роли из суффиксов имён сборок
  assemblies:                  # явные переопределения
    - assembly: ArchLens.Shared
      role: shared
    - assembly: ArchLens.Host
      role: host
      # module: ИмяМодуля      # необязательно
rules:                         # проекция пространств имён на компоненты матрицы (DSM)
  - pattern: "ArchLens.Analysis"
    component: "ArchLens.Analysis"
gate:
  blastRadiusThreshold: 4      # G3
  coreSizeMin: 3               # B5
  maxModulePath: 6             # B6
  coChange:
    maxCommits: 0              # G4; 0 означает «выключено»
    minPair: 3                 # G4
```

Пороги, которых **нет** в YAML и которые зашиты в коде константами: 0.3 / 0.5 для B8, 20 и 3× медиана для C1, 4× и 20 для C2, [1.5, 4] и 4 типа для D1, 3 типа для D2, кластер 4 для D3, `max(10, 2 × медиана)` для E1, длина 8 и расстояние 2 для E4, 5 и 70 % для P1 и C4, ограничения в 20 находок для D3, E1, E2, E3, E4 и 10 свидетельств для F1.

## Порт, потребитель контейнера и рёбра `binding` { #binding-edge }

**Порт** — интерфейс или абстрактный класс (`BindingSemantics.IsPort`). Абстрактный `record` портом не считается, потому что экстрактор присваивает записям вид `record`, а не `class`.

**Потребитель контейнера** — тип, который встречается как сервис или как реализация хотя бы в одной регистрации DI, сделанной **не** из тестовой сборки (`BindingSemantics.IsContainerConsumer`). Внедрения через конструктор учитываются только у потребителей контейнера: класс, который нигде не зарегистрирован, для правил R1, R2 и для метрик `runtime` невидим, даже если у него есть конструктор с параметром-портом.

**Ребро `binding`** выводится (`BindingResolver.Resolve`) для тройки «потребитель внедряет порт S, а S зарегистрирован с реализацией T»: получается ребро `потребитель → T` вида `binding`. Вес равен числу таких троек между одними и теми же потребителем и реализацией. Эти рёбра не входят в граф модулей и не влияют на метрики семейства B; их используют только [R1](findings/R1.md), метрика [`runtime`](metrics/runtime.md) и переключатель «resolve DI» на вкладке Matrix.

## Публичность, `PublicMembers` и `PublicApi` { #public }

Тип считается публичным, если его **эффективная** доступность равна `public` (с учётом вложенности, см. [идентификатор типа](#type-id)).

`PublicApi` типа — отсортированный список идентификаторов документации (`GetDocumentationCommentId`, например `M:Account.Contracts.IAuth.Login(System.String)`) всех его явно объявленных публичных членов, кроме аксессоров свойств и событий (`get`, `set`, `add`, `remove`) и членов из сгенерированного кода. `PublicMembers` — длина этого списка. Идентификатор документации включает имя члена и **типы** его параметров, но не их имена: переименование метода или изменение типа параметра даёт новый идентификатор (для [A8](findings/A8.md) это удаление старого члена и добавление нового), а переименование параметра при тех же типах идентификатор не меняет. Вложенный публичный тип попадает в этот список как член внешнего типа и одновременно учитывается как самостоятельный тип.

## LOC { #loc }

`Loc` типа — число строк исходного текста, занятых его объявлением (от строки начала до строки конца, включительно, суммарно по всем `partial`-частям), без учёта сгенерированных файлов. Это не «логические строки» и не число операторов; пустые строки и комментарии внутри объявления входят в счёт.

## Медиана { #median }

Медиана набора чисел — среднее значение после сортировки. При нечётном числе элементов это центральный элемент; при чётном — среднее арифметическое двух центральных, поэтому в чипах `median types` и `median loc` возможны половинные значения (`5.5`).

## Детерминизм и ordinal-порядок { #ordinal }

Везде, где нужен порядок или разрешение ничьих, Arch Lens сортирует строки по ordinal-сравнению (`StringComparer.Ordinal`): побайтно по кодам символов, где заглавные латинские буквы идут раньше строчных. Это делает результат воспроизводимым между запусками и машинами, но означает, что при равенстве очков «победителя» выбирает имя, а не архитектурный смысл. На страницах правил такие места отмечены словами «ничья разрешается по ordinal».
